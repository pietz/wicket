# Wicket's native UI system: design, revision 2

Revises docs/reviews/2026-11-08-ui-system-design.md with Astra's challenge, the structured-output spike, the owner's round-2 calls, T3 Code's handling of questions and approvals, and the mockups. Nothing here reopens the agreed core: one shared vocabulary, host-owned native rendering, harness structured output, present-only agent in v1, revision-bound extension execution, explicit navigation, no generated styling or executable UI, no replay of acting tasks.

## 1. Principles

1. **Semantic, never visual.** A component says what content is (a collection of things, a labelled fact, a file), never how to draw it. No colours, fonts, columns or layout containers. Wicket owns the look, so agent output and search results can't drift apart.
2. **Two surfaces, already there.** Rows (selection, Return, ⌘K) and pages (measured, scrolling). Every component is a row, a page, or a slot in one. Depth is navigation, which the frame stack already handles.
3. **Bounded composition.** One screen per reply, with fixed slots: a summary, labelled facts, one collection. No block trees. The slots are enough for "three invoices, €420, one overdue" and keep selection and sizing computable.
4. **Entities over presentation.** When Wicket can derive icon, actions, preview and dates from an identifier with APIs it already links, the producer sends the identifier. Subjects enrich; they never forbid descriptive fields.
5. **Markdown is the escape hatch.** A component must do something markdown can't: be selectable, acted on, derived from an entity, or drawn from data (a chart). Otherwise it is prose in a page.
6. **One vocabulary, one authority model.** Agents and extensions share every type. Authority is a value carried by the screen and checked where an action is activated, not a second format.
7. **The schema is the advertisement.** The agent sees only what the running build draws. Tiers grow when a use case appears.
8. **Two demonstrated use cases or it waits.** A component ships when two concrete uses exist (agent prompts from the evaluation set, an extension, a built-in). A hypothetical isn't one.

## 2. Vocabulary and tiers

A reply is one **screen**: `answer`, `list` or `detail`. The kind is chosen by intent (section 7), not by count.

### v1

**answer**: one scalar fact. `{"answer":{"title":"23:41","subtitle":"Monday, 9 Nov · JST","accessory":"UTC+9"}}`. The 60 pt prominent row; Return copies the title.

**list**, the composed reply:

```json
{"list":{
  "summary":"Three invoices, one overdue.",
  "facts":[{"label":"Total","value":"€420"},{"label":"Overdue","value":"1"}],
  "sections":[{"title":"Overdue","items":[{"file":"~/Documents/Invoices/Hetzner 2026-10.pdf","accessory":"since Nov 3"}]},
              {"title":"Due","items":[{"file":"~/Documents/Invoices/Telekom.pdf","accessory":"€180 · Nov 14"}]}]}}
```

- `summary`: markdown with inline styles and links, pinned above the rows, not selectable. Adaptive, no hard clip: it shows whole when it fits beside the rows (three lines or fewer, or the list has at most three rows); otherwise it shows its first three lines with a trailing "more", and **Read Summary** (a screen action, ⌘K) pushes it as a page with the facts as metadata. Expansion is navigation, so there is no third keyboard model.
- `facts`: labelled values as a compact strip under the summary, up to four; more go to the pushed page. A fact's value may be a `file` or `url` subject in v2.
- `items` or `sections` (titled groups, headers skipped by the arrows), never both.
- Sizing: summary, facts and headers are measured; rows stay whole, so the eight-row rule holds.

**detail**: markdown, `metadata`, `actions`, as today. Documented adaptive layout, not a heuristic: metadata goes in the 180 pt sidebar when the markdown measures taller than the metadata column, otherwise full width as a two-column table under the text. The producer sees one rule in the docs; nothing in the data chooses it.

**Subjects**: `file`, `url` on any item (section 3).

**Actions**: `open`, `copy`, `detail`, plus host-derived `reveal` and Quick Look. Extensions keep `paste` and `run`.

### v2

- **choices** (agent only): a block of reply rows above the collection (section 6).
- **image**: on an `answer`, a `detail` or a grid tile: `{"image":{"file":"~/…"}}` or `{"image":{"url":"https://…","alt":"…"}}`; remote only with "Show online content" (section 5).
- **grid**: `{"grid":{"items":[…]}}`, same items, two-dimensional arrows, Quick Look thumbnails for `file` items.
- **show**: pushes any screen in hand, `detail` staying as its alias.
- **Typed values**: a metadata value or accessory may be `{"date":"…"}` (relative, localized) or a subject.

### Later, on two use cases

`chart` as a slot in the composed reply (one series of labelled values, Swift Charts, rows below keep Return meaningful); `table` as typed rows when markdown tables prove insufficient; `timeline` as a dated list; `app` and `color` subjects; `form` (extension only). Rejected still: layout containers, free block trees, custom colours, streaming patches, executable UI.

## 3. Subjects and identity

| Subject | Derived title | Subtitle | Icon | Accessory | Actions | Preview |
|---|---|---|---|---|---|---|
| `file` | last path component | parent folder, `~`-relative | Finder icon | modified date, relative | Open, Reveal in Finder, Copy Path | Quick Look on Space |
| `url` | host, else the URL | path | `globe`, `envelope` for mailto | none | Open, Copy Link | none |

Producer fields win over derived ones. Derived actions follow the producer's, deduplicated by kind and target. The primary action is the producer's first; without one, the subject's Open.

**Canonical form.** A file subject is parsed as `Location` is today (absolute, `~/`, or `file:`), then standardized and symlink-resolved, so Claude's `/private/tmp/x` and Codex's `/tmp/x` are one file. The display keeps the standardized `~`-relative path.

**Default ids.** With a subject, the id defaults to `file:<canonical path>` or `url:<absolute URL>`, so fourteen `.DS_Store` rows never collide. Without one, the title, as today. Duplicate ids under agent authority get an ordinal suffix and a logged count: the model can't be sent the error. Under extension authority duplicates stay an error, which is the contract.

**Missing and deleted targets.** A subject that doesn't exist at decode still shows, with the generic icon and subtitle "Not found", no Quick Look; Open reports it gone, as links do now. A target deleted after decode is caught at activation with the same message. Reveal of a missing file reveals its folder.

## 4. Authority through dispatch

An `Authority` (`.host`, `.extension(revision)`, `.agent`) is stamped on the `Screen` at decode and carried by its `ScreenFrame`. A pushed page inherits the authority of the screen that pushed it. The `ActionTarget` carries it to the dispatcher.

One `ActionPolicy` in Core answers, for an action and an authority, what actually runs: the action, a rewrite, or nothing. It is used in three places:

- **Decode**, recursively: a walker visits every action, including those inside `detail` actions, and a disallowed one fails the reply. The agent schema never offers `run` or `paste`, so one appearing means the schema was bypassed, and the fallback (section 8) applies.
- **Activation**: `ActionDispatcher.perform` applies the policy to every action, derived ones included. Under `.agent`, `.open` goes through today's `Item.Action.following` logic, which moves from the palette's link handler into the policy: web, mail and files open, apps and scripts are revealed. `.run` is refused outright. This is the fix for today's gap, where the dispatcher opens `.open` directly and the restriction lives only in the link path.
- **The action panel** names the real target ("Reveal Script.sh in Finder").

Agent rows take origin `builtin:run-agent`, ids namespaced per run, no frecency.

## 5. Images and online content

**Who fetches.** Wicket, never the agent or the extension process: an ephemeral `URLSession`, https only, no cookies or referrer, redirects only to https, 5 s timeout, 5 MB cap, ImageIO formats only (no SVG), decoded and downsampled off the main thread to the shown size. A local `image` file uses `QLThumbnailGenerator`, which needs no setting.

**The setting.** "Show online content" in Settings ▸ General, off by default, covers every network fetch a screen causes for any producer: remote images now, link previews or favicons if they ever come. It never covers what the agent itself fetched during its run; that is the agent's permission level. When off, the slot shows a glyph and the panel offers **Load Image** for this one screen, so a single photo needs no setting change.

**Caching and privacy.** Memory cache for the session, a disk cache of 50 MB in Application Support (not the config folder), cleared by Settings. A fetch reveals the user's address and, through the URL, the query to that host, which is why the setting exists; the source host is labelled under the image as the mockup shows. Image URLs are never logged.

## 6. Choices

`{"choices":[{"text":"Yes, move them to the Trash"},{"text":"No, keep them"}]}` on any screen, v2, agent only. Rows look like the approval prompt's; Return sends the text verbatim as a Follow Up to the same session; the footer says "Send as Follow Up". Typing instead of picking is the free-text answer, as T3 Code's "Other" shares the composer. Choices carry no commands and are never consent: whatever the agent then does still meets Allow, Allow for Session or Deny.

**Harness questions.** Claude Code's AskUserQuestion (one to four questions, two to four options with label and description, a header, multi-select) and Codex's `item/tool/requestUserInput` (id, header, question, options, `isOther`, `isSecret`, blocking or async) have the same shape as a choices block, and T3 Code shows both in one question panel, one question at a time, with suggested answers editable and free text flowing into its composer. The difference is timing: a blocking harness question holds a live process waiting for an RPC answer, while our choices come after the reply and resume the session. Codex's async questions are answered by a new user message, which is exactly our Follow Up model. So: v2 keeps declining AskUserQuestion and tells the agent to end its turn with choices; the mapping of a blocking question onto a choices screen mid-run, answered through the approval token mechanism, waits until agent questions prove frequent. Secret answers never go through choices.

## 7. Host actions versus row actions

Screen-level host actions belong to the screen, never to each row: **Follow Up** (⌘↩ on every agent screen), **Copy Answer** (a text rendering: summary, facts, one line per row), **Read Summary** when clipped, **Retry** on failure, and **Review and Enable** on extension-building runs. In the action panel they form a second group named after the screen ("Answer"), as mockup 5 shows. Return and ⌘K act on the row. ⌘↩ runs the first screen action when the screen has any, else the row's second action as today, so Follow Up has one chord everywhere. `ActionTarget` gains a `screen: [Item.Action]` group; the wire never carries it.

## 8. Agent rule text

For `agent.md`, under "Your reply":

> Reply only through the structured output; write no prose outside it. Pick the screen by what the user should do next:
>
> - **answer**: one scalar fact: a number, a date, a name. Return copies it.
> - **list**: things the user may open, pick or copy, even if there is only one: files, links, results, options. One row per thing. Say what a row is (`file`, `url`) instead of describing it; Wicket adds the icon, folder, date and actions. A sentence or two of context goes in `summary`, labelled numbers in `facts`.
> - **detail**: explanation, comparison, steps, code, what you did. Markdown; facts with labels go in `metadata`.
>
> After acting, show the result: a list of what changed, or a detail saying what you did. Don't narrate the UI, don't put paths in prose when they can be rows, and don't invent fields.

Spike finding: schema descriptions alone did not steer Luna, so this text ships as instructions on every run, Follow Up included.

**Fallbacks.** Claude's success without `structured_output` keeps the prose as a detail with the notice "Shown as text". `error_max_structured_output_retries`, a decode failure or a Codex failed turn with no prose shows "The agent sent nothing Wicket can show" with Retry and Follow Up. An empty list with a summary becomes a page of the summary; empty with neither is the same notice.

## 9. Schema projection plan

The source stays `docs/extension.schema.json` (2020-12). A Core function `ReplySchema.project(.agent)` emits the provider schema; a golden copy is committed as `docs/agent-reply.schema.json` and regenerated by the check script, so a drift fails the build.

The projection, explicitly:

1. Select the profile's screens and actions from `$defs`; keep `$defs` and `$ref` (both CLIs accept them, the spike's row 9) rather than inlining, so the Detail → Action → Detail recursion terminates by reference. The agent decoder bounds nesting at depth two.
2. Root `{"reply": anyOf[{"list":…},{"detail":…},{"answer":…}]}`: the extension wire's one-key objects are disjoint `anyOf` branches, as are the action kinds. The spike's `type` discriminator is the fallback if either CLI stumbles.
3. Every property required; optionals become `anyOf [T, null]`.
4. `additionalProperties: false` everywhere; `oneOf` becomes `anyOf`; drop `format`, `if`/`then`, `uniqueItems`, `default`; keep `enum`, `const`, `pattern`, `minItems`, `maxItems`. No `$schema` keyword: Claude's validator and OpenAI strict each accept the common subset.
5. A `Reply.normalize` step removes null-valued keys recursively before the Core decoder runs, because `optionalNonEmpty` treats null as present. One normalizer, tested, instead of teaching every decoder about null.

Tests: an invariant walk over the projected schema (object root, all required, no forbidden keywords, nullable optionals); a fixture folder of replies that must normalize and decode, each key path checked against the projected schema's properties, so the schema can't advertise what the decoder rejects; nested forbidden actions rejected. The spike's driver stays as a manual live check against both CLIs.

## 10. Extension compatibility

Protocol stays 1; everything is additive: `summary`, `facts`, `sections`, `file`, `url`, `image`, later `grid`, `show`, `choices`. No meaning changes. Extensions gain subjects, derived actions, Quick Look and, with the setting, remote images. Strict decoding stays: a new field on an older Wicket fails loudly, the documented contract; the docs page gets a "since" column. Protocol 2 is for a change of meaning only. The agent schema needs no version: the build that draws it generates it.

## 11. The v1 slice

In order: (1) `Authority`, `ActionPolicy`, the dispatcher change; (2) `ReplySchema.project`, `Reply.normalize`, golden schema and tests; (3) `summary`, `facts`, `sections` with the adaptive layout; (4) `file` and `url` subjects with identity, derived dates and actions, Quick Look if `QLPreviewPanel` works with the non-activating panel in a day; (5) screen host actions and the panel group; (6) the adapters: `StructuredOutput` not acting, held-back Codex final deltas, path normalization, fallbacks; (7) `agent.md`. Not in v1: grid, image, choices, show, typed values, charts.

**Mockups versus this spec.** Mockup 1's relative times come from the file subject's modified date, so they are v1 without typed values. Mockup 2's Copy Answer chord ⌘⇧C is free but not in the spec; Copy Answer lives in the panel group. Mockup 5's caption says the Answer group is "the same on every row": it is one screen group shown once in the panel, never row actions. Mockup 6 shows the image beside an answer with full-width facts, which is `answer` plus `image` plus `facts` in v2. Mockup 7's "10 more below" is the normal list scroll, not a component.

## 12. Evaluation

**Task success**, not shape: each prompt is scored on what the user can do with one keystroke (open the right file, copy the number, read the explanation), three runs per CLI, Sonnet low and Terra low. Target 90 % valid, 80 % right screen before the owner sees it. Prompt set as in revision 1, extended with: a single-result search (list of one), fourteen `.DS_Store` files (duplicate names), a file deleted mid-run, a mixed reply (explanation plus results plus facts), a 2000-word summary (clipping), German and Japanese text, a question the model wants to ask back.

**Deterministic tests**: schema invariants, fixtures, nested forbidden actions, agent `open` of an `.app` rewritten to reveal at activation, pushed pages inheriting authority, stale targets, duplicate ids, empty screens, every fallback branch.

**Accessibility and keyboard**: VoiceOver reads the summary first, section headers as headings, rows as "name, folder, accessory"; arrows skip headers; Space previews; Escape and ⌘[ as today.

**Latency**: decode plus derivation for 500 file rows under 10 ms on the main thread, icons and dates loaded off it; hotkey-to-visible unchanged, since nothing here runs at summon.

## 13. Open decisions, with recommendations

1. **⌘↩ is Follow Up on every agent screen,** taking the row's second action to ⌘K. Recommend yes: one chord everywhere beats Reveal on ⌘↩.
2. **Summary expansion as a pushed page** rather than an inline toggle. Recommend the page: no new keyboard state, and it doubles as Copy Answer's text.
3. **Duplicate ids under agent authority** tolerated with a suffix, strict for extensions. Recommend this split.
4. **Load Image per screen** when "Show online content" is off, versus a glyph only. Recommend the action: consent for one photo without flipping a global setting.
5. **Harness questions stay declined in v2**, choices come from the reply. Recommend yes, and revisit with counts of declined questions.
6. **Root wrapper** as the extension wire (`{"reply":{"list":…}}`) rather than the spike's `type` discriminator. Recommend the wire shape for one decoder, with the discriminator as the tested fallback.
7. **Quick Look in v1** only if it fits in a day. Recommend yes; it is the proof that subjects pay off.
