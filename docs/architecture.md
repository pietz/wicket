# Architecture

How Wicket is built and how to add to it. Every builder reads this before touching `Sources/`. CONCEPT.md holds the why and the decisions; this page holds the shape of the code. It came out of the first architecture review (2026-11-06, Fable and Astra independently, in strong agreement); later reviews run per [reviews/architecture-review.md](reviews/architecture-review.md) and update it.

Status markers: **(now)** is how the code works today, **(target)** is what the refactor plan below builds. When a step lands, its marker goes.

## Modules

| Target | Owns | Never |
|---|---|---|
| `WicketCore` | Values and deterministic policy: `Item`, actions and their dispatcher, content (`Screen`, `RunResult`), commands, their ids and the registry, ranking, search, the navigation stack's logic, calculator, wire decoding | Processes, AppKit, SwiftUI |
| `WicketHost` | Everything that talks to another process or to OS services shared with the CLI: `ExtensionSession`, `Extensions` (discovery, the active catalog and session lifecycle), `RevisionStore` (sealed revisions), `Agent`, Keychain, login shell, checker | Windows, views |
| `WicketApp` | AppKit and SwiftUI: the panel, views, hotkeys, OS integrations (Spotlight, apps, settings window), composition and settings reconciliation (`AppRuntime`). A library so `WicketAppTests` can `@testable import` it | Policy that could be tested in Core |
| `Wicket` | The executable: only `main.swift`, which starts `WicketApp` | Anything else |
| `WicketCLI` | The `wicket` tool: a thin client over Host | Its own copies of Host logic |

Rule of thumb: if it can be tested without a window, it belongs in Core or Host, with a test.

## Core concepts

**Item: a row.** One result row from any source, with its actions. It is not a command, a screen or an execution context. Items carry a host-stamped **origin** (the `CommandID` whose response produced them; nil for the host's own sources); extension ids are namespaced by origin (`ext:<extension>/<command>:<id>`) so two extensions can't collide.

**Action: data.** What an item can do: `open`, `copy`, `paste`, `reveal` (host only), `detail` and `run` (a `CommandID`: resolved at decode to a command of the item's own extension, so only the host can name a built-in; the host may add `text` to submit, as a fallback row does with the query). Actions never carry closures. One **dispatcher** (`ActionDispatcher`, Core) turns an action plus its context into an **outcome**:

```swift
enum ActionOutcome { case close, push(Detail), open(CommandRun) }
struct CommandRun { var command: RegisteredCommand; var invocation: Invocation; var retry: RetryPolicy; var query: String? }
```

Side effects (open, copy, paste, reveal) are injected as `ActionEffects`; the app's `SystemEffects` implements them with AppKit. `ActionContext` carries the app that was frontmost at summon, which `paste` targets; what a paste can do there (type ⌘V, or only copy and say why) is `PastePlan` (Core), carried out by `SystemEffects`. The dispatcher is synchronous: every `run` (extension commands and built-ins alike) returns `.open` with the `CommandRun` the invocation policy (below) makes of it, and the palette session runs the command for its frame; a built-in that just does something (Settings, Quit) answers `close` before a frame shows. `Item.Action` gains no cases: everything the host does for the user is a built-in reached by `run`. A `run` naming a command that isn't registered is pushed as a failure detail naming the command, which Return copies.

**Command: something you can invoke.** Built-ins (Settings, Quit, Ask AI: see Built-ins below) and extension commands share one identity, `CommandID` (in `WicketCore/Command.swift`), and one shape:

```swift
struct CommandID: Hashable, Codable, Sendable { var owner: Owner; var name: String }  // owner: .builtin or .extension(id)
struct Invocation: Sendable { var command: CommandID; var text: String; var args: [String: JSONValue]? }
```

The **command registry** (`CommandRegistry`, Core) is the one catalog: built-ins plus the extension commands the app registers. It lists the root commands (`CommandsSource` is its projection, through the shared `SearchIndex`; hidden and root-mode commands are reachable by id only), resolves a `CommandID` (the dispatcher's `run`), resolves keywords (for commands the root offers, `isOffered`: listed ones and fallbacks, and only if they take text) and offers its fallbacks (`FallbackSource`). Keyword collisions: a built-in always keeps its keyword, among extensions the first in registry order (extension id, then manifest order) wins, and losers are listed in `keywordConflicts`. Aliases and per-command hotkeys resolve through it (below); `wicket://` deeplinks and the MCP server are to as well. A built-in that belongs to a `Feature` (`RegisteredCommand.feature`) isn't registered while it is off (`setDisabledFeatures`). Persistent bindings store a `CommandID` or an `Invocation`, never a row id. A `CommandID`'s canonical spelling (`description`, `CommandID(_:)`) is `builtin:<name>` or `ext:<extension>/<command>`: settings.json keys, logs and the prefix of an extension item's id all use it.

**Invocation policy: one way in.** Each command declares how it takes text and whether a run may be repeated; the domain owns both types (`Command.swift`) and manifests translate into them (`Manifest.Command.input`, `.retry`):

```swift
enum CommandInput { case none, immediateText, submitText, liveText }
enum RetryPolicy { case never, safeToRepeat }
enum CommandTrigger { case invoked, keyword }
CommandRun(_ command: RegisteredCommand, _ trigger: CommandTrigger, text: String, args: [String: JSONValue]?)
```

`CommandRun(_:_:text:args:)` is the policy, and every way in goes through it: a row or fallback row and a `run` action (the dispatcher, `.invoked`), a hotkey (the dispatcher, as the row), `wicket run` (`.invoked` with its text and `--args`), a keyword or an alias and a space (`PaletteSession.setQuery`, `.keyword`); deeplinks and MCP will be `.invoked`. What it decides:

| Input | Who | Invoked | Keyword or alias and a space |
|---|---|---|---|
| `none` | Settings, Quit | runs now; text ignored | not routed: its alias only names it |
| `immediateText` | extension `once` (and `root`) | runs now on the text; frame on first content | runs on the rest of the line; frame at once, its field filters |
| `submitText` | Ask AI | with text: runs now; without: frame waiting for text | frame waiting, the rest of the line in its field; never runs |
| `liveText` | extension `live` | frame at once, searching the text | frame at once, searching the rest of the line |

`CommandRun.query` nil means "run now, show the frame when the first result is content"; a query means "show the frame at once with this text in its field". A frame waiting for text (`awaitsText`) runs nothing on keystrokes; its target is `.run(command:text:)` with the field, so Return submits through the dispatcher like any action and the answer opens in a frame of its own (Escape goes back to the question). `retry` is the command's own, never inferred from how it was reached or whether it is listed: `never` by default; `safeToRepeat` for live and root runs (searches) and once commands whose manifest says `repeatable`. Built-ins never reach `ExtensionSession`, so theirs only documents intent.

**Bindings: hotkeys and aliases.** `Settings.commands` (`"commands": {"builtin:ask-ai": {"hotkey": "ctrl+option+a", "alias": "ask"}}`) maps a `CommandID` to a `CommandBinding`; each bad key, hotkey or alias is ignored on its own with its reason, and an entry for a command that isn't registered stays in the file, inert, until it is. Aliases go into the registry (`setAliases`): typed alone, an alias puts its command in the `alias` tier, above every exact match; followed by a space it is the command's keyword (for an offered command that takes text; Settings and Quit take none, so their alias only names them). Collisions: alias against alias, the first canonical id keeps it (`aliasConflicts`); an alias beats every keyword (`keywordConflicts`). Hotkeys resolve in `CommandHotkeys.resolve` (Core: the palette's hotkey always wins, then the first canonical id; unregistered commands take no key), and the app's `HotKeys` registers one Carbon hotkey each, with the palette's own, re-registered on every settings reload and registry change (see App runtime). A pressed hotkey goes to `PaletteController.run(bound:)`, which dispatches `.run(command:)` like the command's row: an effect closes, a frame opens (a hidden palette is shown when the frame has content or after 250 ms of running, so a toggle answering `close` shows only its message; a frame with a query, such as Ask AI's waiting for its question, shows at once), and the same hotkey again closes the frame. No keyword text is typed, so no other command's keyword or alias can take the hotkey. A binding is a preference: it never enables or approves an extension. A binding of an extension command that isn't approved is inert like any unregistered one, and takes effect when its revision is approved (see Consent).

**Content: what a screen shows.** One content model for everyone, not only extensions (`WicketCore/Content.swift`, with public initialisers):

```swift
enum Screen { case answer(Item), list([Item]), detail(Detail) }
enum RunResult { case show(Screen), close(message: String?), reload(message: String?) }
```

`Screen` is what a frame above the root shows, whether a command's run sent it or a `detail` action pushed it. What a frame needs to know about a screen, without switching over its cases, are its own properties: `items` (the rows a selection moves through: an answer's one, a list's; nil for a page, whose view lays out its content and measures it to size the card), `title` (a page's, for the pill) and `target` (a page's actions). The wire format is the encoding (`Extension/Decoding.swift`); it has no `show`: `answer`, `list` and `detail` are decoded into it, `close` and `reload` as they are. A new screen (a grid, a form) is a `Screen` case with those properties, its decoding, and its view in `FrameContent`, the one switch from a screen to a view; the frame, sizing, pill, target, failures and reload follow. New interaction it brings (a form's fields and submit, a grid's sideways selection) is its own work on top.

**Command runs: a stream of content.** Whatever a command shows comes from one interface:

```swift
protocol CommandRunner { func run(_ invocation: Invocation, retry: RetryPolicy) -> AsyncThrowingStream<RunResult, any Error> }
```

Each element replaces the content of the command's frame (the rule `ResultSource.updates` has for root sources); `close` closes the palette with its message; `reload` drops the frame (or, if it was never shown, doesn't show it) and runs the frame it was opened from again, with its message; an error replaces the content with a failure detail; ending the iteration (pop, dismiss, a superseding query) must stop the frame's own work, never work it only observes (a build job, owned by the runtime, see Build jobs). `Extensions` (Host) is the first producer: one element per run. A streaming AI answer is a built-in producer behind the same protocol, yielding a growing detail (`.show(.detail)`) again and again; the frame keeps its id and generation across elements, so its view updates in place (scroll position kept: the card content is identified by the frame's id), and the pill spins until the stream ends. Ask AI (`AskAIRunner`, Host) is the second. The session gets one runner, `CommandRouter` (Core): built-ins go to their runner in the app's table, extension commands to `Extensions`; a command nothing runs fails its frame. A run cancelled before its task starts (Escape, another command opened) never calls its runner.

**Built-ins: one table.** Wicket's own commands are data: a `Builtin` (Core) is a `RegisteredCommand` (id, title, icon, input, retry, keyword, fallback, feature) plus its `CommandRunner`, and `AppRuntime.live()` holds the one table of them (tests compose their own). `AppRuntime.init(builtins:)` gives the registry their commands (in table order, which the Shortcuts pane follows) and the router their runners. `Builtin(_:effect:)` is a built-in that just does something: its runner (`EffectRunner`) runs the effect and yields `close` (Settings shows the settings window, Quit terminates). Ask AI's runner is `AskAIRunner` (Host), which reads the applied `ai.provider` on each question. Make a Command (`builtin:make-command`, keyword `make`, `submitText`) is `MakeCommandRunner` over the runtime's `BuildJobs`, and its frame's Stop action is the hidden `builtin:stop-build` (`StopBuildRunner`). Extensions (`builtin:extensions`, keyword `extensions`) and the hidden `builtin:review-extension`, `builtin:enable-extension` and `builtin:disable-extension` are four entries sharing one `ExtensionsRunner` (Host; see Consent). Nothing names a built-in outside its entry except app code that invokes one by id (⌘, runs `CommandID.settings`).

**Palette session and frames.** `PaletteSession` (Core, `@Observable`) owns a stack of **frames** (`Frame`): each keeps its id, query, content (`.search(RootResults)` for the root, `.screen(ScreenFrame)` for everything above it: the latest `Screen` and the `CommandRun` feeding it, nil for a page a `detail` action pushed, which never runs, so a `reload` landing on it does nothing), selection (in its `ItemList`), load state and generation. Escape stops a command being opened, else clears the text, else pops, else hides (`escape()` says which). Return, ⌘↩, ⌘K and ⌘1 to ⌘9 act on the top frame's `ActionTarget` (the selected item's actions, or the detail's). Every restart of a frame's work (a root or live query, a reload) starts a new generation; work results are applied only if frame identity and generation still match, and work is cancelled on pop, dismiss (`reset()`) and superseding queries.

How commands open: typing a registered keyword and a space in the root (`setQuery`) resolves the command with `.keyword` and leaves the keyword in the root's field; `open(CommandRun)` takes the policy's run, from the keyword or an action's outcome. A run with a `query` pushes its frame at once with that text in its field (a live command, a keyword's once command, a command waiting for its text); anything else stays `opening` (the pill spins, other actions wait, Escape cancels) until its first result: content pushes the frame with it, `close` and `reload` act without a frame ever showing. A live frame runs again on every query change after `liveDebounce` (50 ms; a burst sends only the last text, and the superseded run is cancelled), with its command's retry. A once frame filters a list locally by title with the shared fuzzy matcher (`SearchIndex`), never running again for it. The selection follows its item when content is replaced and goes to the top when the text a list answers changes.

Compactness follows the frame (`Frame.isCompact`): the root with an empty query is the bare pill, and so is a live command with an empty query and an empty list, and a command waiting for its text (its placeholder is the prompt); any other pushed frame is content (an empty list shows "No Results"). While a pushed command frame has no content yet the card keeps its height. `PaletteSession.onClose` asks the app to close; a `close` or `reload` message is posted to the session's `messages` after it (see Messages). `PaletteModel` (app) adds only view state (focus, the action panel, the card height, the footer message) and usage; `PaletteController` turns intents into session calls.

**Root search.** `ResultSource` (Core: `instant` plus optional `updates`) is the interface for the root frame only, and stays fast and synchronous on the keystroke path. Root-mode extension commands are one source (`ExtensionRootSource`, Host): after 80 ms without a newer query, each root command whose `pattern` matches gets the text, and its answer or first 10 items join the results as they arrive; failures are recorded in the diagnostics like any failed run (see Diagnostics), never shown inline. `RootResults` (Core) aggregates: each source's latest items, generation checks (a late update for an older query is dropped), ranking. `Ranker` orders by tier (alias, exact, answer, match, fallback), then three policies within a tier: user-ordered fallbacks (fallback items whose origin is in the user's list, in that order; the list itself is a later settings field, `fallbacks: [CommandID]`, not added while Ask AI is the only fallback), host-scored candidates (apps, files, built-ins: score plus frecency, none for fallbacks), then provider-ordered results (each extension command's items as one block, in the order sent, never reordered by habit). Selection lives in `ItemList` (Core), shared by every list: it follows the item id; if the selected item disappears the selection stays on its row (clamped), and truncation never drops the selected item.

**Extension lifecycle.** Host owns discovery, the active catalog and session replacement (`Extensions`: the old session is fully shut down before the new one starts; the app only feeds it folder changes), each extension's **sealed revision** (see Revisions), the **approved revision** (see Consent) and diagnostics. Discovery does not imply permission to run:

```swift
struct DiscoveredExtension { id; folder; state; sealed; approved }
enum State { case approved(SealedRevision), changed(approved: SealedRevision?, current: SealedRevision),
             unapproved(SealedRevision), invalid(String, approved: SealedRevision?) }
typealias Activation = @Sendable ([DiscoveredExtension], RevisionStore) -> [SealedRevision]   // internal
Extensions(directory:, store:, approvals:, diagnostics:, configuration:)
```

`discovered` is every folder in the extensions directory with its state against the approvals as the pass read them: `sealed` is the folder's current revision, `approved` the approved revision if the store still keeps it (`RevisionStore.retained`). The **active catalog** is what the activation returns (at most one revision per extension, the first named), and only it feeds `commands` (each `RegisteredCommand` carrying its `revision`), `rootCommands` and sessions. The public initialiser always uses `approvedRevisions` (every discovered extension's `approved`); an internal one takes another activation for tests of other mechanisms (`currentRevisions`, every valid folder). `result(of:)` refuses an extension outside the catalog with `HostError.notApproved` (a discovered one) or `.unknownCommand`, before any session exists. A session runs its sealed folder (`ExtensionSession(folder: sealed.folder)`), never the authoring folder; its data folder stays per extension id. `load(changed:)` asks for a discovery pass and returns a task that ends once a published snapshot covers the request: the pass (`scan`, `@concurrent`, off the main actor) lists the folders, seals new ones and those the watcher reported (others keep their entry), runs `activate`, marks the catalog active and prunes the store; then `publish` makes it current in one main-actor step (discovery, catalog, root patterns compiled, sessions whose revision left the catalog retired, the old revisions' session reports dropped, `.discovery` diagnostics replaced) and calls `onChange`, where the app re-registers commands. A `load` during a pass is folded into one more pass, so an FSEvents burst costs at most two. The keystroke path never waits for a pass. **Frames bind to their revision:** `CommandRun` binds `Invocation.revision` to a `run` action's revision or else the command's registered one, so every run, a row, keyword, alias, hotkey or root query included, is bound to the revision active when it starts. When the registry changes, `AppRuntime.registryChanged` first stops runs of commands that are gone (`stopCommands`), then `PaletteSession.rebind(to: registry.command)`: a run bound to a revision its command no longer has is reconciled, a frame above it (opened from its old content) goes, and the run either starts again on the command as it is now (`CommandRun.rebound(to:)`: same text and args) if it and the new command are `safeToRepeat` with the same input, or stops with "The extension changed since this was opened; run it again." in its frame (an opening one shows that as its failure). A search re-run does no harm by contract; anything else might change something twice. Every request carries its command's `RetryPolicy`: only `safeToRepeat` runs are resent after a clean exit. Every termination path escalates to SIGKILL.

**Process lifetime.** Both transports (extension sessions and agent runs) start their child through `ProcessTree` (Host), which owns its stdin writer and its lifetime; the transports keep their own protocols. A member of the tree is the child; anything in its process group (`Process` gives the child its own, and a background job stays in it after the child exits); anything holding the write end of its stdout or stderr (found by scanning the user's processes' fd tables, only while a write end is still held, which the read end's peer handle tells cheaply); any process seen as a member in an earlier scan; and every descendant of those (`proc_listchildpids`, which follows children into their own sessions while their parent lives, as Codex runs commands). macOS has no subreaper and no longer shows other processes' environments, so this is what can be attributed without privileges; a process that leaves the group, closes the pipes and outlives every member it was seen through has daemonised on purpose and escapes. `stop(after:grace:)` runs once however often it's called: close stdin, wait (the child's exit is an event, descendants are polled with backoff), SIGTERM every member, grace, then SIGKILL: each member is SIGSTOPped before the next listing so none can fork in between, then all are killed. Its task finishes only when no member is alive (bounded by `killBound` if one survives SIGKILL), which also means the pipes are closed, and returns `Shutdown` for the whole tree. An extension process that exits by itself is stopped the same way (its leftovers get the grace), and the session finalizes (resend, successor, `shutdown()` callers) only after that, so `Extensions`' serialised replacement waits for the old tree, not just the process. An agent run (`AgentRun`, the handle `Agent.run` returns: its events, `cancel()`, `cancelAndWait()` and `ended`) completes only once its tree is gone: the final answer or error is held until then, a tree still running `exitGrace` after it is terminated first (`ended` says `.terminated` or `.killed`, so a build can tell a child was cut off), and a cancelled run ends without a final event (SIGTERM at once). **Quitting:** `AppDelegate.applicationShouldTerminate` answers `.terminateLater` and replies after `AppRuntime.shutdown()`, which runs once and is bounded (2 s): it stops the palette's command frames and calls `CommandRunner.shutdown()` on the router, which shuts every runner down at once: `AskAIRunner` cancels its runs and waits for their trees (each run's task ends only after `cancelAndWait`, so its scratch folder goes after the agent), `Extensions` stops every session and waits for replacements still stopping; at the same time `BuildJobs.shutdown()` cancels the running build job and waits for its agent. All refuse new runs afterwards. **Login-shell PATH:** `LoginShell.path()` (once per process, for sessions, the checker and agents) runs `$SHELL -ilc` in a session of its own (`posix_spawn` with `POSIX_SPAWN_SETSID`, since `Process` can't), so it has no controlling terminal: started from a process that has one (the CLI, tests in a terminal), an interactive shell in a background process group is stopped by SIGTTIN trying to take the terminal, which cost every such process the 5 s deadline and the fallback PATH. A shell that doesn't answer in 5 s is killed with its process group.

**Agent runs.** `Agent` (Host) yields `AgentEvent`s; `AgentProvider` (the names) is in Core so settings can choose one. `AskAIRunner` maps one answer run into its frame's content: a detail titled with the question that grows with the text (throttled to about 30 updates a second), replaced by the final answer, actions Copy Answer and Paste Answer; a provider that isn't ready or a failed run throws, so the frame shows a failure saying what to do. Agent events stay separate from extension RPC.

**Fallbacks and Ask AI.** `FallbackSource` (Core) offers one row in the fallback tier for any non-empty query per registered fallback (`isFallback`, a `submitText` command), its action `.run(command:text:)` with the query, its id `fallback:<command id>`. Ask AI is such a built-in (its entry in the table), unlisted, with the keyword `ai` (a built-in keeps it against extensions; the user's alias beats it, as every keyword); its `ai `, alias and hotkey open its frame waiting for the question. Nothing names Ask AI outside its entry, its runner and its `Feature` case. The next fallback (web search) is one more `submitText` entry.

**The checker is the gate.** `Checker.check(folder, options:)` (Host) is what approves code, so it never runs a candidate with the user's secrets, environment, files or network, and it has no mode that does: `CheckOptions` carries only the version and timeouts. It checks a `SealedRevision` and returns a `CheckedRevision { sealed; report }`, so what was checked and what will run are one identity: the candidate is the revision's retained, read-only folder, checked in place. `wicket check <folder>` is `Checker.check(folder:options:)`: it seals the folder into a temporary store (`RevisionStore.temporary()`), checks that, and deletes the store; a folder that can't be sealed fails with why, and one not named after its id only warns. `CheckIsolation` makes a scratch folder per check (realpath'd, since the sandbox matches resolved paths) with `home`, `tmp`, `data` and a generated `sandbox.sb`; the candidate (realpath'd) is readable, never writable. The session configuration it builds sets every declared secret to a placeholder, `environment` to `HOME`, `TMPDIR`, `CLANG_MODULE_CACHE_PATH` (in scratch: swift's default cache is in the unreadable per-user cache folder) and `WICKET_CHECK=1` (the session adds `PATH`, `LANG`, the `WICKET_` variables and secrets; nothing is inherited) and `wrapper` to `sandbox-exec -f sandbox.sb`, which execs the program so signals and process ownership are unchanged. It is written once the manifest is loaded (`CheckIsolation.seal`), since what it lets the candidate read depends on the program `run` names. The profile is `allow default` minus the ways out: reads under the private roots (`/Users`, `/Volumes`, `/private/var/folders`, `/private/tmp`, `/private/var/tmp`, and the home folder if it is elsewhere) except the scratch folder, the candidate, bash's here-document files and `ProgramReads` of the resolved program (each symbolic link on the way to it, read alone, and its install folder: the one above its `bin`, `sbin` or `shims`, unless that is the home, `~/.local`, `~/.local/share`, `~/Library` or `~/.config`, then the folder the program is in, or the program alone if that is one of them), plus the metadata, not the listings, of the folders above these, since Node and swift resolve the working directory component by component, so a uv, pyenv, nvm or Volta interpreter starts while the rest of the home stays unreadable (a uv extension's check also reads Wicket's uv Pythons and writes its own uv cache, see uv extensions); `network*`, `file-write*` outside the three scratch folders (plus `/dev` nodes and bash 3.2's here-document files in `/var/tmp`), the Keychain and pasteboard Mach services, `appleevent-send` and `lsopen`. Before replaying, the profile is applied to `/usr/bin/true`; if that fails (no `sandbox-exec`, or the caller is itself sandboxed) the check fails closed. No fixture: an error, nothing launched. `finish` shuts the process down before reading the session's issues, so what it writes on the way out counts. `wicket run` is the developer's explicit unsandboxed path (real environment, environment-or-Keychain secrets). Remaining exposure: the candidate can read what lies outside the private roots (the system, /Applications, /Library, /opt/homebrew, /usr/local), the whole install folder of its program, and reach Mach services the profile doesn't name; tools it runs other than `run`'s program that live under the home don't start; `sandbox-exec` is deprecated, so its presence is verified on every check rather than assumed.

**Settings versus consent.** `settings.json` holds preferences only: agents may edit it, and nothing in it can grant consent (principle 6). Consent and approval live in host-owned stores in Application Support, written only by Wicket's own UI: which extension revisions may run is `Approvals` (below); MCP server on and network for build runs come later.

**Consent (Host).** `Approvals` is the store: `approved(id) -> ExtensionRevision?`, `all`, `problem`, and the internal `approve(_:)` and `revoke(_:)`, so nothing outside Host can write it. The file is `Application Support/Wicket/approvals.json` (`ExtensionPaths.approvals`; tests pass their own), `{"version": 1, "approved": {"<id>": "<sha256>"}}`, read once at launch and written atomically (memory changes only after the write). It fails closed: a missing file approves nothing; an unreadable one, another version, a bad id or hash approves nothing and sets `problem`, which each discovery pass reports (`.approvals` diagnostic); the next approval replaces the file. `Extensions.approve(_:)` writes it and awaits a discovery pass with that extension's folder touched (so a folder just installed is sealed), `revoke(_:)` likewise; the pass publishes, `onChange` re-registers (App runtime), and `registryChanged` stops the frames of commands gone and rebinds those whose revision changed. **Changed folders:** a folder whose revision isn't the approved one is `changed`; the approved revision stays active while the store keeps it (pruning keeps the active one), so editing an approved extension never breaks it, and approving it runs the new one. **Rollback** is approving a revision the store still keeps (the previous one is kept). **Install** (`Extensions.install(checked, from:)`, a build's Enable): refuses if a folder of that name exists whose manifest isn't that id; copies the work folder to a hidden `.install-<uuid>` in the extensions folder, seals that copy into the main store and refuses unless its revision is the checked one; moves an existing same-id folder to the Trash (`trash`, a seam for tests); renames the copy into place. `BuildJob.enable(in:)` installs, approves and ends `enabled(sealed, folder:)`.

`ExtensionsRunner` runs the consent screens. Extensions lists `discovered` once per run (accessory Enabled, Changed, Not Enabled or Invalid): an unapproved or changed row's Return is Review and Enable, an enabled row's shows it (Disable, Reveal in Finder), an invalid row's pushes its reason. Review (`args: {"id"}`) shows an enabled extension as enabled; otherwise it shows "Checking…", runs `Checker.check` on the folder's current sealed revision and shows the report, and only a passing check gets an Enable action carrying a fresh token (`args: {"review"}`) that maps, in memory, to that `CheckedRevision`. Make a Command's review carries its job's `reviewToken` instead. Enable takes the token once: a job's installs and approves (`BuildJob.enable`), a review's approves its revision if the store still keeps it; either answers `reload`, so the frame it was opened from runs again and shows the extension enabled (`BuildJobs.start` hands back a built job for its own sentence or an empty one, so the build frame reattaches rather than building again). An unknown token is refused, so a settings binding (no args), a deeplink or another process can't approve. Disable (`args: {"id"}`) revokes and closes with a message. The list beneath a review isn't refreshed by Enable (a stream left open would keep its pill spinning); reopening Extensions shows the new state.

**App runtime.** `AppDelegate` only starts `AppRuntime` (WicketApp), which composes the app (`AppRuntime.live()`: the sources, the registry, the palette model and window, the settings window) and applies settings.json. Every reload goes through `apply(Settings)`, one snapshot in an order that keeps what depends on it coherent:

1. the values read on use: the palette's width (next summon), the AI provider (next answer);
2. the registry: the built-ins of features that are off (`setDisabledFeatures`) and the aliases (`setAliases`);
3. if the registry changed (`CommandRegistry.changes`), the runs of commands no longer in it stop (`PaletteSession.stopCommands(where:)`: an opening is cancelled, the lowest frame running one is popped with everything above it);
4. the root's sources (`setSources`, which searches again), else, if the registry changed, one fresh root search, so a new alias or a feature turned off shows on screen at once;
5. the work behind each feature (`AppRuntime.Work`, start and stop, in `Feature.allCases` order; nothing runs before the first snapshot, so it only starts);
6. the hotkeys (`HotKeys.apply`): command hotkeys no longer wanted are released first, then the palette's changes, then the remaining command hotkeys register, so one change can move a combination between them; then what the panes read: `SettingsStore.commands`, and in the diagnostics the bindings not in effect (`.binding`: per command, and the palette's own under `.bindings`) and keyword conflicts (`.conflict`).

Registering extension commands (after every published discovery, so after an approval, a revoke or a folder change: `registerExtensionCommands`) takes steps 3, 4 and 6 too; the extensions' root source is always among the sources, and only the active catalog's root commands answer. Every field of settings.json fails alone: a bad main hotkey is ignored with its reason and the palette keeps the default, like a bad width or binding; only a file that isn't a JSON object falls back to defaults entirely. While the settings window records a hotkey every hotkey is released (`store.pauseHotKey`); when it ends, settings are reloaded, so the one just written registers at once. The side effects come through seams: `AppRuntime.System` (`registerHotKey`, Carbon in the app; `watch`, FSEvents) and each feature's `Work`, and the window through `PaletteSurface` (`PaletteController`), so `WicketAppTests` applies snapshots against fakes. The Shortcuts pane refuses a hotkey or alias another registered command has (`Settings.hotkeyConflict`, `aliasConflict`); a binding of a command that isn't registered is inert there too, as in `CommandHotkeys`.

## Subsystems

Mechanism moved here from CONCEPT.md's decisions (the reasons stay there).

**Extension runtime (Host).** One `ExtensionSession` actor per extension, shared by the app and the `wicket` tool (`Contents/Helpers/wicket`). A process starts with the first request and is reaped after 60 s idle. Pipes are read with readability handlers (`FileHandle.bytes` held back output and blocked cooperative threads). Secrets are one generic password per extension and name in the login keychain (`wicket secret set`), passed as environment variables; extension data lives in `Application Support/Wicket/ExtensionData/<id>`, outside the watched folder. The session warns when `python3` is the Command Line Tools stub. Fixture `expect` lines match as patterns (fields left out aren't checked). The checker fails on protocol slips the app only records (a stray stdout line). A stopped session refuses new requests; runs that are `safeToRepeat` are resent after a clean exit only when the previous process answered something, so resends always end; the others fail with `HostError.notResent`.

**Diagnostics (Host).** `Diagnostics` (`@MainActor @Observable`) is the one store of what is wrong: each `Diagnostic` has a subject (`.extension(id)`, `.command(CommandID)`, `.settings`, `.bindings`, `.approvals`), a kind (who reports it), a severity, a text and the time it was first reported. Producers replace their own kind's reports (`set` for one subject, `replace` for all), so they never clear each other's, and a report made again keeps its time and causes no observable change. Bounded: the newest 10 per subject and kind, texts at 4 KiB (a stderr tail at 16 KiB, its end from a line start). Producers: `Extensions.load` (`.discovery`: a bad manifest, a folder named wrong, no revision), `Extensions.result` (`.run`: a command's last failure, root and frame alike, with an extension error's `data`, cleared by its next answer; then the session's `report`: `.protocol` issues, `.setup` warnings, `.stderr`, taken only when its version changed), `SettingsStore.reload` (`.settings`: ignored fields as warnings, an unreadable file as the error that `loadError` reads), `AppRuntime.applyHotKeys` (`.binding`, `.conflict`), `BuildJob` (`.check`: a build's failed check under `.extension(id)`, cleared when a later build of that id passes), `Extensions` again (`.approvals` under `.approvals`: an approvals file that couldn't be used). A changed or removed extension's session reports and failures are dropped with its old session. Readers: the Shortcuts pane (`text(for: .command(id), kind: .binding)`), the General pane (`hotKeyFailed`, `loadError`, `warnings`), and the Extensions screen and "Fix with agent" (`report(forExtension:)`: the extension and its commands). One instance per app, made in `AppRuntime.live()` and handed to `SettingsStore` and `Extensions`. What an extension wrote is its own text with two kinds of values replaced before it is stored, and redacted before it is cut to its limit (a cut can split a secret so it no longer matches): the session's secret values (the ones it passed, 4 characters or more) and the texts of the newest 64 runs the session was sent (3 characters or more), longest first. Anything else the extension writes (file contents, API responses, a query older than those 64) is kept as written; Wicket's own texts never quote a query. Nothing in the store is logged. A session keeps its newest 50 issues.

**Messages (Core, presented by the app).** `Messages` is the one channel for transient messages (`Message`: text and kind, `done` or `copied`). Posters: the palette session (a command's `close` message after `onClose`, a `reload`'s message) and `SystemEffects` (a paste that only copied); later voice and onboarding. `AppRuntime` owns it and hands it to the session (through `PaletteModel`) and to the effects; `PaletteController.present` shows a message in the card's footer while the card is up, else in the HUD where the pill is or was.

**Revisions (Core value, Host hashing and storage).** `ExtensionRevision` (`extensionID`, `sha256` in lowercase hex) is computed by `ExtensionRevision(folder:id:)` over a `RevisionTree`: walk the folder without following links, skipping `.git`, `__pycache__`, `.claude` and `.DS_Store` at any depth (tool state and regenerable caches; dependencies such as `node_modules` or vendored packages run, so they count); take regular files and symbolic links (a FIFO, socket or device is an error); sort by relative path as UTF-8 bytes; hash `wicket-revision-1`, then per entry length-prefixed fields (8-byte little-endian length): `f`, path, `x` or `-` (any execute bit), bytes; or `l`, path, the link's target as written. Folders count only through what they hold; other permission bits don't count (so read-only sealing doesn't change it). A link must be relative and its real path (`realpath`, so a chain through another link can't climb out while its spelling stays inside) must be inside the folder and outside the skipped names; else `RevisionError` (an absolute link inside a `.venv` says to vendor packages instead: a virtualenv names absolute paths and can't move). Bounds: 256 MiB and 20,000 files outside the skipped names, dependencies included, checked by `lstat` size during the walk, before anything is read or copied. **Sealing** (`RevisionStore`, root `Application Support/Wicket/Revisions`, `ExtensionPaths.revisions`; tests pass their own): `seal(folder, id:)` walks the folder, loads its manifest (the id must match), hashes it, and if `<root>/<id>/<sha256>` is retained already uses it; otherwise copies the tree into `<root>/<id>/.staging-<uuid>` (`copyfile` with `COPYFILE_CLONE`: an APFS clone, links as links), takes every write bit away (files keep their execute bits, folders become 0555), hashes the copy and reads its manifest again, and renames it to `<sha256>` of the copy, so the revision names exactly the bytes kept even if the folder changed during the copy. `SealedRevision { revision; folder; manifest }` has a file-private initialiser: only the store makes one. A retained copy is trusted, not re-hashed, on reuse. **Garbage:** a revision folder's modification date is when it was last active (`markActive`, each discovery pass); `prune(keeping:)` keeps, per extension, the revisions it is given (the active, the discovered and those of sessions still running or shutting down) and the most recently active other one (the previous, for rollback), deletes the rest (write bits restored first) and any staging folder a crash left. A removed extension keeps its newest revision. `prune` returns the extensions that lost a revision, whose uv cache discovery then prunes (see uv extensions). **Stale runs:** the session is created with its revision, and decoding stamps it (`WireContext.revision`) on every `run` action the extension sends, in items and details. The dispatcher carries it through `CommandRun` into `Invocation.revision`, and `Extensions.result` refuses a run bound to a revision that isn't the active one (checked again against the session after any replacement has finished) with `HostError.extensionChanged` ("the extension changed since this was shown; run it again"), which the frame shows as its failure. Since sessions run the sealed folder, a write to the authoring folder changes nothing that runs until discovery seals it and the catalog activates it.

**uv extensions (Host).** Python with packages runs as `uv run --script <script>` (docs/extensions.md, "Python with uv"). `Manifest.uvScript` (Core) recognises it: `run` is `["uv", "run", "--script", script, …]` with `uv` alone, the script inside the folder; `uvx`, `uv tool …`, a path to uv and any other uv command or option are invalid manifests. `UVStorage` is Wicket's uv state, `cache` and `python` under `ExtensionPaths.uv` (Application Support/Wicket/uv; `SessionConfiguration.uv`, `CheckOptions.uv`, tests pass `UVTest.storage`). `UV.environment(_:storage:mode:)` drops every inherited `UV_` variable and sets `UV_CACHE_DIR`, `UV_PYTHON_INSTALL_DIR`, `UV_MANAGED_PYTHON`, `UV_NO_BUILD`, `UV_NO_CONFIG`, plus `UV_LOCKED` (`run`, `check`) and `UV_OFFLINE` (`check`); the session applies it for a uv extension and refuses to start one whose `<script>.lock` is missing (`uv run` only warns then). Wicket's own steps run the login PATH's `uv` (`UV.program`), never what `run` names, through `UV.execute` (a `ProcessTree`, output tail, timeout and cancellation stop the tree). **Check:** `Checker` seals the profile with the uv storage, so `sandbox.sb` also reads the Python folder and writes the check's `uv-cache`, and `prepare.sb` is the same with the network; `CheckIsolation.prepareUV` requires the lock, clones Wicket's cache into `uv-cache` (`clonefile`, a copy if that fails), runs `uv python find --script` unsandboxed (it reads only `requires-python`; it installs the Python into Wicket's storage) and `uv sync --script --locked --no-build` under `prepare.sb` into the clone; the replay's configuration points uv at the clone, offline. A failure is a check error with uv's last lines and a hint (relock, wheels only). **Build:** after the agent's tree is gone, `BuildJob.lockUV` runs `uv lock --script` in the work folder with Wicket's storage and the network (`UV.lock`, builds off), which leaves a current lock as it is. **Pruning:** after a discovery pass whose `prune` removed revisions, `Extensions` prunes the uv caches of those extensions' configurations (`pruneUV`, `UV.prune`: `uv cache prune` from the cache's parent, since uv refuses a working directory inside it), detached and chained one after another; uv waits for runs using the cache, bounded at 120 s; `shutdown` cancels and awaits it. `uv cache prune` drops every script environment, which the next run rebuilds from the cache (about 0.2 s). **Tests** (`UVTests`) use real uv with one storage kept in the temporary folder, so its Python downloads once; their dependency is a wheel in `Fixtures/uv`, and without uv or, before the first download, the network, they cancel (skip) rather than fail.

**Agent adapters (Host).** `Agent` finds `codex` or `claude` on the login-shell PATH and runs one prompt in a working directory in `answer` or `build` mode, yielding text deltas and activity lines, then one answer (with token usage) or one error. Codex: `app-server` JSON-RPC, an ephemeral thread per run, sandbox `read-only` (answer) or `workspace-write` with network off (build), approval policy `never` (anything still asked is refused), and `-c` overrides that switch off hooks, notify, plugins, apps, browser and computer use, sub-agents, memories, web search and every MCP server listed by `config/read`; answer runs also drop the shell and use a short answer prompt. Claude: `-p` with stream-json and the prompt on stdin, `--safe-mode`, `--strict-mcp-config`, `--no-session-persistence`, `--permission-prompts none`; answer runs `--tools ""`, build runs `--restricted` plus the Bash sandbox without the unsandboxed fallback. Status (`AgentStatus`) is `--version` plus the CLI's login check (20 to 150 ms, no model call); a version outside `AgentProvider.testedVersion`'s major.minor only adds a `warning`. Ending the run kills the whole process tree (each process stopped before its children are listed, since Codex runs commands in their own sessions); the final event comes after the tree has exited (see Process lifetime); a CLI that closed stdout without a final event gets 2 s to exit. Known exposure: both sandboxes can read the whole disk and write to temp folders; Codex still loads `~/.codex/AGENTS.md`; Claude leaves a `.claude/` folder to strip before install.

**Build jobs (Host).** Make a Command's engine, owned by the runtime rather than a frame, because a build takes minutes and must survive Escape:

```swift
@MainActor @Observable final class BuildJob { id; sentence; phase; provider; activities; summary; folder; work; cancel() async; finished() async }
enum Phase { case generating(activity: String), checking, review(CheckedRevision), enabled(SealedRevision, folder: URL), failed(String), cancelled }
@MainActor @Observable final class BuildJobs { current: BuildJob?; start(_ sentence:) throws -> BuildJob; shutdown() async }
```

`BuildJobs` (one per app, made in `AppRuntime.live()` with the diagnostics and the applied `ai.provider`; `AppRuntime.init(buildJobs:)`) runs one job at a time: `start` returns the running job if there is one (so submitting again reattaches), else removes whatever the staging root holds (an ended job's folder, a crash's leftovers; off the main actor) and starts a new one in `ExtensionPaths.staging/<job id>` (tests pass their own root). A job: finds the chosen provider, else the first ready one (`AgentBackend.status`, no caching: builds are rare); runs the agent in `build` mode (network off, writes only in its folder) in `<job>/work` with `BuildPrompt.prompt(for:guide:)`: the sentence, the rules (write `wicket.json`, the program and `session.jsonl` here; macOS's own tools since there is no network, or a uv script whose lock Wicket writes; canned data under `WICKET_CHECK`; don't run `wicket check`; end with a sentence for the user) and the whole of docs/extensions.md, which `Scripts/build-app.sh` copies to `Contents/Resources/extensions.md` (`BuildPrompt.bundledGuide`, failing the job if it is missing). Activities grow `activities` (newest 200) and set `generating(activity:)`; the answer becomes `summary`; an error fails the job. The job goes on only once the run has ended, its tree gone (`AgentRun`); a tree that had to be terminated after the grace fails it (a child was cut off mid-write). Then `checking`: a uv extension is locked (`UV.lock`, see uv extensions), `.claude/` is stripped, a folder without `wicket.json` fails, the folder is sealed into the job's own store (`<job>/revisions`, so discovery's pruning of the main store can't touch it; the revision's hash makes it the same identity wherever install later keeps it) and `Checker.check(sealed)` runs; a passed check is `review(checked)`, a failed one `failed` listing the report's errors, reported to the diagnostics either way. `cancel()` cancels the job's task, which cancels the run and awaits its tree (`cancelAndWait`), then removes the job's folder and ends `cancelled`. Logs carry counts and timings, never the sentence or paths.

`MakeCommandRunner` maps a job to its frame with `Observations` over the job (phase and activities): generating and checking are a detail titled with the sentence, the activities as a list and the current status in italics (actions: Show Files, Stop Making It); review is the extension's name, description, commands (title, keyword, mode), the check report and the agent's summary, with id, version, revision and capabilities as metadata and the actions Enable and Show Files, which ends the stream; enabled shows it enabled with its commands (Disable, Reveal in Finder); failed and cancelled end it with an error the frame shows. Ending the stream only stops observing. An empty sentence reattaches to a running job, or to the latest job if it was built (review or enabled), and otherwise fails saying what to type; the built job's own sentence reattaches too. Enable is the consent screens' (see Consent).

**Panel and card.** `PaletteController` owns the `NSPanel`'s frame (`sizingOptions = []`): the top-left anchor is resolved once per summon, a taller card resizes the window at once and animates the card into the transparent space, a shorter one animates first and shrinks the window in the animation's completion, so the pill never moves. `PaletteMetrics` computes a list's height from fixed row heights (the answer row is 60 pt) up to 384 pt; a detail's height is measured by `DetailView` and only grows while its run streams (`DetailMeasure`, Core). Shrinking waits `shrinkDelay` (300 ms). A 40 pt transparent margin leaves room for the glass rim and shadow; the window draws none of its own.

**Keyboard.** `PaletteChord` (Core) matches chords; `PalettePanel` claims them in `performKeyEquivalent` (before the main menu) and `sendEvent` (before the field editor), routes editing shortcuts (`EditCommand`) to the field and swallows other menu keys. ⌘1 to ⌘9 match the number row by key code. Plain keys stay with the field's `onKeyPress`. `MainMenu` is built once at launch and only shows while the settings window makes Wicket a regular app.

**Settings window.** An `NSWindow` with `NSTabViewController` tabs, one SwiftUI `Form` per pane (General, Features, AI, Shortcuts). It writes through `Settings.update` (change only what changed, keep unknown keys, sorted atomic JSON, never overwrite an invalid file); `FileWatcher`'s reload applies it. The shortcut recorder pauses every Wicket hotkey while recording.

**Built-in sources (app).** `AppsSource` scans `/Applications`, `/System/Applications`, their `Utilities`, `~/Applications`, CoreServices, Finder and the Safari cryptex, one vendor folder deep plus apps inside apps, rescanning on FSEvents. `FilesSource` waits for 2 characters and 80 ms, then runs an MDQuery (`Spotlight`) for every word as a file-name word prefix (`FileSearch`, Core, builds the predicate, scopes and ignore rules), takes up to 500 hits and lets the fuzzy matcher pick the best 20, minus a fixed penalty so an equal app ranks above a file. `CalculatorSource` gives at most one answer-tier row (`calculator:answer`) from `Calculator.evaluate` (Core): Return copies the result, ⌘↩ pastes it into the app below; input that parses but has no real answer (`1 / 0`, `sqrt(-1)`) gets a message row with no actions, and rounding noise is zeroed only where it lies within a few ulps of the inputs (`Math.denoised`), so exact small results stay; `ExchangeRateStore` caches the ECB XML in `~/Library/Caches/Wicket/` and refetches once a day old. Frecency is `UsageStore` (`usage.json` in Application Support, 7-day half-life, capped boost); `PaletteModel` saves it through one `LatestWriter`, which writes snapshots one at a time off the main actor and skips any superseded while waiting, so an older one never lands last.

**Paste.** `SystemEffects` activates the target if needed, polls up to 1 s (10 ms steps) until it is frontmost, waits 50 ms for key focus, checks again, and posts ⌘ plus the key that types V in the current layout (`KeyLookup`, Core: the current layout, then an ASCII-capable one, then ANSI V). Accessibility is requested at most once per session.

## How to add a feature

- **A new kind of root result** (a built-in source): a `ResultSource` in `WicketApp`, its matching and logic in Core with tests, registered in `AppRuntime.live()`. Pick a relevance tier; never ship your own ranking. If the user should be able to turn it off, add a `Feature` case whose raw value is the source's id (and give its background work to the runtime as the feature's `AppRuntime.Work`, in `live()`); the Features pane and settings.json pick it up.
- **A new command**: a built-in is one entry in `AppRuntime.live()`'s table: its `RegisteredCommand` plus its runner (`Builtin(_:effect:)` if it just does something and closes, `Builtin(_:runner:)` with a `CommandRunner` if it shows something; below). Its runner's dependencies are made in `live()`; a built-in the user can turn off also gets a `Feature` case (its title and summary for the Features pane). Extension commands register from their manifests. Either gets search, keywords, aliases and hotkeys (and later deeplinks) through the registry and the invocation policy, with no plumbing of its own; declare its `input` (`none` if it just does something, so a keyword or alias and a space don't open a frame for it; `submitText` for typed text run on Return, with `isFallback` to be offered for any query) and its `retry`.
- **A new screen type** (grid, form, custom UI later): a `Screen` case (with its `items`, `title` and `target`), its decoding, and its view in `FrameContent`. Not a parallel system.
- **A new action**: not a new `Item.Action` case. Something the host does for the user (reveal, approve an extension, roll back, web search) is a built-in, and an item offers it as `.run(command:text:args:)`. The cases are the data primitives (open, copy, paste, reveal, detail, run); presentation in `ActionPresentation`.
- **A new setting**: a field in `Settings` (Core) with a default, applied live; if it grants anything, it is consent and does not belong in settings.
- **A command with its own screen** (Ask AI, an MCP tool): a `CommandRunner` producing `RunResult`s for its `Invocation` (a growing answer yields a new `.show(.detail)` per chunk), registered as a command (a built-in: its entry in the table in `AppRuntime.live()`); its frame, loading state, failures and cancellation come with it.
- **Anything long-running**: owned by a frame or a host actor, cancellable, never on the keystroke path.
