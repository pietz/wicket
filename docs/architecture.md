# Architecture

How Wicket is built and how to add to it. Every builder reads this before touching `Sources/`. [CONCEPT.md](../CONCEPT.md) holds the decisions and their reasons; [ROADMAP.md](../ROADMAP.md) holds status and plans. The [review index](reviews/README.md) separates historical advice from the current contracts in [extensions.md](extensions.md) and [markup.md](markup.md).

## Modules

| Target | Owns | Never |
|---|---|---|
| `WicketCore` | Values and deterministic policy: `Item`, actions and their dispatcher, content (`Screen`, `RunResult`), commands, their ids and the registry, ranking, search, the navigation stack's logic, calculator, wire decoding | Processes, AppKit, SwiftUI |
| `WicketHost` | Everything that talks to another process or to OS services shared with the CLI: `ExtensionProcess` (one run), `Extensions` (discovery, the active catalog and runs), `RevisionStore` (sealed revisions), `Agent`, Keychain, login shell, checker | Windows, views |
| `WicketApp` | AppKit and SwiftUI: the panel, views, the palette hotkey, OS integrations (Spotlight, apps, settings window), composition and settings reconciliation (`AppRuntime`). A library so `WicketAppTests` can `@testable import` it | Policy that could be tested in Core |
| `Wicket` | The executable: only `main.swift`, which starts `WicketApp` | Anything else |
| `WicketCLI` | The `wicket` tool: a thin client over Host | Its own copies of Host logic |

Rule of thumb: if it can be tested without a window, it belongs in Core or Host, with a test.

## Core concepts

**Item: a row.** One result row from any source, with its actions. It is not a command, a screen or an execution context. Items carry a host-stamped **origin** (the `CommandID` whose response produced them; nil for the host's own sources); extension ids are namespaced by origin (`ext:<extension>/<command>:<id>`) so two extensions can't collide.

**Action: data.** What an item can do: `open`, `copy`, `paste`, `reveal` (host only), `detail` and `run` (a `CommandID`: resolved at decode to a command of the item's own extension, so only the host can name a built-in; the host may add `text` to submit, as a fallback row does with the query). Actions never carry closures. One **dispatcher** (`ActionDispatcher`, Core) turns an action plus its context into an **outcome**:

```swift
enum ActionOutcome { case close, push(Detail, Authority), open(CommandRun), refused(String) }
struct CommandRun { var command: RegisteredCommand; var invocation: Invocation; var query: String? }
```

**Authority: who made a screen.** `Authority` (Core, `Authority.swift`) is `.host`, `.extension(revision)` or `.agent`. Decoding stamps it (`WireContext.authority`: an extension's response `.extension` with the revision that ran, which its `run` actions are bound to; an agent's reply `.agent`) on the screen's `ScreenContext`, which the frame keeps; a page a `detail` action pushes gets the authority of the action that pushed it (`ActionOutcome.push(_, authority)`, `PaletteSession.push(_:from:)`), so a page an agent's row opens stays the agent's. `ActionTarget` carries it to the dispatcher. `ActionPolicy` is the one table: which results (`RunResult.Kind`) and actions (`Item.Action.Kind`) each authority may send, used by the decoders (the `oneOf` kinds of a result and of every action, nested ones included, are the sender's, so a `run` three pages deep fails an agent's reply), and what activating an action does, used by `ActionDispatcher.perform(_:as:in:)` for every action, derived ones included: under `.agent` an `open` is followed like a link (below), `paste` and `run` are refused (`.refused(reason)`, which the palette posts as a failure message); a `reveal` (the host's, derived for file subjects, so it runs under every authority while no producer sends it) of something no longer there reveals its folder. `ActionPolicy.resolve` is also what the actions menu asks to name the real target, since a rewrite to Reveal drops the producer's title.

Side effects (open, copy, paste, reveal, and `inspect`, what a file is) are injected as `ActionEffects`; the app's `SystemEffects` implements them with AppKit. A link clicked in a page (an answer, an extension's detail) is an action too: the palette's `OpenURLAction` hands it to `PaletteController.open(link:)`, which performs it as an `.open` under `.agent` whoever drew the page (a page's text is untrusted), so `Item.Action.following` (Core) makes it `.open` or `.reveal`, the palette closes and a missing file says so (`SystemEffects.open`). Web and mail links open; a `file://` URL, an absolute path or a `~` path opens unless it would run something (an extension in `runnableExtensions`, under the link's name or its symlink target, or what `SystemEffects.inspect` finds runnable: an executable regular file or a Finder alias), which is revealed in Finder instead; any other link (other schemes, relative paths) isn't followed and says so. `ActionContext` carries the app that was frontmost at summon, which `paste` targets; what a paste can do there (type ⌘V, or only copy and say why) is `PastePlan` (Core), carried out by `SystemEffects`. The dispatcher is synchronous: every `run` (extension commands and built-ins alike) returns `.open` with the `CommandRun` the invocation policy (below) makes of it, and the palette session runs the command for its frame; a built-in that just does something (Settings, Quit) answers `close`, so its frame only ever shows the loading state. `Item.Action` gains no cases: everything the host does for the user is a built-in reached by `run`. A `run` naming a command that isn't registered is pushed as a failure detail naming the command, which Return copies.

**Command: something you can invoke.** Built-ins (Settings, Quit, Run Agent: see Built-ins below) and extension commands share one identity, `CommandID` (in `WicketCore/Command.swift`), and one shape:

```swift
struct CommandID: Hashable, Codable, Sendable { var owner: Owner; var name: String }  // owner: .builtin or .extension(id)
struct Invocation: Sendable { var command: CommandID; var text: String; var args: [String: JSONValue]? }
```

The **command registry** (`CommandRegistry`, Core) is the one catalog: built-ins plus the extension commands the app registers. It lists the root commands (`CommandsSource` is its projection, through the shared `SearchIndex`; a row's accessory is its keyword in effect, else "Command"; hidden commands are reachable by id only), resolves a `CommandID` (the dispatcher's `run`), resolves keywords (for commands the root offers, `isOffered`: listed ones and fallbacks, and only if they take text) and offers its fallbacks (`FallbackSource`). Keyword collisions: a built-in always keeps its keyword, among extensions the first in registry order (extension id, then manifest order) wins, and losers are listed in `keywordConflicts`. A command that uses AI (`RegisteredCommand.usesAI`, from its table entry: Run Agent and Follow Up) isn't registered while AI is off (`setAIEnabled`). Persistent bindings store a `CommandID` or an `Invocation`, never a row id. A `CommandID`'s canonical spelling (`description`, `CommandID(_:)`) is `builtin:<name>` or `ext:<extension>/<command>`: settings.json keys, logs and the prefix of an extension item's id all use it.

Command manifests may declare `search` (up to 16 nonblank strings, 128 Unicode scalars each). `RegisteredCommand.search` carries them into `SearchIndex` alongside keywords: keys are prepared once, alternate matches score one point below equivalent title matches, and phrases never route a keyword invocation. The checker warns only for listed commands without terms.

**Invocation policy: one way in.** Each command declares how it takes text; the domain owns the type (`Command.swift`) and manifests translate into it (`Manifest.Command.input`):

```swift
enum CommandInput { case none, immediateText, submitText, liveText }
enum CommandTrigger { case invoked, keyword }
CommandRun(_ command: RegisteredCommand, _ trigger: CommandTrigger, text: String, args: [String: JSONValue]?)
```

`CommandRun(_:_:text:args:)` is the policy, and every way in goes through it: a row or fallback row and a `run` action (the dispatcher, `.invoked`), `wicket run` (`.invoked` with its text and `--args`), a keyword and a space (`PaletteSession.setQuery`, `.keyword`); deeplinks and MCP will be `.invoked`. What it decides:

| Input | Who | Invoked | Keyword and a space |
|---|---|---|---|
| `none` | Settings, Quit | runs now; text ignored | not routed |
| `immediateText` | extension `once` | runs now on the text | runs on the rest of the line; its field filters |
| `submitText` | Run Agent | with text: runs now; without: waits for text | waits, the rest of the line in its field; never runs |
| `liveText` | extension `live` | searches the text | searches the rest of the line |

Every run pushes its frame at once; `CommandRun.query` is the text its field starts with. A frame waiting for text (`awaitsText`) runs nothing on keystrokes; its target is `.run(command:text:)` with the field, so Return submits through the dispatcher like any action and the answer opens in a frame of its own (Escape goes back to the question).

**Content: what a screen shows.** One content model for everyone, not only extensions (`WicketCore/Content.swift`, with public initialisers):

```swift
enum Screen { case answer(Item), list(Listing), detail(Detail) }
struct Listing { var summary: String?; var sections: [Section] }  // Section: title?, items
enum RunResult { case show(Screen, ScreenContext = .host), close(message: String?), reload(message: String?), stay }
struct ScreenContext { var authority: Authority; var actions: [Item.Action]; var secondary: Int }
```

`Screen` is what a frame above the root shows, whether a command's run sent it or a `detail` action pushed it. A list is composed: an optional markup `summary` above one collection of rows, flat (one section without a title, `Listing(_:)`, also an array literal) or in titled sections. A page's view lays out its content and is measured to size the card; `Screen.title` is a page's, for the pill; Copy and Paste take a page's text from its markup (`Markup.plainText`). The `ScreenContext` beside it says who made it and holds the host's **screen actions** (Follow Up, Copy Answer, Paste Answer, Load Images, Retry, Review and Enable: never on rows, never on the wire); `ScreenFrame` keeps it and builds the frame's `ActionTarget`: the selected row's or the page's actions under the screen's authority, plus `screen`, the screen actions, which run as the host. Return runs `ActionTarget.primary`: the row's first action, else (a page with nothing selected and no actions of its own, as an agent's answer is) the screen's first. ⌘↩ runs `ActionTarget.secondary`: the screen action `ScreenContext.secondary` names when the screen came with any (an answer's Follow Up, after Copy Answer), else the second action; it is fixed when the target is made, so an action the palette adds to `screen` later (Load Images) never takes ⌘↩ from the row. An agent's answer is a `.detail` with no actions of its own and `.agent` authority: all of Wicket's actions on it are screen actions, so they run as the host and the page's rows keep the agent's policy. A pushed page keeps the screen actions of the frame beneath. `Listing.headerTitles(for:)` maps the rows on screen (`ScreenFrame.list`, filtered) back to the sections: a title above each section's first shown row, none at all once a search ranks rows across sections. The wire format is the encoding (`Extension/Decoding.swift`); it has no `show`: `answer`, `list` and `detail` are decoded into it, `close` and `reload` as they are. A new screen (a grid, a form) is a `Screen` case with those properties, its decoding, and its view in `FrameContent`, the one switch from a screen to a view; the frame, sizing, pill, target, failures and reload follow. New interaction it brings (a form's fields and submit, a grid's sideways selection) is its own work on top.

**Subjects.** An item may name what it is, `Item.subject` (`Subject.swift`): `.file(URL)` (an absolute or `~/` path or a `file:` URL, standardized but named as sent) or `.url(URL)` (a scheme other than `file:`). Decoding derives what the producer left out: title (the file's name, the link's host), subtitle (the folder from `~`, or "Not found" when the file isn't there at decode; the link's path), icon (the Finder icon; a globe, an envelope for `mailto:`), id (`file:` plus the canonical path, symlinks resolved, of a missing file its nearest existing folder's, so `/private/tmp/x` and `/tmp/x` are one row; `url:` plus the link) and actions (`Item.Action.merged`: the producer's, then the derived Open, Reveal in Finder and Copy Path, or Open and Copy Link, that don't repeat one by kind and target). The app derives the rest when drawing: a file row without an accessory shows its modified date (`FileDate`, read off the main actor as the row appears). Quick Look isn't built (see Composed lists and pages). Duplicate ids fail an extension's list; in an agent's reply the later ones get an ordinal suffix (`#2`) and a logged count, since the model can't be told.

**Command runs: a stream of content.** Whatever a command shows comes from one interface:

```swift
protocol CommandRunner { func run(_ invocation: Invocation) -> AsyncThrowingStream<RunResult, any Error> }
```

Each element replaces the content of the command's frame (the rule `ResultSource.updates` has for root sources); `close` closes the palette with its message; `reload` drops the frame (or, if it was never shown, doesn't show it) and runs the frame it was opened from again, with its message; `stay` only drops the frame, leaving the one beneath running (an action that answers the screen it was picked on, such as an agent's approval); an error replaces the content with a failure detail; ending the iteration (pop, dismiss, a superseding query) must stop the frame's own work. `Extensions` (Host) is the first producer: one element per run. An AI answer is a built-in producer behind the same protocol, yielding a growing detail (`.show(.detail)`) again and again; the frame keeps its id and generation across elements, so its view updates in place (scroll position kept: the card content is identified by the frame's id), and the pill spins until the stream ends. Run Agent (`AgentRunner`, Host) is the second. The session gets one runner, `CommandRouter` (Core): built-ins go to their runner in the app's table, extension commands to `Extensions`; a command nothing runs fails its frame. A run cancelled before its task starts (Escape, another command opened) never calls its runner.

**Built-ins: one table.** Wicket's own commands are data: a `Builtin` (Core) is a `RegisteredCommand` (id, title, icon, input, keyword, fallback, whether it uses AI) plus its `CommandRunner`, and `AppRuntime.live()` holds the one table of them (tests compose their own). `AppRuntime.init(builtins:)` gives the registry their commands (in table order) and the router their runners. `Builtin(_:effect:)` is a built-in that just does something: its runner (`EffectRunner`) runs the effect and yields `close` (Settings shows the settings window, Quit terminates). Run Agent's runner is the app's one `AgentRunner` (Host), which reads the applied `ai.provider` on each question; its hidden `builtin:ai-settings` opens Settings on the AI pane. Building commands has no built-in of its own: Run Agent does it (see Wicket extending itself). Extensions (`builtin:extensions`, keyword `extensions`) and the hidden `builtin:review-extension`, `builtin:enable-extension`, `builtin:disable-extension` and `builtin:trash-extension` are five entries sharing one `ExtensionsRunner` (Host; see Consent); the hidden `builtin:set-secret` is `SecretsRunner`. Nothing names a built-in outside its entry except app code that invokes one by id (⌘, runs `CommandID.settings`).

**Palette session and frames.** `PaletteSession` (Core, `@Observable`) owns a stack of **frames** (`Frame`): each keeps its id, query, content (`.search(RootResults)` for the root, `.screen(ScreenFrame)` for everything above it: the latest `Screen` and the `CommandRun` feeding it, nil for a page a `detail` action pushed, which never runs, so a `reload` landing on it does nothing), selection (in its `ItemList`), load state and generation. Escape goes up one layer: while voice listens it only stops listening; in the actions menu (an `NSMenu` tracking the keys) it closes only the menu; else `back()` pops the top frame whatever its text (stopping its run), else clears the root's text, and returns false at an empty root, where `PaletteController.escape()` hides the palette. The hotkey closes from any depth. Return, ⌘↩, ⌘K and ⌘1 to ⌘9 act on the top frame's `ActionTarget` (the selected item's actions, or the detail's, with the screen's actions; a clicked or numbered row's is `Frame.target(for:)`, so it keeps the screen's authority). Every restart of a frame's work (a root or live query, a reload) starts a new generation; work results are applied only if frame identity and generation still match, and work is cancelled on pop, dismiss (`reset()`) and superseding queries.

How commands open: typing a registered keyword and a space in the root (`setQuery`) resolves the command with `.keyword` and leaves the keyword in the root's field; `open(CommandRun)` takes the policy's run, from the keyword or an action's outcome. Every run pushes its frame at once, with `CommandRun.query` in its field. Until its first result the frame is starting (`Frame.isStarting`: the pill spins and shows the command's title, the card keeps its height, other actions wait, Escape pops it and stops the run); a command that only has an effect shows nothing more than that, since its `close` or `reload` drops the frame. A live frame runs again on every query change after `liveDebounce` (50 ms; a burst sends only the last text, and the superseded run is cancelled, which stops its process before the next starts). A once frame filters a list locally by title with the shared fuzzy matcher (`SearchIndex`), never running again for it. The selection stays on top until the user moves it, then follows its item when content is replaced and goes to the top when the text a list answers changes.

Compactness follows the frame (`Frame.isCompact`): the root with an empty query is the bare pill, and so is a live command with an empty query and an empty list, and a command waiting for its text (its placeholder is the prompt); any other pushed frame is content (an empty list shows "No Results"). The root with a query and nothing found shows "No Results" too, but only once its slow sources finished (`Frame.isLoading`); until then, as while a pushed command frame has no content yet, the card keeps its height, so typing never flashes it. A page takes no text: its pill holds the title as a focusable label with the field's keys (Return, Escape, the arrows), not an editable field. The card is whole rows only: eight, or an answer and seven. With nothing to run in a pushed frame, the footer shows "Back esc" (`PaletteModel.canGoBack`). `PaletteSession.onClose` asks the app to close; a `close` or `reload` message is posted to the session's `messages` after it (see Messages). `PaletteModel` (app) adds only view state (focus, the card height, the footer message) and usage; `PaletteController` turns intents into session calls.

**Root search.** `ResultSource` (Core: `instant` plus optional `updates`) is the interface for the root frame only, and stays fast and synchronous on the keystroke path. `RootResults` (Core) aggregates: each source's latest items, generation checks (a late update for an older query is dropped), ranking. `Ranker` orders by tier (exact, answer, match, fallback), then two policies within a tier: the host's fallback rows in the order `FallbackSource` gives (registry order; no frecency, no title sort), host-scored candidates (apps, files, built-ins: score plus frecency). After sorting, if `RequestText.readsLikeRequest(query)` (Core, pure) and no item is strong (`Ranker.isStrong`: exact or answer tier, or a host match with at least `strongScorePerScalar` (5) points per query scalar; a run through the query's words earns about 7, scattered letters about 2 to 3), the first fallback moves to the top. `RequestText` accepts text with a letter ending in a question mark, two or more words beginning with an English/German question or instruction word, or at least four plain words (paths, URLs, numbers and expressions do not count as plain words). `RootResults` reranks on every update, so a strong late result (a file from Spotlight) takes the top back, and the untouched selection follows it. Selection lives in `ItemList` (Core), shared by every list: it stays on the top row until the user moves it, then follows the item id; if the selected item disappears the selection stays on its row (clamped), and truncation never drops the selected item.

**Extension lifecycle.** Host owns discovery, the active catalog and runs (`Extensions`: a replaced revision's runs are stopped; the app only feeds it folder changes), each extension's **sealed revision** (see Revisions), the **approved revision** (see Consent) and diagnostics. Discovery does not imply permission to run:

```swift
struct DiscoveredExtension { id; folder; state; sealed; approved }
enum State { case approved(SealedRevision), changed(approved: SealedRevision?, current: SealedRevision),
             unapproved(SealedRevision), invalid(String, approved: SealedRevision?) }
Extensions(directory:, store:, approvals:, diagnostics:, configuration:)
```

`discovered` is every folder in the extensions directory with its state against the approvals as the pass read them: `sealed` is the folder's current revision, `approved` the approved revision if the store still keeps it (`RevisionStore.retained`). The **active catalog** is every discovered extension's `approved` revision, and only it feeds `commands` (each `RegisteredCommand` carrying its `revision`) and runs. `result(of:)` refuses an extension outside the catalog with `HostError.notApproved` (a discovered one) or `.unknownCommand`, before any process starts. A run uses its sealed folder (`sealed.folder`), never the authoring folder; its data folder stays per extension id. `load(changed:)` asks for a discovery pass and returns a task that ends once a published snapshot covers the request: the pass (`scan`, `@concurrent`, off the main actor) lists the folders, seals new ones and those the watcher reported (others keep their entry), and decides the catalog; then `publish` makes it current in one main-actor step (discovery, catalog, runs of revisions that left the catalog stopped, their failures dropped, `.discovery` diagnostics replaced), prunes the store and calls `onChange`, where the app re-registers commands. A `load` during a pass is folded into one more pass, so an FSEvents burst costs at most two. The keystroke path never waits for a pass. **Frames bind to their revision:** `CommandRun` binds `Invocation.revision` to a `run` action's revision or else the command's registered one, so every run, a row, keyword or root query included, is bound to the revision active when it starts. When the registry changes, `AppRuntime.registryChanged` first stops runs of commands that are gone (`stopCommands`), then `PaletteSession.rebind(to: registry.command)`: a run bound to a revision its command no longer has stops with "The extension changed since this was opened…" in its frame, with Run Again (Return: the same command, text and args, bound to the current revision), and the frames above it (opened from its old content) go. That frame becomes a page with no run behind it, so a later rebind leaves the frames Run Again opens alone. Nothing reruns by itself. Every termination path escalates to SIGKILL.

**Process lifetime.** Both transports (extension runs and agent runs) start their child through `ProcessTree` (Host), which owns its stdin writer and its lifetime; the transports keep their own protocols. A member of the tree is the child; anything in its process group (`Process` gives the child its own, and a background job stays in it after the child exits); anything holding the write end of its stdout or stderr (found by scanning the user's processes' fd tables, only while a write end is still held, which the read end's peer handle tells cheaply); any process seen as a member in an earlier scan; and every descendant of those (`proc_listchildpids`, which follows children into their own sessions while their parent lives, as Codex runs commands). macOS has no subreaper and no longer shows other processes' environments, so this is what can be attributed without privileges; a process that leaves the group, closes the pipes and outlives every member it was seen through has daemonised on purpose and escapes. `stop(after:grace:)` runs once however often it's called: close stdin, wait (the child's exit is an event, descendants are polled with backoff), SIGTERM every member, grace, then SIGKILL: each member is SIGSTOPped before the next listing so none can fork in between, then all are killed. Its task finishes only when no member is alive (bounded by `killBound` if one survives SIGKILL), which also means the pipes are closed, and returns `Shutdown` for the whole tree. An extension run that exits by itself is stopped the same way (its leftovers get the grace), and the run returns only after that, so the extension's next run waits for the old tree, not just the process. An agent run (`AgentRun`, the handle `Agent.run` returns: its events, `cancel()`, `cancelAndWait()` and `ended`) completes only once its tree is gone: the final answer or error is held until then, a tree still running `exitGrace` after it is terminated first (`ended` says `.terminated` or `.killed`), and a cancelled run ends without a final event (SIGTERM at once). **Quitting:** `AppDelegate.applicationShouldTerminate` answers `.terminateLater` and replies after `AppRuntime.shutdown()`, which runs once and is bounded (2 s): it stops the palette's command frames and calls `CommandRunner.shutdown()` on the router, which shuts every runner down at once: `AgentRunner` cancels its runs and waits for their trees (each run's task ends only after `cancelAndWait`), and `Extensions` stops every run and waits for their trees. All refuse new runs afterwards. **Login-shell PATH:** `LoginShell.path()` (once per process, for extension runs, the checker and agents) runs `$SHELL -ilc` in a session of its own (`posix_spawn` with `POSIX_SPAWN_SETSID`, since `Process` can't), so it has no controlling terminal: started from a process that has one (the CLI, tests in a terminal), an interactive shell in a background process group is stopped by SIGTTIN trying to take the terminal, which cost every such process the 5 s deadline and the fallback PATH. A shell that doesn't answer in 5 s is killed with its process group.

**Agent runs.** `Agent` (Host) yields `AgentEvent`s; `AgentProvider` (the names) is in Core so settings can choose one. `AgentBackend` (Host) is what answers need from providers (status and a run; `installed`, or tests' stand-ins), and `AgentBackend.ready(_:)` is the one provider choice: the chosen provider or nothing, else the first ready of Claude (Claude Code) and ChatGPT (Codex), its status checked before every run and never cached; `AgentUnavailable` says why none can answer. `AgentRunner` (Host; `AnswerDraft` is the presentation) maps one run into its frame's content: a detail titled with the question that shows the status, then each whole message the agent writes (`AgentEvent.message`: Claude Code's main-agent `assistant` text, Codex's `item/completed` for an `agentMessage`), then the answer. The messages stay when they end with the final answer, else the answer replaces them. Tool use, thinking and token usage aren't shown. Actions Copy Answer and Paste Answer (the final answer alone) once there is text. Run Agent runs in the folder of the Finder selection (`AgentRunner.folder(for:)`: the selected folder itself when it is the only item) or else the home folder, with the provider's `AgentOptions` (see Agent settings). **Follow Up**: the adapter yields `AgentEvent.session` (Claude Code's session id from its `result`, Codex's thread id from `thread/start` or `thread/resume`) before its answer; on a finished answer with one, `AgentRunner` records an `AgentRunner.Conversation` (provider, folder, options, session) under a token (the latest 20, in memory) and inserts Follow Up second among the actions (⌘↩): a `.run` of the hidden submit-text `builtin:follow-up` with `conversation: <token>` and no text, so it opens a frame waiting for text whose pill says "Follow up" (Escape pops back to the answer; with voice set to listen on open, `PaletteController.perform` listens for any frame an action opens waiting for its text, and `PaletteSession.setSpokenQuery` writes into such a frame). Submitted, `AgentRunner` continues that conversation: it runs with the conversation's provider, folder and options and `AgentRequest.resume`, without the summon context; the answer frame is titled with the follow-up question and offers Follow Up again under the same token. An unknown token fails ("This conversation has ended"). **Approvals**: what the agent's own permission policy asks about (`AgentEvent.approvals`) shows first, oldest on top: what it asks to run (where, as `~/…`; its reason; then the command in a code block), which host it asks to reach (host and protocol), what it asks to change (the change kinds and paths, relative to the run's folder when inside it, else absolute, and a `grantRoot` folder it asks to write under for the rest of the run) or which other tool it asks to use (its input in brief), with how many more wait, and its actions Allow and Deny, each a `.run` of the hidden `builtin:ai-approval` with a token and the decision. Allow grants that one call only. That command looks the token up in `AgentRunner` (tokens live until answered or until their run ends), sends `AgentRun.reply`, drops the approval from the draft at once (it stays out until the agent's next list no longer has it) and answers `stay`, so the answer's frame keeps running; an expired token (answered already, a fast second Return, an ended run) changes nothing and answers `stay` too. Leaving the frame (Escape, or the palette closing) ends the run and its process tree like any answer; there is no timeout on a question. A provider that isn't ready shows a failure saying what to do, its action Open AI Settings (the hidden `builtin:ai-settings`, which opens Settings on the AI pane). A run that fails keeps the text it sent with a note that the answer is incomplete; its actions are Retry (`.run` of Run Agent with the same question, so a retry only ever runs when picked) and, when there is text, Copy Answer. While a frame is loading, a detail without actions of its own has no target (`Frame.target`), so Return can't copy a status or half a page. Agent events stay separate from extension RPC.

**Wicket extending itself (Host).** There is no command for building commands: the user asks Run Agent ("build a command that shows the weather", "change my invoices command", "what can you do?"). `ExtensionAuthoring` (made in `AppRuntime.live()` with the `Extensions` and the registry's commands, set on `AgentRunner.authoring`) does two things for every run. Before the run, `instructions()` becomes `AgentRequest.instructions`, which each adapter adds to the agent's own prompt (Codex as the thread's developer instructions, Claude Code as `--append-system-prompt`). It is built again for every run from three parts: Wicket's rules (`bundledRules`: `Contents/Resources/agent.md`, copied from Resources/agent.md, so they update with the app), whose last section, "Your reply", is completed by `Markup.agentReference()`, the markup catalog as the agent learns it (about 3.7 KB, inline rather than a file to read, see CONCEPT.md); then, under "The user's own instructions", the user's `agent.md` (`instructionsFile`: `Settings.directory()`, so `~/.config/wicket`, Wicket Dev's folder or `WICKET_CONFIG_DIR`) with HTML comments stripped, left out when empty; then a generated "This Wicket" section of absolute paths: the extensions folder; the authoring kit's guide, schema and samples (`bundledKit`: `Contents/Resources/Authoring`, which `Scripts/build-app.sh` fills with docs/extensions.md, docs/extension.schema.json, docs/examples/{week-number,unicode} and Extensions/{slugify,github-prs,gallery} at their repository paths, so the guide's relative links work; the samples are whatever folders are there); the bundled `wicket` tool, with how to `check` a folder and read an extension's runs (`log <id>`); and the command list, which `instructions()` writes to `ExtensionPaths.commandList` (Application Support/Wicket/commands.md): every registered command by id, with title, subtitle, keyword, how it takes input, whether search lists it and an extension's folder, fields clipped to 80 characters and at most 300 commands, read by the agent only when it needs it. Settings ▸ AI's Edit Agent Instructions opens `editableInstructions()`, which first creates the file, if missing, holding a one-line comment. A `Snapshot` of every discovered folder's revision (or invalid reason) is taken too. Once the run's answer arrives (its process tree is gone, so the files are complete), `changed(since:)` runs `Extensions.reload()` (a discovery pass that reseals every folder, since the file watcher may not have reported yet) and returns the folders that differ from the snapshot and don't run as they are (new, changed or invalid). Each becomes a "Review and Enable <name>" action (`builtin:review-extension` with its id), first among the finished answer's actions, before Copy and Paste. Review, check and Enable are the consent screens' (see Consent), unchanged; Enable registers the command at once. A run that fails or stops with an error is compared the same way once its tree is gone, and its reviews come first on the failure page, before Retry. So is a run the user stops by leaving its frame (Escape, the palette closing): there is no page left to offer them on, but the changed folders are discovered (so the Extensions command lists them with Review and Enable) and the build conversation below is recorded. **The build conversation.** When a run's answer (or failure, or stop) offers reviews and the agent named its session, `AgentRunner` records the run's `Conversation` (provider, folder, options, session; `Codable`) for each extension it added or changed (`ExtensionHistory.remember`, the latest per extension, see Extension history), so a follow-up that changes it again replaces it. **Fix with Agent** (`ExtensionAuthoring.fix`: a failed check's review page, an invalid folder's page, an enabled extension's page with a fixable failure among its newest 10 runs, and the failure page of an extension command) is `.run(command: .runAgent, text: "Find out why it fails and fix it.\n\n<failure>", args: ["title": "Fix NAME", "extension": id])`; the failure is the check report, the folder's reason, or the latest three failed runs from the history (`Extensions.fixAction`, else the error's text). **Change with Agent** (`ExtensionAuthoring.change`, on an enabled extension's page) is the same run without text, so Run Agent's frame waits for the request, typed or spoken, and keeps the `extension` arg for it. For an `extension` arg, `AgentRunner` prefixes the prompt with `ExtensionAuthoring.about(id)` (the extension's name, id, folder and `wicket log` command) and resumes the remembered conversation through Follow Up's resume path (`AgentRequest.resume`, its provider, folder and model options); the agent's permission policy is the one configured now (see Agent adapters). It starts a new conversation when none is remembered. If a resumed run fails (an unknown session, its provider not ready), its failure page offers Start New Conversation after Retry: the same invocation with `fresh: true`, which skips the remembered conversation. Nothing retries on its own. Either way it is an ordinary run, so its answer offers Review and Enable for what it changed; Run Agent titles its frame with a `title` arg when given, else the question.

**Markup (Core).** Agent replies, an extension's `detail.markdown` and `list.summary` are markup: Markdown with native component tags (docs/markup.md). `Markup.Parser` turns text into a `Document` of blocks (`.markdown`, `.text` for anything shown as written, `.component(any Component)`) in two passes. `MarkupScanner` walks the bytes line by line into a tree of elements and text ranges: tags only at block position, fenced code (and indented code at the top level) opaque, attributes in any quoting with entities decoded, an unclosed tag closed by its parent, a stray close dropped, and a tag inside prose (unknown, or not at block position) noted, since it shows as text. `MarkupBuilder` holds that tree to the catalog: validation, aliases, placement, limits (`Markup.Limits` for the document, `Tag.limit` per tag), layout depth, wrappers and the joining of repeated tags into groups; it names no tag. Each component is one file in `Markup/Components/` conforming to `Component`: its `tags` (attributes, body, role, focus, "use when"), an `example` with its Copy Answer text, `make(_ build: Markup.Build)` reading its validated attributes and content, `text(home:)`, `targets` and, for groups, `joining`/`titled`. `Markup.components` is the registry: the agent's instructions (`agentReference()`), the reference in docs/markup.md (`reference()`, kept equal by a test; `WICKET_UPDATE_GOLDEN=1` rewrites it), the lint and the tests read it, so adding a component touches only its file (and its view, in the app). Rows decode into `Item`s through the same `Item(subject:…)` initializer as the wire, so `ActionPolicy` applies unchanged; ids are unique per document (`#2` for a repeat) and namespaced by origin. The agent path never fails and logs only issue counts by kind (`Markup.document`); `Markup.lint` returns every issue, and `RunResult.markupProblems` is what `wicket run` reports for an extension's response. How real agents follow it is measured by `replyMarkupEvaluation` (Tests/WicketHostTests/MarkupEvalTests.swift, opt in with `WICKET_EVAL_MARKUP=claude,codex` and `WICKET_EVAL_OUT=<file>`): 14 prompts through Run Agent with the real rules, each reply parsed as the palette does and linted as `wicket run` does; results in docs/reviews/2026-11-08-markup-eval.md. A `Parser` kept for a growing reply (updated per whole message) caches its prose runs, path parsing and file facts, so a 64 KiB re-parse costs about 1.7 ms in release.

**Fallbacks and Run Agent.** `FallbackSource` (Core) offers one row in the fallback tier for any non-empty query per registered fallback (`isFallback`, a `submitText` command), its action `.run(command:text:)` with the query, its id `fallback:<command id>`. Run Agent is such a built-in (its entry in the table), unlisted, with the keyword `ai` (a built-in keeps it against extensions); its `ai ` opens its frame waiting for the question. Nothing names Run Agent outside its entry and its runner. It is the only built-in fallback, and extensions add no root rows, so it is the only fallback row. `LinkSource` (Core, id `links`) gives one answer-tier row, "Open apple.com", when the query plainly is a web address (`LinkSource.link`: an http(s) URL with a host, or a bare host whose last label is in a short list of top-level domains that aren't common file extensions, so `1.5`, `file.txt` and `README.md` never match).

**The check is static.** `Checker.check(_:)` (Host) reviews a `SealedRevision` before it may be enabled without running any of its code: sealing already validated the folder and the manifest, so it adds what the manifest can't say about itself (listed commands without search terms warn; the program `run` names must resolve, and the Command Line Tools `python3` stub warns). `wicket check <folder>` is `Checker.check(folder:)`: it seals the folder into a temporary store (`RevisionStore.temporary()`), checks that, and deletes the store; a folder that can't be sealed fails with why, and one not named after its id only warns. Responses are validated where code runs anyway: strictly by `wicket run`, which also fails on an error response and on any markup problem (`RunResult.markupProblems`), and by the app's decoder, which draws imperfect markup.

**Settings versus consent.** `settings.json` holds preferences only, under the [consent principle](../CONCEPT.md#principles). Consent and approval live in host-owned stores in Application Support, written only by Wicket's own UI: which extension revisions may run is `Approvals` (below); whether and when Wicket listens is `VoiceConsent` (see Voice input). What an agent may do unasked is the agent's own configuration, not Wicket's (see Agent adapters).

**Agent settings.** Two providers, `AgentProvider` (Core): `claude` shown as "Claude" and `codex` as "ChatGPT" (`name`; `cli` names Claude Code and Codex in setup hints), Claude first in `allCases`. Preferences in settings.json, `"ai": {"provider": "claude", "claude": {"model": "opus", "effort": "high", "speed": "fast"}, "codex": {…}}`: `ai.provider` nil means none chosen (the first ready one answers), and `Settings.AI[provider]` is an `AgentOptions` (Core: `model` and `effort` one word each, `speed`), starting from `AgentProvider.defaultOptions` (Claude `sonnet`, ChatGPT `gpt-6.1-terra`, effort `medium`, speed `regular`); only fields that differ from those are written, and each field fails alone. `AppRuntime.live()` sets `AgentRunner.options` to read them when a question is asked, and the run's `AgentRequest` carries them. Each adapter maps them in one function (see Agent adapters: `CodexTranscript.turnSettings`, `ClaudeTranscript.settings`). Settings ▸ AI starts with Use AI (`ai.enabled`, see The AI switch); while it is on, it shows one provider picker and, below it, the shown provider's Model, Reasoning effort and Speed, with a footer that says where that agent's permission policy is set (`AIPane.permissions`). The picker shows the chosen provider, else the first ready one (`AIPane.current`); a provider that isn't installed or signed in is listed with why and can't be picked, and with none ready (`AIPane.noneReady`) one line says how to set one up, with Check Again. Models come from `Agent.models()` (`AgentModels.swift`: Codex's app-server `initialize` and `model/list`, Claude Code's `-p --input-format stream-json --safe-mode` with one `initialize` control request, its "default" entry left out; neither calls a model or needs a login; 10 s bound), giving each model's efforts and whether it has a fast speed; the effort list follows the chosen model, choosing a model moves an effort it lacks to medium (or its first) and drops a fast speed it lacks, and a value the file names that the CLI doesn't list still shows as written.

**Consent (Host).** `Approvals` is the store: `approved(id) -> ExtensionRevision?`, `all`, `problem`, and the internal `approve(_:)` and `revoke(_:)`, so nothing outside Host can write it. The file is `Application Support/Wicket/approvals.json` (`ExtensionPaths.approvals`; tests pass their own), `{"version": 1, "approved": {"<id>": "<sha256>"}}` (an older file's `previous` is ignored), read once at launch and written atomically (memory changes only after the write). It fails closed: a missing file approves nothing; an unreadable one, another version, a bad id or hash approves nothing and sets `problem`, which each discovery pass reports (`.approvals` diagnostic); the next approval replaces the file. `Extensions.approve(_:)` writes it and awaits a discovery pass with that extension's folder touched (so a folder just written is sealed), `revoke(_:)` likewise; the pass publishes, `onChange` re-registers (App runtime), and `registryChanged` stops the frames of commands gone and rebinds those whose revision changed. **Changed folders:** a folder whose revision isn't the approved one is `changed`; the approved revision stays active while the store keeps it (pruning keeps the active one), so editing an approved extension never breaks it, and approving it runs the new one.

`ExtensionsRunner` runs the consent screens. Extensions lists, once per run: a damaged approvals file (accessory Problem, Copy Diagnostics), then `discovered` (accessory Enabled, Problem, Changed, Not Enabled or Invalid), then Open Extensions Folder (created if missing), which is all an empty folder shows. An unapproved or changed row's Return is Review and Enable, an enabled row's shows it, an invalid row's shows its page (its reason, Fix with Agent); Disable is always last. An enabled row says Problem when a command's newest run of the active revision failed (`ExtensionHistory.failing`) or the diagnostics hold a warning or error about it (`report(forExtension:)`: a keyword conflict, say), with the failure's or the newest problem's first line as subtitle. Review (`args: {"id"}`) on an enabled extension shows its page: its commands, its declared secrets as Set or Not set, its problems (diagnostics), its recent failures (the history's newest three fixable failures among its last 10 runs, which outlive a restart); actions Run (its first listed command, bound to the revision), Fix with Agent (when it has recent failures), Reveal in Finder, Change with Agent, Set NAME… per secret (one not set goes first of all), Copy Diagnostics (everything the diagnostics hold about it, then its run history, as text), Disable, and Move to Trash, which ends every extension page. Otherwise it runs `Checker.check` on the folder's current sealed revision and shows the report, and only a passing check gets an Enable action carrying a fresh token (`args: {"review"}`) that maps, in memory, to that revision (a failing one gets Fix with Agent instead, see Wicket extending itself); Enable takes the token once: it approves its revision if the store still keeps it and closes with a message ("Enabled Slugify."). An unknown token is refused, so a settings binding (no args), a deeplink or another process can't approve. Disable (`args: {"id"}`) revokes and closes with a message. Move to Trash (`args: {"id"}`, no confirmation: the Trash is the undo) calls `Extensions.trash(_:)`, which refuses an id that isn't a discovered folder directly in the extensions directory, revokes its approval, moves the folder to the Trash (`FileManager.trashItem`), deletes its history (runs and build conversation), and awaits a pass, its runs' end and one more pass, so pruning drops every sealed revision (and the store's now empty `<id>` folder, as `RevisionStore.prune` does for any extension left with none); `ExtensionData/<id>` and its Keychain secrets stay, so a folder put back from the Trash works once enabled again. It answers `reload` with "Moved Slugify to the Trash.": the page beneath reloads, and Review of an id no longer discovered answers `reload` too, so the page goes and the Extensions list beneath reloads. Reopening a review reads the current state, so it never shows a disabled extension as enabled.

**Secrets from the palette.** `builtin:set-secret` (hidden, `submitText`, args `id` and `name`) is `SecretsRunner`: its frame waits for the value in a masked field (`SecureField`), Return stores it (trimmed) with `Keychain.setSecret` (the item `wicket secret set` writes) if the extension, approved or current, declares that secret (each run reads secrets when it starts, so the next run gets the new value) and closes with "Stored NAME". The value is never logged or shown. A frame run that fails with `HostError.missingSecret` shows a page offering the same Set action instead of a failure (`Extensions.run`).

**App runtime.** `AppDelegate` only starts `AppRuntime` (WicketApp), which composes the app (`AppRuntime.live()`: the sources, the registry, the palette model and window, the settings window, the menu bar icon) and applies settings.json. Every reload goes through `apply(Settings)`, one snapshot in an order that keeps what depends on it coherent:

1. the values read on use: the palette's width (next summon), the pages' text size (`PaletteModel.textSize`, which `DocumentView` scales every font, height and gap of the page by: `TextSize.points` maps a size designed for body 13 to the step's body, so proportions stay), whether pages load images from the web (`showOnlineContent`, at once) and the AI provider (next answer);
2. the registry: the built-ins that use AI, unless `ai.enabled` is off (`setAIEnabled`);
3. if the registry changed (`CommandRegistry.changes`), the runs of commands no longer in it stop (`PaletteSession.stopCommands(where:)`: the lowest frame running one is popped with everything above it);
4. if the registry changed, one fresh root search, so AI turned off shows on screen at once;
5. the hotkey (`PaletteHotKey.apply`), and in the diagnostics why it isn't in effect (`.hotkey`);
6. the menu bar icon (`MenuBarSurface.update`): shown or hidden by `showInMenuBar`, with the hotkey in effect (`PaletteHotKey.inEffect`: settings' own, or the previous one while another app holds it) as Open Wicket's key equivalent.

Registering extension commands (after every published discovery, so after an approval, a revoke or a folder change: `registerExtensionCommands`) takes steps 3 and 4 too. Every field of settings.json fails alone: a bad hotkey is ignored with its reason and the palette keeps the default, like a bad width; a valid one another app holds leaves the palette on the combination it had (kept across a recording pause), with `PaletteHotKey.problem` naming both under `.hotkey`, and is tried again on every apply; only a file that isn't a JSON object falls back to defaults entirely. While the settings window records a hotkey it is released (`store.pauseHotKey`); when it ends, settings are reloaded, so the one just written registers at once. The side effects come through seams: `AppRuntime.System` (`registerHotKey`, Carbon in the app; `watch`, FSEvents) and the sources' background work (`work`: the app scan and exchange rates, started once after the first snapshot), and the windows through `PaletteSurface` (`PaletteController`) and `MenuBarSurface` (`MenuBarItem`), so `WicketAppTests` applies snapshots against fakes.

**The AI switch.** `ai.enabled` (Settings ▸ AI, "Use AI"; written only when off) is the one built-in switch: off, the commands with `usesAI` leave the registry (`CommandRegistry.setAIEnabled`), so Run Agent's row and keyword go and a running answer stops. Apps, files, the calculator and links are always on (the scope call is in CONCEPT.md).

## Subsystems

The flows below implement the calls in [CONCEPT.md](../CONCEPT.md).

**Extension runtime (Host).** `ExtensionProcess.run(_:manifest:folder:revision:configuration:)`, shared by the app and the `wicket` tool (`Contents/Helpers/wicket`), is one run: resolve `run[0]` (`resolve`, on the login-shell PATH), set the environment (secrets from `RunConfiguration.secret`, `HostError.missingSecret` before anything starts), start it through `ProcessTree`, write `Request.line` and close stdin, then read stdout to its end (at most `outputLimit`, 1 MiB, else `outputTooLong` and the tree is stopped) and keep the last 64 KiB of stderr (`OutputTail`), each on a detached task so cancelling the caller can't cut the reading short. Once the process exits, what it left gets `exitGrace` before SIGTERM (`stop(after:grace:)`); a timer stops the tree at `timeout` (30 s); cancelling the caller stops it at once and still waits for it. The result is `Response.decode` (strict, with `WireContext`): a `RunResult` or the extension's `ExtensionError`; empty stdout is `HostError.exited`, a line that isn't JSON says to log to stderr. `Run` carries the raw output (for `wicket run`), the result, the stderr tail and the secrets passed (for redaction). `Extensions` serialises each extension's runs: `enqueue` chains each run's task after the previous one's (`tails[id]`), so a superseded live query's tree is gone before the next query starts; `stop(id)` cancels its runs in flight (their callers get `HostError.stopped`), which `publish`, trash and `shutdown()` use. Secrets are one generic password per extension and name in the login keychain (`wicket secret set`, or Set NAME… in the palette), passed as environment variables; extension data lives in `Application Support/Wicket/ExtensionData/<id>`, outside the watched folder.

**Diagnostics (Host).** `Diagnostics` (`@MainActor @Observable`) is the one store of what is wrong: each `Diagnostic` has a subject (`.extension(id)`, `.command(CommandID)`, `.settings`, `.hotkey`, `.approvals`), a kind (who reports it), a severity, a text and the time it was first reported. Producers replace their own kind's reports (`set` for one subject, `replace` for all), so they never clear each other's, and a report made again keeps its time and causes no observable change. Bounded: the newest 10 per subject and kind, texts at 4 KiB. Producers: `Extensions.load` (`.discovery`: a bad manifest, a folder named wrong, no revision), `SettingsStore.reload` (`.settings`: ignored fields as warnings, an unreadable file as the error that `loadError` reads), `AppRuntime` (`.hotkey`; `.conflict`, keyword conflicts, whenever the registry changes), `Extensions` again (`.approvals` under `.approvals`: an approvals file that couldn't be used). A removed or changed extension's keyword conflicts go when `AppRuntime` recomputes them for the new registry. Readers: the General pane (`text(for: .hotkey, kind: .hotkey)`, `loadError`, `warnings`), and the Extensions screen (`report(forExtension:)`: the extension and its commands; warnings and errors make its row say Problem and fill its page's Problems, and Copy Diagnostics copies them all). The store is this run of Wicket's; what outlives it is the extension history (below). One instance per app, made in `AppRuntime.live()` and handed to `SettingsStore` and `Extensions`. Run failures are not reported here: the extension history (below) owns them. Nothing in the store is logged.

**Extension history (Host).** `ExtensionHistory` (an actor; `Extensions.history`, made in `AppRuntime.live()`, nil in tests that don't pass one) keeps what Wicket knows about each extension beyond its code, in `ExtensionPaths.history/<id>/` (Application Support, never the extension's folder, which is sealed; ids are checked with `Manifest.isSlug`, so a CLI argument can't leave the root): `runs.jsonl`, one `Run` per line (time, the revision's first 12 hex digits, command, `Outcome`, milliseconds, and for a failure its message, text, args and stderr tail), and `conversation.json`, the build conversation (see Wicket extending itself). `Extensions.result(of:)` records every run of a discovered extension except a cancelled one, with `Outcome(error)`: `error` an `ExtensionError` (its message and `data`), `rejected` `invalidResponse` (the decoder's path and reason, "unknown field …") or `outputTooLong`, `timeout`, `crashed` `exited` or `launch`, and `refused` anything Wicket refused (`notApproved`, `extensionChanged`, `missingSecret`, `stopped`, a `UserError`); the message and the run's stderr tail have the secret values the run was passed (4 characters or more, longest first) replaced before they are cut (a cut can split a secret so it no longer matches); anything else the extension wrote (file contents, API responses) is kept as written. Text and args are kept only for failures (cut at 500 characters and 1 KiB), since reproducing a failure needs its input and a success's input helps no one. A success after a success of the same command and revision replaces it with `count` one higher, so live keystrokes fold into one entry and never push a failure out. Bounds: 50 entries and 128 KiB per file, oldest dropped; messages and stderr at 2 KiB. The actor caches each file once read (Wicket is its only writer) and rewrites it atomically per run, about 0.7 ms with a full file, off the main actor. `ExtensionHistory.text` is the plain-text form `wicket log <id>` prints and Fix with Agent and Copy Diagnostics carry. `Outcome.isFixable` (anything but `ok` and `refused`) decides where Fix with Agent is offered: `Extensions.run` turns a fixable failure into the failure page a frame would show (`Detail.failure`, so Return copies it) with Fix with Agent as its screen action (⌘↩); refusals still fail the frame as before.

**Messages (Core, presented by the app).** `Messages` is the one channel for transient messages (`Message`: text and kind, `done`, `copied` or `failed`). Posters: the palette session (a command's `close` message after `onClose`, a `reload`'s message) and `SystemEffects` (a copy's "Copied", a paste that only copied or found the clipboard changed, an open that failed: "Couldn't open it" and why: a missing file or disk, caught before asking macOS, no app for it, or macOS's error; a cancelled Gatekeeper prompt says nothing) and `VoiceInput` (why listening failed or couldn't start); later onboarding. `SystemEffects` posts in a task, after the dispatcher's `close` hid the palette in the same turn, so its messages show in the HUD. `AppRuntime` owns it and hands it to the session (through `PaletteModel`) and to the effects; `PaletteController.present` shows a message in the card's footer while the card is up, else in the HUD where the pill is or was; both lead with the kind's symbol (`Message.Kind.symbol`).

**Revisions (Core value, Host hashing and storage).** `ExtensionRevision` (`extensionID`, `sha256` in lowercase hex) is computed by `ExtensionRevision(folder:id:)` over a `RevisionTree`: walk the folder without following links, skipping `.git`, `__pycache__`, `.claude` and `.DS_Store` at any depth (tool state and regenerable caches; dependencies such as `node_modules` or vendored packages run, so they count); take regular files and symbolic links (a FIFO, socket or device is an error); sort by relative path as UTF-8 bytes; hash `wicket-revision-1`, then per entry length-prefixed fields (8-byte little-endian length): `f`, path, `x` or `-` (any execute bit), bytes; or `l`, path, the link's target as written. Folders count only through what they hold; other permission bits don't count (so read-only sealing doesn't change it). A link must be relative and its real path (`realpath`, so a chain through another link can't climb out while its spelling stays inside) must be inside the folder and outside the skipped names; else `RevisionError` (an absolute link inside a `.venv` says to vendor packages instead: a virtualenv names absolute paths and can't move). Bounds: 256 MiB and 20,000 files outside the skipped names, dependencies included, checked by `lstat` size during the walk, before anything is read or copied. **Sealing** (`RevisionStore`, root `Application Support/Wicket/Revisions`, `ExtensionPaths.revisions`; tests pass their own): `seal(folder, id:)` walks the folder, loads its manifest (the id must match), hashes it, and if `<root>/<id>/<sha256>` is retained already uses it; otherwise copies the tree into `<root>/<id>/.staging-<uuid>` (`copyfile` with `COPYFILE_CLONE`: an APFS clone, links as links), takes every write bit away (files keep their execute bits, folders become 0555), hashes the copy and reads its manifest again, and renames it to `<sha256>` of the copy, so the revision names exactly the bytes kept even if the folder changed during the copy. `SealedRevision { revision; folder; manifest }` has a file-private initialiser: only the store makes one. A retained copy is trusted, not re-hashed, on reuse. **Garbage:** `prune(keeping:)` deletes every revision it isn't given (write bits restored first) and any staging folder a crash left; `Extensions.prune` gives it the active, the discovered, those of runs in flight (`inUse`, stopping ones included until their trees are gone) and every approved revision (`Approvals`); it runs at publication, never during a scan (a run of the outgoing catalog may start mid-scan), and again when the last run of a replaced revision ends. A removed extension keeps only its approved revision. **Stale runs:** each run decodes with its revision, stamped (`WireContext.revision`) on every `run` action the extension sends, in items and details. The dispatcher carries it through `CommandRun` into `Invocation.revision`, and `Extensions.result` refuses a run bound to a revision that isn't the active one with `HostError.extensionChanged` ("the extension changed since this was shown; run it again"), which the frame shows as its failure. Since runs use the sealed folder, a write to the authoring folder changes nothing that runs until discovery seals it and the catalog activates it.

**Agent adapters (Host).** `Agent` finds `codex` or `claude` on the login-shell PATH and runs one prompt in a working directory, yielding each whole message, the list of waiting approvals whenever it changes, the session, then one answer or one error. `AgentRun.reply(to:_:)` answers an approval without waiting: replies go through an `AsyncStream` that `AgentProcess` drains on its own task, writing the transcript's `reply` line to stdin, so stdout parsing never waits for the user. **The permission policy is the agent's own.** Wicket passes no permission mode, approval policy or sandbox: whatever the user configured for the agent applies, and Wicket shows what it asks. Verified with throwaway configurations (temporary `HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`): Claude Code 2.1.319 takes `permissions.defaultMode` from its settings (user, project or local; `default` asks, `acceptEdits` allows edits and simple file commands, `auto` approves through its classifier; a project's `bypassPermissions` is ignored and falls back to `default`), on a fresh run and on `--resume` alike, where the mode configured now applies, not the one the session started with. Codex 0.167 takes `approval_policy`, `sandbox_mode` and `approvals_reviewer` from `~/.codex/config.toml` on `thread/start`, but `thread/resume` alone keeps the thread's original policy even after the configuration changed (a thread started with `never` and `danger-full-access` ran a command unasked after both settings were removed). `config/read` can't fix that: an unset key reads as null, which means no override, and the effective default depends on the folder's trust (`read-only` untrusted, `workspace-write` trusted). So a resume first sends `thread/start` with `ephemeral: true` in the working directory, which reports the `approvalPolicy`, `sandbox` and `approvalsReviewer` a new thread gets now and leaves nothing in Codex's history, and sets those on the resumed `turn/start` (`sandboxPolicy` takes the reported object as is); a probe that reports none fails the run rather than resume under the saved policy. Settings ▸ AI's footer tells the user where to set it. **Codex**: `codex app-server`, `initialize`, then `thread/start` with only `cwd` and short `developerInstructions` (Codex's own prompt stays, since it teaches the tools), not ephemeral, so the thread is kept in Codex's history; a follow-up (`AgentRequest.resume`) sends the ephemeral `thread/start` and then `thread/resume`, in a new app-server process, with `threadId`, `cwd`, the instructions again, `excludeTurns: true` (the resumed thread still remembers the earlier turns) and the current policy. Features, hooks and MCP servers come from the user's configuration. The user's choices go on `turn/start` (`CodexTranscript.turnSettings`): `model`, `effort`, `serviceTierForTurn` (`priority` for fast, else `default`, which is standard speed even for a model whose catalog default is the fast tier). Its `item/commandExecution/requestApproval` (a `.network` approval when it carries `networkApprovalContext`, its host and protocol; else a `.command` with its `cwd`) and `item/fileChange/requestApproval` (with its `grantRoot`) become `AgentApproval`s (the JSON-RPC id kept as a `JSONValue`, so a number stays a number; a file change's paths come from its `item/started`, since the request names only the item) until `serverRequest/resolved` removes them; the reply is `{"id": <id>, "result": {"decision": "accept" | "decline"}}`. Every other server request is refused. Each `agentMessage` is a message; the last one not in the commentary phase is the answer at `turn/completed`. **Claude Code** (verified with 2.1.319 and the Agent SDK's `_internal/query.py`): `-p --output-format stream-json --verbose --input-format stream-json --permission-prompt-tool stdio --append-system-prompt <instructions>` (sessions persist, in the user's Claude Code history; a follow-up adds `--resume <session id>`, which keeps the id) plus the user's choices (`ClaudeTranscript.settings`: `--model`, `--effort`, and `--settings {"fastMode":true}` for fast, since with `-p` fast mode needs that opt-in); otherwise the user's settings, rules, hooks, MCP servers and CLAUDE.md apply. The prompt goes in as `{"type":"user","message":{"role":"user","content":…},"parent_tool_use_id":null,"session_id":"default"}` and stdin stays open (no `initialize` request needed) until the `result`, when the transcript closes it so the CLI exits. Each prompt is `{"type":"control_request","request_id":…,"request":{"subtype":"can_use_tool","tool_name","display_name","input","tool_use_id",…}}`: Bash becomes a `.command` (its `description` as the reason, no folder, since Claude Code's shell keeps its `cd`s and the prompt doesn't say where it is), Edit, MultiEdit, Write and NotebookEdit a `.fileChange` ("write notes/b.txt"), anything else a `.tool` with its input in brief. The approval's id is an object holding the request id and the input, since an allow must echo it: `{"type":"control_response","response":{"subtype":"success","request_id":…,"response":{"behavior":"allow","updatedInput":<input>}}}`, or `{"behavior":"deny","message":…}`. Its permission suggestions are never sent back, so an allow grants that call only. An approval goes when its tool's `tool_result` arrives (or a `control_cancel_request` names it), sub-agents' included; only the main agent's text is a message. AskUserQuestion is denied at once; other control requests (hooks, SDK MCP) get an error response. Status (`AgentStatus`) is `--version` plus the CLI's login check (20 to 150 ms, no model call); a version outside `AgentProvider.testedVersion`'s major.minor only adds a `warning`; `wicket agent status` prints it. Ending the run kills the whole process tree (each process stopped before its children are listed, since Codex runs commands in their own sessions); the final event comes after the tree has exited (see Process lifetime); a CLI that closed stdout without a final event gets 2 s to exit. Known exposure: a run does whatever the user's agent configuration allows unasked (Claude Code's `auto` or `bypassPermissions`, Codex's `never` with `danger-full-access`: anything, unseen by Wicket), loads the user's hooks and MCP servers in that folder, and can write extensions (which still run only once reviewed and enabled).

**Composed lists and pages (app).** `ResultsView` draws a list's summary (`ListTop`: the summary's document, as a page draws one) at the top of the rows' scroll view, so a long one scrolls away; the card makes room for it up to `PaletteMetrics.maxListTop` (four rows) above up to eight whole rows, once `ListTop` has measured it (`PaletteModel.measureListTop`). A section's title (`SectionHeader`, a VoiceOver heading) is drawn in the same container as its first row, so scrolling to the row shows its title and the arrows only ever land on rows. Row icons come from `IconCache` (`IconView`): symbols at once, Finder icons rendered to a bitmap off the main actor on first use and cached by standardized path, the row keeping an empty square meanwhile. A page (`DocumentView`) puts an extension's metadata by `DetailLayout`: in the 180 pt column when its text, laid out beside the column, is taller than the column, else as a table under the text; both heights are measured at the column's widths whichever way it is drawn (a hidden copy of the side-by-side layout only behind a full-width page, which is short by then), so the choice never oscillates and follows a growing answer.

**Documents (app).** `Frame.show` parses a page's markup once into a `Document` (`ScreenFrame.document`; a growing answer keeps its `Markup.Parser`). A detail whose document is only rows (a `Document.listing`), with no actions or metadata of its own, is shown as a list, so it filters; any other is a measured page whose `Document.targets` (in reading order: a column whole, then the next) are the frame's rows in an `ItemList(selectsFirst: false)`: nothing is selected until an arrow moves, up past the first target selects nothing again, and an arrow that moves no selection (no targets, or past the last) scrolls the page by three lines. Every press is a `PaletteModel.navigation`, apart from initial positioning (a new list at its top): a list reveals its selected row, clamped to the bottom under a tall summary, and goes back to its top only on Up at the first row. Typing a printable key on a page (`PaletteRootView.isTyped`) runs `PaletteSession.typingAction`, the first screen action whose command waits for text (Follow Up on an answer), with the typed text in its field; a page without one ignores typing. `DocumentView` draws the blocks in one scroll view (`DocumentBlocks`: the only switch, over prose, verbatim text and a component); each component is drawn by its own file in `Markup/`, a `ComponentView` registered by node type in `ComponentViews.registered` (a test checks every `Markup.components` entry has one, and a component without a view falls back to its text). A target's view takes `.target(item)`: the selection's fill, its ⌘1 to ⌘9 hint, a click runs it, its id scrolls it into view, VoiceOver reads it as a button. `DocumentFocus` (environment) carries the selection, hints and how to run a target; `TextSize.points`/`scale` size everything; `ToneStyle` maps the four tones to system blue, green, orange and red. Columns stack when a column would be narrower than 150 pt times the text scale (`ColumnsView`, a `Grid` in `ViewThatFits`). Charts are Swift Charts with `ChartView.summary` as VoiceOver's label.

**Images (app).** `ImageLoader.shared` (an `NSCache` charged by decoded bytes, 128 MB; one load per URL, cancelled when its last viewer goes; four at a time through `Gate`; timings only in the perf log) loads every image off the main thread: a local file through `QLThumbnailGenerator`, a remote one through `RemoteImages`, Wicket's own ephemeral `URLSession` (no cookies, cache or credentials), https only, with an SSRF check refusing a host unless every address it resolves to (`getaddrinfo`, which reads every literal spelling too) is public unicast, a redirect too, 8 MiB (checked as bytes arrive), 10 s, decoded with ImageIO to at most 2048 px and never SVG or PDF. DNS can change between this check and URLSession's connection; CONCEPT.md records that accepted rebinding risk. With `showOnlineContent` off, remote images are not fetched: tiles report themselves (`BlockedImagesKey`) and the screen offers Load Images (the hidden `builtin:load-images`, a `Builtin(_:staying:)` registered by `AppRuntime.init`) to load that page's; the action names its page in its args (`PaletteModel.pageArg`), since the built-in's own frame is on top while it runs. ⌘K pops up the actions menu (`ActionMenu`, a native `NSMenu` built from the `ActionTarget` captured on opening; `PaletteController.showActions` pops it from the panel's content view above the footer's right end, or under the pill without a card). It lists the target's actions, then the screen's under a section header ("Answer" on an agent's screen, else the command's title); each is named as `ActionDispatcher.resolve` says it runs (an agent's Open of an app shows as Reveal with the file's name, a detail as the item's one-line subtitle), and ↩ and ⌘↩ show as the key equivalents of the primary and `secondary`. The menu only records the choice; once tracking ends the controller runs it through `run(_:at:)`, the same dispatcher path as Return. While it tracks, `windowDidResignKey` doesn't hide the palette, the panel takes key back afterwards, and `hide()` cancels a menu still open; NSMenu's type-to-select replaces a search field. The footer shows the screen action ⌘↩ runs (Follow Up) on its left.

**Panel and card.** `PaletteController` owns the `NSPanel`'s frame (`sizingOptions = []`): the top-left anchor is resolved once per summon, a taller card resizes the window at once and animates the card into the transparent space, a shorter one animates first and shrinks the window in the animation's completion, so the pill never moves. `PaletteMetrics` computes a list's height: its summary as measured (`ListTop`, at most `maxListTop`; nil, keep the card, until it is), then its first eight rows (the answer row is 60 pt) with the section titles among them (24 pt each), so the card holds whole rows under any top and a plain list stops at 384 pt; a page's height is its content as `DocumentView` measures it, up to the same eight-row cap, and only grows within one generation of its frame (`PaletteModel.detailHeight`), so a streaming answer never shrinks mid-stream while a live command's next query starts over. Shrinking waits `shrinkDelay` (300 ms). A 40 pt transparent margin leaves room for the glass rim and shadow; the window draws none of its own.

**Keyboard.** `PaletteChord` (Core) matches chords (⌘K, ⌘↩: the screen's `secondary` action when it has one (Follow Up on an answer), else the row's second, ⌘1 to ⌘9, ⌘,, ⌘L, ⌃N, ⌃P); `PalettePanel` claims them in `performKeyEquivalent` (before the main menu) and `sendEvent` (before the field editor), routes editing shortcuts (`EditCommand`) to the field and swallows other menu keys. ⌘1 to ⌘9 match the number row by key code. **Menu bar icon.** `MenuBarItem` (WicketApp) owns an `NSStatusItem` (SwiftUI's `MenuBarExtra` needs a SwiftUI `App`, like the `Settings` scene), created the first time it is shown and only hidden after that, so nothing runs on the palette's path. Its menu is Open Wicket, Settings… and Quit Wicket; the first two call the runtime's `showPalette` and `showSettings`, the same paths as the hotkey and ⌘,, and Quit is `NSApp.terminate`, so quitting goes through the usual shutdown. With the icon hidden, opening the app again still shows the palette (`applicationShouldHandleReopen`).

**Settings window.** An `NSWindow` with `NSTabViewController` tabs, one SwiftUI `Form` per pane (General, AI, Voice; General holds Show online content); the Voice pane also writes `VoiceConsent`, the only store written besides the file. It writes through `Settings.update` (change only what changed, keep unknown keys, sorted atomic JSON, never overwrite an invalid file); `FileWatcher`'s reload applies it. The shortcut recorder releases Wicket's hotkey while recording. Launch at login is the system's (`SMAppService`, in the General pane), never mirrored into the file.

**Built-in sources (app).** `AppsSource` scans `/Applications`, `/System/Applications`, their `Utilities`, `~/Applications`, CoreServices, Finder and the Safari cryptex, one vendor folder deep plus apps inside apps, rescanning on FSEvents. `FilesSource` waits for 2 characters and 80 ms, then runs an MDQuery (`Spotlight`) for every word as a file-name word prefix (`FileSearch`, Core, builds the predicate, scopes and ignore rules), takes up to 500 hits, adds home's own visible entries (each home folder is a scope, since home itself would mean walking `~/Library`, so loose files like `~/report.pdf` and the folders themselves come from a directory listing) and lets the fuzzy matcher pick the best 20 (the whole query, else each word on its own less a prefix bonus, so words in any order match and the name in the query's order ranks first), minus a fixed penalty so an equal app ranks above a file. `CalculatorSource` gives at most one answer-tier row (`calculator:answer`) from `Calculator.evaluate` (Core): Return copies the result, ⌘↩ pastes it into the app below; input that parses but has no real answer (`1 / 0`, `sqrt(-1)`) gets a message row with no actions, and rounding noise is zeroed only where it can't be an answer: a `Quantity` carries the decimal places of the typed numbers through sums, differences and products, and a sum smaller than half that quantum is zero (`Quantity.cleaned`), so `1 - 0.9 - 0.1` is 0 while `9007199254740991 - 9007199254740990` stays 1; trigonometry zeroes only within a few ulps of the argument (`Math.denoised`); `ExchangeRateStore` caches the ECB XML in `~/Library/Caches/Wicket/` and refetches once a day old. Conversion conventions follow Tinycast's: a bare amount converts to the default currency (from the default currency itself, to USD, or EUR for USD), a trailing operator or `to` is dropped so the prefix answers, and sums and differences answer in the last unit. Frecency is `UsageStore` (`usage.json` in Application Support, 7-day half-life, capped boost), which only the root search ranks by, so only a root row's use is recorded (not answers or fallback rows); `PaletteModel` saves it through one `LatestWriter`, which writes snapshots one at a time off the main actor and skips any superseded while waiting, so an older one never lands last.

**Summon context (Core value, app capture).** `SummonContext` (Core) is the files the user had selected in Finder when they summoned Wicket; nil when they came from another app or nothing was selected. `PaletteController` starts `ContextCapture` (app) with the paste target, after the panel is ordered front, and hands the task to `PaletteSession.captureContext`; `hide()` clears it. The capture runs detached, only when Finder was frontmost: `get selection as alias list` as a raw Apple event sent with `kAEDoNotPromptForUserConsent` (empty unless Automation of Finder was granted), bounded at 150 ms, its time in the Perf log. It never prompts, and never reads the clipboard. The session shows it once captured (`context`: the pill's chip, `SummonContext.summary`, "Finder · 3 items"; Backspace in an empty field calls `dismissContext()`), and stamps it into `Invocation.context` when a run of a command with `RegisteredCommand.usesContext` (Run Agent) starts, waiting for a capture still running at most `contextWait` (300 ms); every other command's invocation has none. `AgentRunner` runs in the selection's folder (`AgentRunner.folder(for:)`) and sends the question followed by `SummonContext.promptBlock` (a `<context>` block with `<selected_files>`); the frame's title and Retry stay the question. Settings ▸ AI shows the Finder permission and asks for it on a click (`ContextCapture.finderAccess(ask:)`); the app is signed with the Apple events entitlement and has an `NSAppleEventsUsageDescription`. Nothing captured is logged or reaches the diagnostics.

**Voice input (app; transcript policy in Core).** `VoiceConsent` is the consent: `Application Support/Wicket/voice.json`, `{"version": 1, "listen": "onOpen" | "onCommand" | "off"}`, read at launch, written atomically only by Settings ▸ Voice (`VoicePane`), memory changed only after the write; a missing, unreadable or other-version file is off. `VoiceInput` (`@MainActor @Observable`, on `PaletteModel.voice`) is the one state machine, `state`: `idle`, `armed` (the microphone on quietly) or `listening` (`isListening`, in the open). `arm()` and `listen()` (only when not off, from idle) start a `Transcriber` session; `listen()` while armed just switches to listening on the same session. Armed, nothing is written: the first transcript with a letter or digit (`VoiceInput.isSpeech`) switches to listening and is written. The session writes each transcript through `write` (`PaletteSession.setSpokenQuery`: the root's text without keyword routing, or the text of a frame waiting for it, such as a follow-up; false once any other frame is on top, which stops listening), and stops after `Timing.silence` (60 s) without a new word (dictation runs through pauses until a key), `noSpeech` (6 s) with none, `limit` (5 min), on `stop()`, or on a failure, which `fail` posts to `Messages`. A generation counter drops anything a stopped session still delivers; stopping cancels the session's task, so its stream's next element ends it and the microphone stops. `keyPressed(isEscape:)`: while armed or listening any key stops it and goes on to the field; only a listening Escape is consumed (armed, Escape clears or hides as usual, and nothing heard is left behind). `PaletteController` calls `arm()` after the panel is ordered front and the previous app captured when the mode is `onOpen` (off the hotkey-to-visible path), and when an action opens a frame waiting for its text; `stop()` in `hide()` and before performing an action; and feeds every key from `PalettePanel.onKeyDown` (before chords) to `keyPressed`, except ⌘L. **By hand**: while voice is on, the pill ends with `MicButton` (where speech has somewhere to go, `PaletteModel.takesSpeech`: the root or a frame waiting for its text): `mic` idle, `mic.fill` armed (the only sign of it, besides macOS's orange dot), tinted while listening; its tooltip names ⌘L (`PaletteChord.listen`), and both call `PaletteController.listen()`. Starting clears the field. While listening (not armed) a moving `waveform` replaces the pill's glyph; the prompt never changes. A transcript moves the field editor's caret to the end but AppKit scrolls only after its own edits, so `PaletteRootView` reports every query change (`onQueryChange`) and `PalettePanel.revealCaret()` scrolls the field editor to its selection. **Transcription** (`AppleTranscriber`): on a detached task, refuses unless `AVAudioApplication.recordPermission` is granted (it never prompts), picks the language (`VoiceLanguage.choose`), checks the model is installed (`AssetInventory.assetInstallationRequest` is nil; `status` said `supported` for an installed model), taps the default input with `AVAudioEngine` and converts each buffer to `SpeechAnalyzer.bestAvailableAudioFormat` (16 kHz mono Int16 here) with `AVAudioConverter`, and feeds a `SpeechAnalyzer` with a `SpeechTranscriber` (volatile and fast results, `modelRetention: .lingering`); `Transcript` (Core) joins finalized segments and the volatile tail, and `Transcript.searchText` trims it and drops a trailing full stop ("Safari." still finds Safari; a question mark stays for the request rule). The model runs in a system process; in a headless test with a spoken file the first words came about 25 ms after audio warm and 170 ms cold, and volatile results arrive in bursts about a second apart. `VoicePane` turns voice on by asking for the microphone, downloading the language's model if missing (with progress) and reserving it (`AssetInventory.reserve`, released when turned off), then writes `onOpen`; its picker switches to `onCommand` ("Only when I ask"); its footer leads with how to start listening. The app has `NSMicrophoneUsageDescription` (and `NSSpeechRecognitionUsageDescription`, unused so far, so a framework check can't crash it) and the hardened runtime's `com.apple.security.device.audio-input` entitlement. Transcripts are never logged; the Perf log has only the time to the first words.

**Paste.** `SystemEffects` writes the clipboard itself (no "Copied" on top of the paste's own message), activates the target if needed, polls up to 1 s (10 ms steps) until it is frontmost, waits 50 ms for key focus, checks again, and posts ⌘ plus the key that types V in the current layout (`KeyLookup`, Core: the current layout, then an ASCII-capable one, then ANSI V). One paste is pending at a time: a newer paste or a copy cancels it, and ⌘V is pressed only if the clipboard's `changeCount` is still the one its write left. Accessibility is requested at most once per session.

## How to add a feature

- **A new kind of root result** (a built-in source): a `ResultSource` in `WicketApp`, its matching and logic in Core with tests, registered in `AppRuntime.live()`. Pick a relevance tier; never ship your own ranking. Background work it needs (a scan, a refresh loop) goes to the runtime's `work` in `live()`, which starts it once.
- **A new command**: a built-in is one entry in `AppRuntime.live()`'s table: its `RegisteredCommand` plus its runner (`Builtin(_:effect:)` if it just does something and closes, `Builtin(_:staying:)` if it does something and leaves the palette as it is (its effect gets the `Invocation`, and what it acts on comes in the action's args, since its own frame is on top when it runs), `Builtin(_:runner:)` with a `CommandRunner` if it shows something; below). Its runner's dependencies are made in `live()`; one that asks a model sets `usesAI`, so the AI switch covers it. Extension commands register from their manifests. Either gets search and keywords (and later deeplinks) through the registry and the invocation policy, with no plumbing of its own; declare its `input` (`none` if it just does something, so a keyword and a space don't open a frame for it; `submitText` for typed text run on Return, with `isFallback` to be offered for any query).
- **A new screen type** (grid, form, custom UI later): a `Screen` case (with its `items` and `title`), its decoding, and its view in `FrameContent`. Not a parallel system.
- **A new action**: not a new `Item.Action` case. Something the host does for the user (reveal, approve an extension) is a built-in, and an item offers it as `.run(command:text:args:)`. The cases are the data primitives (open, copy, paste, reveal, detail, run); presentation in `ActionPresentation`.
- **A new setting**: add a field and default in `Settings` (Core), its independent decoder and `Settings.update` serialization, then apply it in `AppRuntime.apply` and expose it in the relevant settings pane. Cover invalid-field fallback, preserving unknown keys on write, and live application in the settings/runtime tests. If it grants anything, it is consent and belongs in a UI-owned store instead.
- **A markup component**: implement `Component` in `WicketCore/Markup/Components/` and register it in `Markup.components` (`Catalog.swift`); add its native view in `WicketApp/Markup/` and register its type in `ComponentViews.registered`. Include tags, attributes, an example, plain text and targets. Refresh the generated reference with `WICKET_UPDATE_GOLDEN=1 swift test --filter docsMatchTheRegistry`; add parser/lint and view coverage for the new behavior. [markup.md](markup.md) is the agent-facing contract.
- **An extension feature**: first try the existing commands, args, lists, markup and actions in [extensions.md](extensions.md), using several ordinary entries if needed. A wire change goes in `WicketCore/Extension/` (manifest/request/response as applicable), [extension.schema.json](extension.schema.json), the guide and sample, then its Host runtime handling. Cover strict decoding and the app/CLI path; use `wicket check` for static validation and `wicket run` for real execution. Keep protocol 2's one-request/one-response lifetime.
- **A command with its own screen** (Run Agent): a `CommandRunner` producing `RunResult`s for its `Invocation` (a growing answer yields a new `.show(.detail)` per whole message), registered as a command (a built-in: its entry in the table in `AppRuntime.live()`); its frame, loading state, failures and cancellation come with it.
- **Anything long-running**: owned by a frame or a host actor, cancellable, never on the keystroke path.

## Developer commands and opt-in checks

Run from the repository root. `Scripts/check.sh` builds with warnings as errors, runs all ordinary tests and lints Swift formatting. Tests use fakes and recorded streams unless explicitly opted into a real agent. Never launch the app or run `.build/*/wicket` to check a CLI change: on a case-insensitive disk that name is the app. Use the CLI product `WicketCLI` or the bundled `Contents/Helpers/wicket`.
