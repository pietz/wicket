# Architecture

How Wicket is built and how to add to it. Every builder reads this before touching `Sources/`. CONCEPT.md holds the why and the decisions; this page holds the shape of the code. It came out of the first architecture review (2026-11-06, Fable and Astra independently, in strong agreement); later reviews run per [reviews/architecture-review.md](reviews/architecture-review.md) and update it.

Status markers: **(now)** is how the code works today, **(target)** is what the refactor plan below builds. When a step lands, its marker goes.

## Modules

| Target | Owns | Never |
|---|---|---|
| `WicketCore` | Values and deterministic policy: `Item`, actions and their dispatcher, content (`Screen`, `RunResult`), commands, their ids and the registry, ranking, search, the navigation stack's logic, calculator, wire decoding | Processes, AppKit, SwiftUI |
| `WicketHost` | Everything that talks to another process or to OS services shared with the CLI: `ExtensionSession`, `Extensions` (discovery and session lifecycle), `Agent`, Keychain, login shell, checker | Windows, views |
| `WicketApp` | AppKit and SwiftUI: the panel, views, hotkeys, OS integrations (Spotlight, apps, settings window), composition and settings reconciliation (`AppRuntime`). A library so `WicketAppTests` can `@testable import` it | Policy that could be tested in Core |
| `Wicket` | The executable: only `main.swift`, which starts `WicketApp` | Anything else |
| `WicketCLI` | The `wicket` tool: a thin client over Host | Its own copies of Host logic |

Rule of thumb: if it can be tested without a window, it belongs in Core or Host, with a test.

## Core concepts

**Item: a row.** One result row from any source, with its actions. It is not a command, a screen or an execution context. Items carry a host-stamped **origin** (the `CommandID` whose response produced them; nil for the host's own sources); extension ids are namespaced by origin (`ext:<extension>/<command>:<id>`) so two extensions can't collide.

**Action: data.** What an item can do: `open`, `copy`, `paste`, `reveal` (host only), `detail` and `run` (a `CommandID`: resolved at decode to a command of the item's own extension, so only the host can name a built-in; the host may add `text` to submit, as a fallback row does with the query). Actions never carry closures. One **dispatcher** (`ActionDispatcher`, Core) turns an action plus its context into an **outcome**:

```swift
enum ActionOutcome { case close, push(Detail), open(CommandRun) }
struct CommandRun { var command: RegisteredCommand; var invocation: Invocation; var retry: RetryPolicy; var query: String? }
```

Side effects (open, copy, paste, reveal, open settings, quit) are injected as `ActionEffects`; the app's `SystemEffects` implements them with AppKit. `ActionContext` carries the app that was frontmost at summon, which `paste` targets; what a paste can do there (type ⌘V, or only copy and say why) is `PastePlan` (Core), carried out by `SystemEffects`. The dispatcher is synchronous: Settings and Quit run their effect and close; any other `run` (extension commands, and built-ins that show something, like Ask AI) returns `.open` with the `CommandRun` the invocation policy (below) makes of it, and the palette session runs the command for its frame. A `run` naming a command that isn't registered is pushed as a failure detail naming the command, which Return copies.

**Command: something you can invoke.** Built-ins (`BuiltinCommand`: Settings, Quit, Ask AI) and extension commands share one identity, `CommandID` (in `WicketCore/Command.swift`), and one shape:

```swift
struct CommandID: Hashable, Codable, Sendable { var owner: Owner; var name: String }  // owner: .builtin or .extension(id)
struct Invocation: Sendable { var command: CommandID; var text: String; var args: [String: JSONValue]? }
```

The **command registry** (`CommandRegistry`, Core) is the one catalog: built-ins plus the extension commands the app registers. It lists the root commands (`CommandsSource` is its projection, through the shared `SearchIndex`; hidden and root-mode commands are reachable by id only), resolves a `CommandID` (the dispatcher's `run`), resolves keywords (for commands the root offers, `isOffered`: listed ones and fallbacks, and only if they take text) and offers its fallbacks (`FallbackSource`). Keyword collisions: a built-in always keeps its keyword, among extensions the first in registry order (extension id, then manifest order) wins, and losers are listed in `keywordConflicts`. Aliases and per-command hotkeys resolve through it (below); `wicket://` deeplinks and the MCP server are to as well. A built-in that belongs to a `Feature` (`RegisteredCommand.feature`) isn't registered while it is off (`setDisabledFeatures`). Persistent bindings store a `CommandID` or an `Invocation`, never a row id. A `CommandID`'s canonical spelling (`description`, `CommandID(_:)`) is `builtin:<name>` or `ext:<extension>/<command>`: settings.json keys, logs and the prefix of an extension item's id all use it.

**Invocation policy: one way in.** Each command declares how it takes text and whether a run may be repeated; the domain owns both types (`Command.swift`) and manifests translate into them (`Manifest.Command.input`, `.retry`):

```swift
enum CommandInput { case none, immediateText, submitText, liveText }
enum RetryPolicy { case never, safeToRepeat }
enum CommandTrigger { case invoked, keyword }
CommandRun(_ command: RegisteredCommand, _ trigger: CommandTrigger, text: String, args: [String: JSONValue]?)
```

`CommandRun(_:_:text:args:)` is the policy, and every way in goes through it: a row or fallback row and a `run` action (the dispatcher, `.invoked`), a hotkey (the dispatcher, as the row), `wicket run` (`.invoked` with its text and `--args`), a keyword or an alias and a space (`PaletteSession.setQuery`, `.keyword`); deeplinks and MCP will be `.invoked`. What it decides:

| Input | Who | Invoked | Keyword or alias and a space |
|---|---|---|---|
| `none` | Settings, Quit | runs now; text ignored | not routed: its alias only names it |
| `immediateText` | extension `once` (and `root`) | runs now on the text; frame on first content | runs on the rest of the line; frame at once, its field filters |
| `submitText` | Ask AI | with text: runs now; without: frame waiting for text | frame waiting, the rest of the line in its field; never runs |
| `liveText` | extension `live` | frame at once, searching the text | frame at once, searching the rest of the line |

`CommandRun.query` nil means "run now, show the frame when the first result is content"; a query means "show the frame at once with this text in its field". A frame waiting for text (`awaitsText`) runs nothing on keystrokes; its target is `.run(command:text:)` with the field, so Return submits through the dispatcher like any action and the answer opens in a frame of its own (Escape goes back to the question). `retry` is the command's own, never inferred from how it was reached or whether it is listed: `never` by default; `safeToRepeat` for live and root runs (searches) and once commands whose manifest says `repeatable`. Built-ins never reach `ExtensionSession`, so theirs only documents intent.

**Bindings: hotkeys and aliases.** `Settings.commands` (`"commands": {"builtin:ask-ai": {"hotkey": "ctrl+option+a", "alias": "ask"}}`) maps a `CommandID` to a `CommandBinding`; each bad key, hotkey or alias is ignored on its own with its reason, and an entry for a command that isn't registered stays in the file, inert, until it is. Aliases go into the registry (`setAliases`): typed alone, an alias puts its command in the `alias` tier, above every exact match; followed by a space it is the command's keyword (for an offered command that takes text; Settings and Quit take none, so their alias only names them). Collisions: alias against alias, the first canonical id keeps it (`aliasConflicts`); an alias beats every keyword (`keywordConflicts`). Hotkeys resolve in `CommandHotkeys.resolve` (Core: the palette's hotkey always wins, then the first canonical id; unregistered commands take no key), and the app's `HotKeys` registers one Carbon hotkey each, with the palette's own, re-registered on every settings reload and registry change (see App runtime). A pressed hotkey goes to `PaletteController.run(bound:)`, which dispatches `.run(command:)` like the command's row: an effect closes, a frame opens (a hidden palette is shown when the frame has content or after 250 ms of running, so a toggle answering `close` shows only its message; a frame with a query, such as Ask AI's waiting for its question, shows at once), and the same hotkey again closes the frame. No keyword text is typed, so no other command's keyword or alias can take the hotkey. A binding is a preference: it never enables or approves an extension. Until the consent store (step 5) approves extension revisions, the app registers no extension commands and adds no `ExtensionRootSource` (`AppRuntime.extensionCommandsInPalette`, the one switch), so they appear nowhere in the palette and a `run` action naming one fails as not found. Everything else (the runner, command frames) is wired either way, so flipping the switch is the whole change.

**Content: what a screen shows.** One content model for everyone, not only extensions (`WicketCore/Content.swift`, with public initialisers):

```swift
enum Screen { case answer(Item), list([Item]), detail(Detail) }
enum RunResult { case show(Screen), close(message: String?), reload(message: String?) }
```

`Screen` is what a frame above the root shows, whether a command's run sent it or a `detail` action pushed it. What a frame needs to know about a screen, without switching over its cases, are its own properties: `items` (the rows a selection moves through: an answer's one, a list's; nil for a page, whose view lays out its content and measures it to size the card), `title` (a page's, for the pill) and `target` (a page's actions). The wire format is the encoding (`Extension/Decoding.swift`); it has no `show`: `answer`, `list` and `detail` are decoded into it, `close` and `reload` as they are. A new screen (a grid, a form) is a `Screen` case with those properties, its decoding, and its view in `FrameContent`, the one switch from a screen to a view; the frame, sizing, pill, target, failures and reload follow. New interaction it brings (a form's fields and submit, a grid's sideways selection) is its own work on top.

**Command runs: a stream of content.** Whatever a command shows comes from one interface:

```swift
protocol CommandRunner { func run(_ invocation: Invocation, retry: RetryPolicy) -> AsyncThrowingStream<RunResult, any Error> }
```

Each element replaces the content of the command's frame (the rule `ResultSource.updates` has for root sources); `close` closes the palette with its message; `reload` drops the frame (or, if it was never shown, doesn't show it) and runs the frame it was opened from again, with its message; an error replaces the content with a failure detail; ending the iteration (pop, dismiss, a superseding query) must stop the work. `Extensions` (Host) is the first producer: one element per run. A streaming AI answer is a built-in producer behind the same protocol, yielding a growing detail (`.show(.detail)`) again and again; the frame keeps its id and generation across elements, so its view updates in place (scroll position kept: the card content is identified by the frame's id), and the pill spins until the stream ends. Ask AI (`AskAIRunner`, Host) is the second. The session gets one runner, `CommandRouter` (Core): built-ins go to the runner registered for their `CommandID`, extension commands to `Extensions`; a command nothing runs fails its frame.

**Palette session and frames.** `PaletteSession` (Core, `@Observable`) owns a stack of **frames** (`Frame`): each keeps its id, query, content (`.search(RootResults)` for the root, `.screen(ScreenFrame)` for everything above it: the latest `Screen` and the `CommandRun` feeding it, nil for a page a `detail` action pushed, which never runs, so a `reload` landing on it does nothing), selection (in its `ItemList`), load state and generation. Escape stops a command being opened, else clears the text, else pops, else hides (`escape()` says which). Return, ⌘↩, ⌘K and ⌘1 to ⌘9 act on the top frame's `ActionTarget` (the selected item's actions, or the detail's). Every restart of a frame's work (a root or live query, a reload) starts a new generation; work results are applied only if frame identity and generation still match, and work is cancelled on pop, dismiss (`reset()`) and superseding queries.

How commands open: typing a registered keyword and a space in the root (`setQuery`) resolves the command with `.keyword` and leaves the keyword in the root's field; `open(CommandRun)` takes the policy's run, from the keyword or an action's outcome. A run with a `query` pushes its frame at once with that text in its field (a live command, a keyword's once command, a command waiting for its text); anything else stays `opening` (the pill spins, other actions wait, Escape cancels) until its first result: content pushes the frame with it, `close` and `reload` act without a frame ever showing. A live frame runs again on every query change after `liveDebounce` (50 ms; a burst sends only the last text, and the superseded run is cancelled), with its command's retry. A once frame filters a list locally by title with the shared fuzzy matcher (`SearchIndex`), never running again for it. The selection follows its item when content is replaced and goes to the top when the text a list answers changes.

Compactness follows the frame (`Frame.isCompact`): the root with an empty query is the bare pill, and so is a live command with an empty query and an empty list, and a command waiting for its text (its placeholder is the prompt); any other pushed frame is content (an empty list shows "No Results"). While a pushed command frame has no content yet the card keeps its height. `PaletteSession.onClose` asks the app to close; a `close` or `reload` message is posted to the session's `messages` after it (see Messages). `PaletteModel` (app) adds only view state (focus, the action panel, the card height, the footer message) and usage; `PaletteController` turns intents into session calls.

**Root search.** `ResultSource` (Core: `instant` plus optional `updates`) is the interface for the root frame only, and stays fast and synchronous on the keystroke path. Root-mode extension commands are one source (`ExtensionRootSource`, Host): after 80 ms without a newer query, each root command whose `pattern` matches gets the text, and its answer or first 10 items join the results as they arrive; failures are recorded in the diagnostics like any failed run (see Diagnostics), never shown inline. `RootResults` (Core) aggregates: each source's latest items, generation checks (a late update for an older query is dropped), ranking. `Ranker` orders by tier (alias, exact, answer, match, fallback), then three policies within a tier: user-ordered fallbacks (fallback items whose origin is in the user's list, in that order; the list itself is a later settings field, `fallbacks: [CommandID]`, not added while Ask AI is the only fallback), host-scored candidates (apps, files, built-ins: score plus frecency, none for fallbacks), then provider-ordered results (each extension command's items as one block, in the order sent, never reordered by habit). Selection lives in `ItemList` (Core), shared by every list: it follows the item id; if the selected item disappears the selection stays on its row (clamped), and truncation never drops the selected item.

**Extension lifecycle.** Host owns discovery and session replacement (`Extensions`: the old session is fully shut down before the new one starts; the app only feeds it folder changes), each extension's **revision** (see Revisions), the **approved revision** (see consent below, **(target)**) and diagnostics. Discovery does not imply permission to run. Every request carries its command's `RetryPolicy`: only `safeToRepeat` runs are resent after a clean exit. Every termination path escalates to SIGKILL.

**Process lifetime.** Both transports (extension sessions and agent runs) start their child through `ProcessTree` (Host), which owns its stdin writer and its lifetime; the transports keep their own protocols. A member of the tree is the child; anything in its process group (`Process` gives the child its own, and a background job stays in it after the child exits); anything holding the write end of its stdout or stderr (found by scanning the user's processes' fd tables, only while a write end is still held, which the read end's peer handle tells cheaply); any process seen as a member in an earlier scan; and every descendant of those (`proc_listchildpids`, which follows children into their own sessions while their parent lives, as Codex runs commands). macOS has no subreaper and no longer shows other processes' environments, so this is what can be attributed without privileges; a process that leaves the group, closes the pipes and outlives every member it was seen through has daemonised on purpose and escapes. `stop(after:grace:)` runs once however often it's called: close stdin, wait (the child's exit is an event, descendants are polled with backoff), SIGTERM every member, grace, then SIGKILL: each member is SIGSTOPped before the next listing so none can fork in between, then all are killed. Its task finishes only when no member is alive (bounded by `killBound` if one survives SIGKILL), which also means the pipes are closed, and returns `Shutdown` for the whole tree. An extension process that exits by itself is stopped the same way (its leftovers get the grace), and the session finalizes (resend, successor, `shutdown()` callers) only after that, so `Extensions`' serialised replacement waits for the old tree, not just the process. An agent run's stream ends after its tree is stopped (cancellation: SIGTERM at once; a finished run: grace first).

**Agent runs.** `Agent` (Host) yields `AgentEvent`s; `AgentProvider` (the names) is in Core so settings can choose one. `AskAIRunner` maps one answer run into its frame's content: a detail titled with the question that grows with the text (throttled to about 30 updates a second), replaced by the final answer, actions Copy Answer and Paste Answer; a provider that isn't ready or a failed run throws, so the frame shows a failure saying what to do. Agent events stay separate from extension RPC.

**Fallbacks and Ask AI.** `FallbackSource` (Core) offers one row in the fallback tier for any non-empty query per registered fallback (`isFallback`, a `submitText` command), its action `.run(command:text:)` with the query, its id `fallback:<command id>`. Ask AI (`AskAI`, Core) is such a built-in, unlisted, with the keyword `ai` (a built-in keeps it against extensions; the user's alias beats it, as every keyword); its `ai `, alias and hotkey open its frame waiting for the question. Nothing names Ask AI outside its definition, its runner and the composition in `AppRuntime`. The next fallback (web search) is one more `submitText` registration.

**The checker is the gate.** `Checker.check(folder, options:)` (Host) is what approves code, so it never runs a candidate with the user's secrets, environment, files or network, and it has no mode that does: `CheckOptions` carries only the version and timeouts. `CheckIsolation` makes a scratch folder per check (realpath'd, since the sandbox matches resolved paths) with a sealed copy of the candidate (`candidate/<folder name>`), `home`, `tmp`, `data` and a generated `sandbox.sb`. The session configuration it builds sets every declared secret to a placeholder, `environment` to `HOME`, `TMPDIR` and `WICKET_CHECK=1` (the session adds `PATH`, `LANG`, the `WICKET_` variables and secrets; nothing is inherited) and `wrapper` to `sandbox-exec -f sandbox.sb`, which execs the program so signals and process ownership are unchanged. The profile is `allow default` minus the ways out: `network*`, `file-write*` outside the three scratch folders (plus `/dev` nodes and bash 3.2's here-document files in `/var/tmp`), the Keychain and pasteboard Mach services, `appleevent-send` and `lsopen`. Before replaying, the profile is applied to `/usr/bin/true`; if that fails (no `sandbox-exec`, or the caller is itself sandboxed) the check fails closed. No fixture: an error, nothing launched. `finish` shuts the process down before reading the session's issues, so what it writes on the way out counts. `wicket run` is the developer's explicit unsandboxed path (real environment, environment-or-Keychain secrets). Remaining exposure: the candidate can read files the user can (as the agent sandboxes can) and reach Mach services the profile doesn't name; `sandbox-exec` is deprecated, so its presence is verified on every check rather than assumed.

**Settings versus consent.** `settings.json` holds preferences only: agents may edit it, and nothing in it can grant consent (principle 6). Consent and approval (which extension revisions may run, MCP server on, network for build runs) live in a host-owned store in Application Support **(target)**, written only by Wicket's own UI.

**App runtime.** `AppDelegate` only starts `AppRuntime` (WicketApp), which composes the app (`AppRuntime.live()`: the sources, the registry, the palette model and window, the settings window) and applies settings.json. Every reload goes through `apply(Settings)`, one snapshot in an order that keeps what depends on it coherent:

1. the values read on use: the palette's width (next summon), the AI provider (next answer);
2. the registry: the built-ins of features that are off (`setDisabledFeatures`) and the aliases (`setAliases`);
3. if the registry changed (`CommandRegistry.changes`), the runs of commands no longer in it stop (`PaletteSession.stopCommands(where:)`: an opening is cancelled, the lowest frame running one is popped with everything above it);
4. the root's sources (`setSources`, which searches again), else, if the registry changed, one fresh root search, so a new alias or a feature turned off shows on screen at once;
5. the work behind each feature (`AppRuntime.Work`, start and stop, in `Feature.allCases` order; nothing runs before the first snapshot, so it only starts);
6. the hotkeys (`HotKeys.apply`): command hotkeys no longer wanted are released first, then the palette's changes, then the remaining command hotkeys register, so one change can move a combination between them; then what the panes read: `SettingsStore.commands`, and in the diagnostics the bindings not in effect (`.binding`: per command, and the palette's own under `.bindings`) and keyword conflicts (`.conflict`).

Registering extension commands (behind the switch) takes steps 3, 4 and 6 too. Every field of settings.json fails alone: a bad main hotkey is ignored with its reason and the palette keeps the default, like a bad width or binding; only a file that isn't a JSON object falls back to defaults entirely. While the settings window records a hotkey every hotkey is released (`store.pauseHotKey`); when it ends, settings are reloaded, so the one just written registers at once. The side effects come through seams: `AppRuntime.System` (`registerHotKey`, Carbon in the app; `watch`, FSEvents) and each feature's `Work`, and the window through `PaletteSurface` (`PaletteController`), so `WicketAppTests` applies snapshots against fakes. The Shortcuts pane refuses a hotkey or alias another registered command has (`Settings.hotkeyConflict`, `aliasConflict`); a binding of a command that isn't registered is inert there too, as in `CommandHotkeys`.

## Subsystems

Mechanism moved here from CONCEPT.md's decisions (the reasons stay there).

**Extension runtime (Host).** One `ExtensionSession` actor per extension, shared by the app and the `wicket` tool (`Contents/Helpers/wicket`). A process starts with the first request and is reaped after 60 s idle. Pipes are read with readability handlers (`FileHandle.bytes` held back output and blocked cooperative threads). Secrets are one generic password per extension and name in the login keychain (`wicket secret set`), passed as environment variables; extension data lives in `Application Support/Wicket/ExtensionData/<id>`, outside the watched folder. The session warns when `python3` is the Command Line Tools stub. Fixture `expect` lines match as patterns (fields left out aren't checked). The checker fails on protocol slips the app only records (a stray stdout line). A stopped session refuses new requests; runs that are `safeToRepeat` are resent after a clean exit only when the previous process answered something, so resends always end; the others fail with `HostError.notResent`.

**Diagnostics (Host).** `Diagnostics` (`@MainActor @Observable`) is the one store of what is wrong: each `Diagnostic` has a subject (`.extension(id)`, `.command(CommandID)`, `.settings`, `.bindings`), a kind (who reports it), a severity, a text and the time it was first reported. Producers replace their own kind's reports (`set` for one subject, `replace` for all), so they never clear each other's, and a report made again keeps its time and causes no observable change. Bounded: the newest 10 per subject and kind, texts at 4 KiB (a stderr tail at 16 KiB, its end from a line start). Producers: `Extensions.load` (`.discovery`: a bad manifest, a folder named wrong, no revision), `Extensions.result` (`.run`: a command's last failure, root and frame alike, with an extension error's `data`, cleared by its next answer; then the session's `report`: `.protocol` issues, `.setup` warnings, `.stderr`, taken only when its version changed), `SettingsStore.reload` (`.settings`: ignored fields as warnings, an unreadable file as the error that `loadError` reads), `AppRuntime.applyHotKeys` (`.binding`, `.conflict`). A changed or removed extension's session reports and failures are dropped with its old session. Readers: the Shortcuts pane (`text(for: .command(id), kind: .binding)`), the General pane (`hotKeyFailed`, `loadError`), and the Extensions screen and "Fix with agent" (`report(forExtension:)`: the extension and its commands). One instance per app, made in `AppRuntime.live()` and handed to `SettingsStore` and `Extensions`. What an extension wrote has the session's secret values (the ones it passed, 4 characters or more) and, for a failed run, the run's text (3 characters or more) replaced before it is stored; Wicket's own texts never quote a query. Nothing in the store is logged. A session keeps its newest 50 issues.

**Messages (Core, presented by the app).** `Messages` is the one channel for transient messages (`Message`: text and kind, `done` or `copied`). Posters: the palette session (a command's `close` message after `onClose`, a `reload`'s message) and `SystemEffects` (a paste that only copied); later voice and onboarding. `AppRuntime` owns it and hands it to the session (through `PaletteModel`) and to the effects; `PaletteController.present` shows a message in the card's footer while the card is up, else in the HUD where the pill is or was.

**Revisions (Core value, Host hashing).** `ExtensionRevision` (`extensionID`, `sha256` in lowercase hex) is computed by `ExtensionRevision(folder:id:)`: walk the folder without following links, skipping `.git`, `node_modules`, `.venv`, `__pycache__`, `.claude` and `.DS_Store` at any depth; take regular files and symbolic links (a FIFO, socket or device is an error); sort by relative path as UTF-8 bytes; hash `wicket-revision-1`, then per entry length-prefixed fields (8-byte little-endian length): `f`, path, `x` or `-` (any execute bit), bytes; or `l`, path, the link's target as written. Folders count only through what they hold; other permission bits don't count. A link must be relative and its real path (`realpath`, so a chain through another link can't climb out while its spelling stays inside) must be inside the folder and outside the skipped names; else `RevisionError`. Bounds: 32 MiB and 5000 files outside the skipped names, checked by `lstat` size before anything is read. `Extensions.load` hashes new folders and those its watcher reported (others keep theirs), on the main actor at load time only; a folder that fails is not installed and its reason is a `.discovery` diagnostic. The session is created with its revision, and decoding stamps it (`WireContext.revision`) on every `run` action the extension sends, in items and details. The dispatcher carries it through `CommandRun` into `Invocation.revision`, and `Extensions.result` refuses a run whose revision isn't the session's (checked after any replacement has finished) with `HostError.extensionChanged` ("the extension changed since this was shown; run it again"), which the frame shows as its failure. Runs the user names (a row, keyword, alias, hotkey, `wicket run`) carry no revision and run what is installed. Remaining gap: a change between the write and its FSEvents delivery (0.3 s latency) still runs under the old revision's stamp.

**Agent adapters (Host).** `Agent` finds `codex` or `claude` on the login-shell PATH and runs one prompt in a working directory in `answer` or `build` mode, yielding text deltas and activity lines, then one answer (with token usage) or one error. Codex: `app-server` JSON-RPC, an ephemeral thread per run, sandbox `read-only` (answer) or `workspace-write` with network off (build), approval policy `never` (anything still asked is refused), and `-c` overrides that switch off hooks, notify, plugins, apps, browser and computer use, sub-agents, memories, web search and every MCP server listed by `config/read`; answer runs also drop the shell and use a short answer prompt. Claude: `-p` with stream-json and the prompt on stdin, `--safe-mode`, `--strict-mcp-config`, `--no-session-persistence`, `--permission-prompts none`; answer runs `--tools ""`, build runs `--restricted` plus the Bash sandbox without the unsandboxed fallback. Status (`AgentStatus`) is `--version` plus the CLI's login check (20 to 150 ms, no model call); a version outside `AgentProvider.testedVersion`'s major.minor only adds a `warning`. Ending the stream kills the whole process tree (each process stopped before its children are listed, since Codex runs commands in their own sessions); a CLI that closed stdout without a final event gets 2 s to exit. Known exposure: both sandboxes can read the whole disk and write to temp folders; Codex still loads `~/.codex/AGENTS.md`; Claude leaves a `.claude/` folder to strip before install.

**Panel and card.** `PaletteController` owns the `NSPanel`'s frame (`sizingOptions = []`): the top-left anchor is resolved once per summon, a taller card resizes the window at once and animates the card into the transparent space, a shorter one animates first and shrinks the window in the animation's completion, so the pill never moves. `PaletteMetrics` computes a list's height from fixed row heights (the answer row is 60 pt) up to 384 pt; a detail's height is measured by `DetailView` and only grows while its run streams (`DetailMeasure`, Core). Shrinking waits `shrinkDelay` (300 ms). A 40 pt transparent margin leaves room for the glass rim and shadow; the window draws none of its own.

**Keyboard.** `PaletteChord` (Core) matches chords; `PalettePanel` claims them in `performKeyEquivalent` (before the main menu) and `sendEvent` (before the field editor), routes editing shortcuts (`EditCommand`) to the field and swallows other menu keys. ⌘1 to ⌘9 match the number row by key code. Plain keys stay with the field's `onKeyPress`. `MainMenu` is built once at launch and only shows while the settings window makes Wicket a regular app.

**Settings window.** An `NSWindow` with `NSTabViewController` tabs, one SwiftUI `Form` per pane (General, Features, AI, Shortcuts). It writes through `Settings.update` (change only what changed, keep unknown keys, sorted atomic JSON, never overwrite an invalid file); `FileWatcher`'s reload applies it. The shortcut recorder pauses every Wicket hotkey while recording.

**Built-in sources (app).** `AppsSource` scans `/Applications`, `/System/Applications`, their `Utilities`, `~/Applications`, CoreServices, Finder and the Safari cryptex, one vendor folder deep plus apps inside apps, rescanning on FSEvents. `FilesSource` waits for 2 characters and 80 ms, then runs an MDQuery (`Spotlight`) for every word as a file-name word prefix (`FileSearch`, Core, builds the predicate, scopes and ignore rules), takes up to 500 hits and lets the fuzzy matcher pick the best 20, minus a fixed penalty so an equal app ranks above a file. `CalculatorSource` gives at most one answer-tier row (`calculator:answer`) from `Calculator.evaluate` (Core); `ExchangeRateStore` caches the ECB XML in `~/Library/Caches/Wicket/` and refetches once a day old. Frecency is `UsageStore` (`usage.json` in Application Support, 7-day half-life, capped boost).

**Paste.** `SystemEffects` activates the target if needed, polls up to 1 s (10 ms steps) until it is frontmost, waits 50 ms for key focus, checks again, and posts ⌘ plus the key that types V in the current layout (`KeyLookup`, Core: the current layout, then an ASCII-capable one, then ANSI V). Accessibility is requested at most once per session.

## How to add a feature

- **A new kind of root result** (a built-in source): a `ResultSource` in `WicketApp`, its matching and logic in Core with tests, registered in `AppRuntime.live()`. Pick a relevance tier; never ship your own ranking. If the user should be able to turn it off, add a `Feature` case whose raw value is the source's id (and give its background work to the runtime as the feature's `AppRuntime.Work`, in `live()`); the Features pane and settings.json pick it up.
- **A new command**: a built-in that just does something is a case in `BuiltinCommand` (its title and icon) and its effect in the dispatcher; one that shows something is a registered command plus a `CommandRunner` (below); extension commands register from their manifests. Either gets search, keywords, aliases and hotkeys (and later deeplinks) through the registry and the invocation policy, with no plumbing of its own; declare its `input` (`none` if it just does something, so a keyword or alias and a space don't open a frame for it; `submitText` for typed text run on Return, with `isFallback` to be offered for any query) and its `retry`.
- **A new screen type** (grid, form, custom UI later): a `Screen` case (with its `items`, `title` and `target`), its decoding, and its view in `FrameContent`. Not a parallel system.
- **A new action**: a case in `Item.Action`, handled by the dispatcher, returning an outcome. Presentation (title, symbol) in `ActionPresentation`.
- **A new setting**: a field in `Settings` (Core) with a default, applied live; if it grants anything, it is consent and does not belong in settings.
- **A command with its own screen** (Ask AI, an MCP tool): a `CommandRunner` producing `RunResult`s for its `Invocation` (a growing answer yields a new `.show(.detail)` per chunk), registered as a command (a built-in: a `BuiltinCommand` case, its runner added to the `CommandRouter` in `AppRuntime.init`); its frame, loading state, failures and cancellation come with it.
- **Anything long-running**: owned by a frame or a host actor, cancellable, never on the keystroke path.

## Phase 3 plan (third review, 2026-11-06)

The third review (Fable and Astra, independently) found Phase 2 landed as described and the core primitives holding. Both found the same three gaps on the path to approval and Make a command: approval is a switch in the App, not a gate in Host, so a deeplink, MCP or the CLI would pass it; what runs is a mutable folder, not the exact files that were checked and approved; and all work dies with its frame, so a minutes-long build would die on Escape. Each step is green commits with tests.

- **G. Contract holes.** The checker rejects fixtures that exercise nothing (an empty `session.jsonl` passes today). `ScreenFrame.target` keeps the submitted invocation's `args` and `revision` instead of rebuilding it. Diagnostics redact before they truncate, redact the queries a session was sent, and claim no more privacy than they give. `PaletteModel`'s usage saves are serialized. The checker sandbox stops reading the user's files outside the candidate and the toolchains, or the limit is stated where approval is asked.
- **H. Built-ins as data.** One `Builtins` table (registered command plus runner) composed in `AppRuntime.live()`; delete `BuiltinCommand`, the `AskAI` statics, `PaletteMode` and the Settings and Quit cases in `ActionDispatcher` (they become runners yielding `.close`). `ExtensionCommand` folds into `RegisteredCommand`. Renames: `Query.revision` to `generation`, `CommandRegistry.revision` to `changes`, so `revision` means only `ExtensionRevision` (and the wire counter). Rule: no new `Item.Action` cases; everything the host does is a built-in reached by `.run`.
- **I. Sealed revisions and an active catalog.** Host keeps retained copies of revisions (folder plus hash, dependencies included: the install contents differ from authoring exclusions) in host storage; checking returns the revision it checked, on the retained copy. Discovery (every extension, with its state: enabled, changed, unapproved, invalid) is separate from the active catalog the registry projects. Loading and hashing leave the main actor and publish one snapshot. Frames bind to the revision they resolved and are reconciled when activation changes.
- **J. Process completion and build jobs.** An agent run reports its final answer only after its process tree has exited, and has an awaitable cancel; app termination awaits the runtime's shutdown. A Host-owned `@Observable` build job (generating, checking, review, installed, failed) that a frame observes through a runner: closing the frame detaches, only explicit cancel stops the job.

Then: the consent store against these boundaries (approvals written only by Wicket's UI, `notApproved` thrown before any session starts, fails closed on missing or corrupt approvals, rollback is activating a retained approved revision), deleting `extensionCommandsInPalette`; the review UI as the build job's command frame (not a pushed detail, which cannot reload after approve).

Can wait: a `Settings` field-decoding helper (before the fallback list), splitting `PaletteController` into window geometry and a coordinator (before the Extensions screen), `Diagnostics` beside `Messages` in Core, `Codable` wire types for deeplinks and MCP, empty-query sources and result-driven compactness for favorites (keystroke path: measure), an invocation context for deeplinks and MCP (their authority is not palette interaction).
