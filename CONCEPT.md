# Wicket: concept and proof-of-concept plan

> A wicket is the small door built into a big gate. Wicket is a small, fast, native macOS launcher that opens onto your whole Mac and your agents.

Status: M1 (palette) built on 2026-11-06; see "Decisions" and "Measurements" below. Everything else is a starting position to challenge, not a spec.

## The thesis

A launcher should be a tiny, very fast native core plus **one extension protocol simple enough that coding agents write extensions in seconds**. In the agent era, a large built-in feature set and a click-optimised extension store matter less than a documented, performant way to extend. The launcher can even write its own extensions using the coding agent the user already has (Codex CLI on a ChatGPT subscription, or Claude Code).

## Vision v2: the AI-era command surface (brainstorm, 2026-11-06)

The owner's direction after M1, captured before the architecture is reworked around it. "Launcher" undersells it: the question is what the most integral piece of the OS looks like once AI agents exist. Nothing here is decided yet; the advisor round and a design memo come next.

- **Many first-class features, not just apps.** App launching is one of several: local file search, a smart calculator (natural-language input, unit and currency conversion with current exchange rates, AI fallback for questions it can't compute), AI chat and quick answers, MCP tools, and extensions. Pick the best of Raycast and Alfred, kept clean, fast and intuitive.
- **Levelled extensions.**
  1. No UI: return one result instantly (an answer, a copyable value, an action).
  2. Pick from fixed native layouts (list, detail, grid, form), Raycast-style.
  3. Later: genuinely custom UIs that still follow Wicket's design language.
- **Extensions by prompt, self-extending like the Pi agent harness.** Software is now personal: people write single-user SwiftUI apps with agents. Wicket's built-in AI knows Wicket's own extension system, writes new extensions when asked, and hot-reloads them, so "add a feature" is a sentence. Open question: does the user ever need to see an extensions directory, or is it an implementation detail the agent manages?
- **AI at the core, not bolted on.** Which providers, subscriptions and API keys to support (agent CLIs on existing subscriptions such as Codex and Claude Code, API keys, on-device Apple Foundation Models), and what AI can do here: chat, quick answers, acting on selected text, building extensions, routing a request to the right feature.
- **Voice.** Summon with the hotkey and, if no key is typed, just speak: on-device transcription (macOS 26 SpeechAnalyzer) turns speech into the query, and the AI can answer aloud. Everything AI and voice related must be switchable and customisable.
- **Release style.** Work on `main`; publish early as an alpha (0.0.x) once it's worth showing.

## Why build it (research summary, November 2026)

- **Commercial market.** Raycast 2.0 (Aug 2026) rewrote the app around WebViews plus Node. Power users complain about memory, process count and AI being pushed, and in Sept 2026 AI moved to credits with bring-your-own-key behind Pro ($10/mo). Alfred is one-time paid, steady but slow; Alfred 6 (native workflow UIs) is still in closed beta as of November 2026. Monarch is a solo-dev, pre-1.0, one-time-paid app.
- **Apple.** Spotlight on macOS 26 Tahoe added actions via App Intents, quick keys, clipboard history and Shortcuts. The casual tier is gone; a new launcher has to win on depth, speed and taste for keyboard-heavy users. macOS 27 mainly adds Siri chat to Spotlight.
- **Open source.**
  - **Tinycast** (github.com/abue-ammar/tinycast) is native Swift 6, AGPL-3.0, macOS 26+, 9k stars since June 2026, and mostly one author. It is excellent but feature-in-core: of about 132k Swift lines, roughly 24k are launcher core and the rest is around 30 built-in features (AI 21k, Raycast compatibility runtime 14.5k Swift plus 11k JS, calculator 9.6k, window management 9k). The author plans to remove Raycast compatibility once a native plugin system exists (issue #1397). It has no App Intents, and Alfred import, contextual "act on selection" (#1323) and non-US keyboard layouts are explicitly not planned (docs/not-planned.md).
  - **Vicinae** (github.com/vicinaehq/vicinae) is C++/Qt, GPL-3.0 and cross-platform, with Raycast extension compatibility; it has run on macOS since July 2026.
  - Nobody runs Alfred workflows outside Alfred.
- **Our gap.** Small core, agent-native extensibility, MCP in both directions, and OS-level AI actions such as acting on selected text. Tinycast is a great launcher but deliberately not this.

## Principles

1. **The core stays small.** Target 15 to 25k lines for the core at maturity. A feature belongs in the core only if it needs deep OS integration or must be instant; everything else is an extension.
2. **Speed is a feature, and we measure it.** Hotkey-to-visible latency, keystroke-to-results latency and idle memory (including helper processes) are tracked from day one and compared against Tinycast.
3. **One protocol, documented for agents.** One page of docs plus a JSON schema, so an agent with no other context can write a working extension in any language.
4. **Native UI only.** Extensions send data; Wicket draws it with AppKit and SwiftUI. No WebViews.
5. **Bring your own intelligence.** No accounts, no telemetry, no hosted AI. AI features call the user's local agent CLIs or their own API keys.
6. **The settings file never grants consent.** Agents and people edit `settings.json`, so anything that amounts to a permission (auto-paste, keystroke listening, exposing an MCP server, enabling a downloaded extension) is only switched on through the UI, never by the file or a backup import. Lesson from Tinycast's settings import.
7. **Simple over clever.** Fewer settings, fewer special cases.
8. **Use the newest Apple frameworks.** Prefer the latest SwiftUI, AppKit and system APIs (Liquid Glass, Observation, Swift Testing, App Intents) over hand-written equivalents: less code, and Apple's implementations are usually well optimised. Drop to older APIs (Carbon, AppKit) only where no modern one does the job, and say why in a comment.

## Architecture sketch (to validate in the PoC)

- **App shell:** Swift 6, AppKit `NSPanel` (non-activating, floating) hosting SwiftUI, running as an agent app (`LSUIElement`). Global hotkey via `RegisterEventHotKey` or a modern equivalent.
- **Core features:**
  - App search (scan of fixed application folders, refreshed by FSEvents, with an in-memory index; see Decisions)
  - File search via the Spotlight index
  - Fuzzy ranking with usage frecency
  - Clipboard history
  - Snippets (maybe; decide whether it belongs in the core)
- **Extension protocol v0:**
  - An extension is a folder with a manifest (for example `wicket.json`: id, name, commands, keyword, icon) and an executable.
  - The host talks to it over newline-delimited JSON on stdin/stdout.
  - Host to extension: `query` (text), `action` (item id, action id), `cancel`.
  - Extension to host: `list` (items with title, subtitle, icon, accessories and actions), `detail` (markdown), `form` (fields), `toast`, `copy`, `paste`, `open`, `close`.
  - Two run modes: **one-shot** (spawned per query, Alfred script-filter style, simplest) and **persistent** (a long-lived process for stateful or streaming extensions).
  - Hot reload via FSEvents.
  - Alfred Script Filter JSON is close enough to one-shot mode that a compatibility adapter may come almost free later.
- **"Make me a command":** a built-in command takes a description, creates an extension folder, runs the user's agent CLI (`codex exec` first, `claude -p` as an option) with the protocol docs as context, then hot-reloads and opens the result. Errors go back to the agent for a retry.
- **MCP client:** configured MCP servers' tools appear as launcher actions. Arguments come from a form generated from the tool's JSON schema, and the result is shown as a detail view. This works well for actions and less well for browsing UIs; accept that.
- **MCP server:** Wicket exposes its core (clipboard history, snippets, run an extension command, open things) so the user's agents can use it.
- **Selection AI actions:** read the selected text via the Accessibility API (with a copy fallback), let the user pick a prompt (each prompt is an extension), run it, then replace or paste the result.
- **Agent quick-start:** start a Codex or Claude session in a chosen project folder, with a prompt, from the launcher.

## Proof-of-concept plan

The goal is to test the core bet, that agent-written extensions plus MCP replace a big extension store, while proving the core can be faster and lighter than Tinycast. Each milestone ends in something usable.

1. **M1 Palette.** App shell, hotkey, panel, app search with fuzzy ranking, and launching apps. Measure hotkey-to-visible time and idle memory.
2. **M2 Extension protocol v0.** Manifest, one-shot and persistent modes, list and detail views, actions, hot reload. Write `docs/extensions.md` (agent-facing, one page) plus a JSON schema. Ship 2 to 3 sample extensions in different languages (shell, Python, Swift or TypeScript).
3. **M3 "Make me a command".** Generate an extension from a description through the Codex CLI and hot-load it. Test it on 5 realistic requests and record how many work first try.
4. **M4 Selection action.** One AI action on selected text, replacing or pasting the result.
5. **M5 MCP.** Client (tools as actions) and minimal server.
6. **Evaluate.** Use Wicket and Tinycast side by side for a few days. Go/no-go is decided on whether agent-written extensions feel magical and whether the core is measurably as fast or faster.

Clipboard, snippets, file search and polish come after the go decision unless they are needed earlier.

## Reference policy

- Tinycast (AGPL-3.0) and Vicinae (GPL-3.0) are **references, not sources**. Before committing to a non-trivial design decision (hotkey handling, panel behaviour, app indexing, text injection, Accessibility, extension rendering), check how they solved it and why. Their docs and issue trackers record many pitfalls. Tinycast's `docs/features/*.md`, `docs/not-planned.md` and `CONTRIBUTING.md` are especially useful.
- **Design first, then compare.** For each non-trivial feature we first work out our own approach from first principles. Before building, we check how Tinycast (and Vicinae if relevant) solved the same problem and ask whether our design is still the best one knowing theirs. If we have good reasons to differ, we build ours; if theirs turns out cleaner, we adopt the idea (re-implemented, never copied). Record the comparison in Decisions.
- A local clone may live in `reference/` (gitignored).
- **Do not copy code** from either project: that would force our licence to (A)GPL, and the licence is not decided yet.

## Architecture v2 (decided 2026-11-06)

From the Vision v2 brainstorm, two independent advisor memos (Claude Fable 5.1 and GPT-6 Astra, which agreed on almost everything) and the owner's calls. This supersedes the older "Architecture sketch" where they conflict.

- **One data model, two execution modes.** First-party features (apps, files, calculator, AI answers, MCP tools) and extensions produce the same items, views and actions and render through the same native code. First-party features run in-process for speed; extensions run out-of-process, so a crash never takes Wicket down. The extension wire format is the Codable encoding of the same types, so a first-party feature can move out to an extension without redesign.
- **Extension protocol:** versioned JSON-RPC 2.0 over newline-delimited stdio (stdout for protocol, stderr for bounded diagnostics). Requests carry query revisions; late output is dropped. One session model: a command can answer and exit, interactive extensions stay alive while used and are reaped after a short idle timeout. Never spawn every extension on every keystroke. Per-extension memory goes in the perf log from day one.
- **UI levels:** 1 a single answer or action; 2 fixed native layouts (list and detail first, grid and form later); 3 later, a declarative tree of Wicket's own components rendered natively in the design language. Never load generated SwiftUI bundles into the process.
- **Trust: full freedom (owner's call).** Extensions can be any executable or script (shell, Python, JavaScript, Swift, ...) and run with the user's permissions, the same trust as the coding agent that wrote them. Protection is review-before-enable (summary, file list, declared capabilities), staged revisions with rollback, and never auto-enabling downloaded extensions. A sandboxed mode (for example constrained JavaScript) can be added later as a separate work mode, if sharing extensions with strangers becomes a thing.
- **Self-extension:** the built-in agent writes into a staging revision with the one-page docs, the JSON schema and samples; a host-owned checker (a `wicket` CLI in the app bundle that validates manifests, runs fixture queries and checks output against the schema) gates going live; install is an atomic switch with rollback; failures get "Fix with agent" with the diagnostics attached. Extensions live under Application Support, are revealable in Finder, and are managed from an Extensions screen (edit by prompt, disable, repair, roll back, export).
- **Agent runtime:** the user's existing coding agents through their machine interfaces: Codex `app-server` first, Claude Code's stream-json next, on the user's own subscriptions, one adapter each with pinned, tested versions. No agent loop of our own until needed. API keys (Keychain) for direct quick answers later. Apple Foundation Models only for small bounded jobs (routing, extraction, rewriting), never for writing code.
- **AI never sits on the keystroke path.** Deterministic results (commands, calculations, local matches) answer instantly; "Ask AI" is a deliberate fallback row, and partial queries are never sent to a cloud model. Natural-language maths: AI may propose an expression, the deterministic engine evaluates it.
- **Ranking across sources:** host-owned relevance classes (exact, answer, match, fallback) instead of comparing arbitrary per-source scores; selection is preserved by item id, so a late result never changes what Return runs.
- **Compact by default (owner's call, 2026-11-06).** Summoning shows only the search pill; results, answers and views expand below it only when there is something to show, and collapse again when the query is cleared. Wicket is AI-native: doing things (asking, speaking, running commands) comes first, browsing a list of apps second. The pill also carries state (idle, listening, thinking). Showing results on an empty query may come back later as an option.
- **Voice: speak on summon (owner's call).** Summon, then type or talk; no extra trigger. If no key is pressed within a short grace period after the palette appears, Wicket starts on-device transcription (SpeechAnalyzer/SpeechTranscriber) and shows a listening state; the first keystroke stops listening and discards audio. The grace period is tuned against measured mic start-up time, so fast typists never open the microphone. Partial transcripts update the query but never execute actions. Spoken answers via AVSpeechSynthesizer, mic released while speaking. All switchable in settings.
- **0.0.1 alpha scope:** result sources; apps, Spotlight file search, calculator with currency; extension runtime with answer, list and detail plus two or three useful samples; "make a command" via Codex; quick AI answers; settings file; signed build and Homebrew cask. Next: voice, MCP client and server, grid and form, level 3 UI, chat history.

## Decisions

- **App icon:** the approved warm ivory open doorway on graphite. `Resources/AppIcon-master.png` is the unmasked 1024px source; `Resources/AppIcon.icns` is the static macOS export with all standard/Retina sizes, an 824px continuous rounded tile and 100px transparent margins on its 1024px canvas. The bundling script copies it and `CFBundleIconFile` selects it. The padding belongs only to the static export, not to future Icon Composer layers.

- **Extension protocol v1 accepted (2026-11-06)**, spec in `docs/extensions.md` and `docs/extension.schema.json`. Two methods only: `run` (request) and `cancel` (notification); no `initialize` or `shutdown` handshake (the protocol version is in the manifest, context comes in environment variables, shutdown is stdin close then SIGTERM then SIGKILL, as in MCP's stdio rules). Command modes `once`, `live` and `root` (with a `pattern` regex so root extensions aren't woken for unrelated typing). Results: `answer`, `list`, `detail`, `close`, `reload`. Actions: `open`, `copy`, `paste`, `detail`, `run`. A clean exit with unanswered requests means "restart me", which unifies one-shot scripts and persistent processes in one session model. Validated with a schema, replayed fixtures, and a fresh agent that built a working extension from the page alone. Lead's calls on its open questions: secrets declared in the manifest, stored in the Keychain, passed as environment variables (v1); `session.jsonl` fixtures are the checker's format; the host warns when `python3` is the Command Line Tools stub; streaming, cached root items and list sections come later. The `Item` model gains wire-friendly decoding (defaults for optional fields, `score` host-only) and the new action cases.
- **Extension runtime built (2026-11-06).** A `WicketHost` library holds the process session (an actor per extension), the login-shell PATH, the Keychain and the checker, shared by the app and the `wicket` tool, so `wicket check` runs extensions exactly as the app does. The tool lives at `Wicket.app/Contents/Helpers/wicket`, because `Contents/MacOS/wicket` collides with `Contents/MacOS/Wicket` on case-insensitive volumes. Fixture `expect` lines match as patterns (fields left out aren't checked), so date-dependent answers stay testable. Every declared secret is required; secrets live in the login keychain as one generic password per extension and name, and `wicket secret set` stores them until the Extensions screen exists. The app tolerates protocol slips that don't lose an answer (a stray stdout line is recorded, not fatal); the checker fails on them. Extension data lives in `Application Support/Wicket/ExtensionData/<id>`, outside the watched extensions folder. Pipes are read with readability handlers: `FileHandle.bytes` held back pipe output and blocked cooperative threads.
- **Process lifecycle rules (2026-11-06, refactor step 5).** No resend of anything that may have changed state: when a process exits cleanly after answering something, its unanswered queries (search text for root, live and once commands) go to a fresh process, but a command run by an item's `run` action fails with "actions are never resent", since it may already have written files or called an API. The wire request doesn't say which is which, so the caller passes a host-side `RequestKind` (`.query` or `.action`) with every request; the checker's fixtures and `wicket run` without `--args` are queries. Queries are not capped at one resend: each resend needs the previous process to have answered something, so it always ends, and a one-shot script with several overlapping keystrokes needs one per request. Every way of giving up on a process escalates to SIGKILL (stdin close or an overlong stdout line, then SIGTERM, then SIGKILL after the grace period). A stopped session refuses new requests, so a caller holding an old session can never restart it. `Extensions` (discovery, sessions, replacement) moved from the app into WicketHost; the app only feeds it folder changes. Replacing an extension's session (its folder changed or went away) chains the old session's shutdown, and the next session for that id starts only after it, so two processes never share its data directory. An agent run whose CLI closed stdout without a final event waits up to 2 s for its exit, then kills the tree without waiting on the live process.
- **Agent adapters built (2026-11-06).** `Agent` in WicketHost runs `codex` or `claude` (found on the login-shell PATH) with a prompt, a working directory and a mode: `answer` (no tools) or `build` (edit the working directory, run sandboxed commands, no network). It returns an `AsyncStream` of text deltas and one-line activity summaries, ending with one answer (with token usage) or one error. Ending the stream SIGKILLs the whole process tree, stopping each process before listing its children, because Codex runs commands in their own sessions. Codex runs through `app-server` (JSON-RPC over stdio), not `exec --json`: it costs no more for these one-shot runs (one ephemeral thread and turn, about 0.2 s setup), and it gives typed items, token usage, a sandbox policy per turn and approvals as requests. The approval policy is `never`, and anything Codex still asks is refused. Claude Code runs `-p` with stream-json output and the prompt on stdin. Status (`wicket agent status`) is `--version` plus `codex login status` or `claude auth status`, taking 20 to 150 ms with no model call. Check it before a run: a logged-out Codex retries for about 17 s before failing. Tested with Codex 0.167 and Claude Code 2.1; another major.minor still runs, with an "untested version" warning. Safety: Codex runs ephemeral threads in a `read-only` (answer) or `workspace-write` sandbox with network off (build). `-c` overrides switch off hooks, notify, plugins, apps, browser and computer use, sub-agents, memories, web search and every MCP server in the user's config (listed in-band with `config/read`, then disabled per thread). Answer runs also drop the shell and the code-mode host, and a short answer prompt replaces Codex's agent prompt. Claude gets `--safe-mode` (no CLAUDE.md, hooks, plugins, skills or MCP), `--strict-mcp-config`, `--no-session-persistence` and `--permission-prompts none`. Answer runs get `--tools ""`. Build runs get `--restricted` (file tools confined to the folder, settings files ignored) plus Claude's Bash sandbox without the unsandboxed fallback. One test run per CLI confirmed it: a shell `touch ../x` from the folder fails with "Operation not permitted". Remaining exposure: commands in both sandboxes can read the whole disk and write to temp folders. Codex still loads the global `~/.codex/AGENTS.md` and the user's model settings. Claude leaves a `.claude/` folder in the working directory, which must be stripped before install. Claude's network block is from its sandbox documentation, not tested. Build runs have no network, so an agent can't live-test an extension that calls a web API; allowing network per build is a later call, because it widens the exfiltration risk.
- **Value model (2026-11-06, refactor step 1 of docs/architecture.md).** Commands have one identity, `CommandID` (owner `.builtin` or `.extension(id:)`, plus a name). Every extension item carries a host-stamped `origin` (the `CommandID` whose response produced it; nil for the host's own sources), set from the decoder's `WireContext`, and its id is namespaced as `ext:<extension>/<command>:<id>`, so two extensions (or two commands) sending the same id or title can't share a selection or frecency entry. `run` actions are resolved to a `CommandID` of the item's own extension at decode time; the wire still sends a bare command name. Show in Finder is a host-only `reveal(url:)` action, rejected on the wire (as the built-in `command` action was until step 4). Content (`Detail`, `RunResult`) lives in `WicketCore/Content.swift` with public initialisers; its wire decoding is in `Extension/Decoding.swift`. Provider order: extension items keep the order they were sent in within a tier and get no frecency boost (step 2 replaced the first version, which encoded list positions as descending scores).
- **Root versus list behaviour (2026-11-06, refactor step 2).** `ResultSource` moved to WicketCore. Selection (`ItemList`) is separate from root aggregation (`RootResults`: each source's items, revision checks, ranking), so a command's own list can reuse selection without root ranking. Within a tier the `Ranker` applies three policies in this order: user-ordered fallbacks (fallback items whose origin `CommandID` is in the user's list, in that order; the setting comes later, resolved through the registry), the host's own items by score plus frecency, then extension items, one block per command (sorted by extension id, then command name), each in the order sent. Host items come first because the host can judge how well its own items match the query and can't judge an extension's: an extension that answers every query must not push the app the user typed off the top row, and one that is sure uses the answer tier. Fallbacks never get a frecency boost, since a fixed menu shouldn't move. Selection rules: it follows the item id; a vanished selection stays on the same row, clamped to the last (an emptied list selects nothing), like Mail after a delete, so the highlight never jumps; truncation to the 50-row limit never drops the selected item, which takes the last row instead; only a change of query text resets it to the top, so a same-text refresh (apps changed, rates arrived) keeps it.
- **Registry and dispatcher (2026-11-06, refactor step 4).** One `CommandRegistry` (WicketCore) catalogs every invocable command: the built-ins (`BuiltinCommand`: Wicket Settings, Quit Wicket) and extension commands, keyed by `CommandID`. The root search's commands are its projection (`CommandsSource`, over the shared `SearchIndex`, a keyword matching as an alternate name; hidden and root-mode extension commands are reachable by id only); row ids stay `commands:<name>` (`commands:<extension>/<command>` for extensions) so recorded usage carries over. Built-ins are invoked like everything else, by a `run` action naming their `CommandID`; `Item.Action.command(id:)` is gone, and since the decoder resolves a wire `run` against the sender's own extension, only the host can name a built-in (and an extension entry with a built-in id is ignored). Keyword collisions: a built-in always keeps its keyword (what Wicket ships must behave the same on every Mac); among extensions the first in registry order (extension id, then manifest order) wins, so the winner never depends on install or load order; losers stay searchable and runnable by id and are listed in `keywordConflicts` for the Extensions screen; keywords match ignoring case. User aliases, when they come, are the user's explicit choice and should beat both. Extension commands are kept out of the palette by one switch (`AppDelegate.extensionCommandsInPalette = false`): they run without any approval until the consent store lands, so the app doesn't register them, and a `run` action naming one fails as "Command Not Found". `ActionRunner` became `ActionDispatcher` (WicketCore): `perform(action, context) async -> ActionOutcome` (`close(message:)`, `push(Screen)`, `reload(message:)`, `stay`), with side effects injected as `ActionEffects` (`SystemEffects` in the app), so the mapping is tested without AppKit. Open, copy, paste and reveal close; `detail` pushes; a built-in runs its effect and closes; an extension `run` goes to `Extensions.run(invocation, kind: .action)` and its result maps one to one (answer, list, detail pushed; close and reload passed on). A failure (error response, host error, a command no longer installed) is pushed as a detail titled "<command> Failed" with the error text and the command, which Return copies and Escape leaves; a cancelled run stays. `PaletteController` runs one action at a time, applies the outcome only after it is known, and hiding cancels an action still running (and so its request). The ⌘, chord runs the Settings command. The app frontmost at summon (pid and bundle id, nil if it is Wicket) is captured right after the panel is ordered front, off the hotkey-to-visible path, and passed to `paste`, which still copies until the Accessibility flow lands. Not drawn yet, both step 6 with their first producers: close and reload messages (a HUD), and pushed lists and answers (command frames; nothing can produce one while extensions are out of the palette, and one that did would log a fault). Both landed in step 6 (Extension palette integration, below), which also made the dispatcher synchronous.

Made during M1, informed by Tinycast where noted.

- **Project setup: SwiftPM plus `Scripts/build-app.sh`.** No Xcode project. `WicketCore` holds pure, Foundation-only logic (matching, ranking, usage) and is unit-tested with `swift test`; the `Wicket` executable is the AppKit shell. The script builds, assembles `build/Wicket.app` with `Resources/Info.plist` (`LSUIElement`) and signs it with the local Apple Development identity, so TCC grants (Accessibility, needed from M4) survive rebuilds. Tinycast uses XcodeGen plus a committed pbxproj because it embeds helper bundles and asset catalogs; we can revisit if we need those, and `actool` can be called from the script before that.
- **Hotkey: Carbon `RegisterEventHotKey`.** Tinycast uses the same; it is still the only public system-wide hotkey API that needs no Accessibility or Input Monitoring permission. Default ⌥Space, configurable in the settings file. The handler passes the key event's own timestamp along, so latency is measured from the keypress.
- **Settings: `~/.config/wicket/settings.json`**, plain JSON that people and agents edit by hand (`WICKET_CONFIG_DIR` overrides the folder, for tests and the benchmark). For now `{"hotkey": "option+space", "paletteWidth": 600, "ai": {"provider": "codex"}}`: the hotkey is spelled as modifiers (`cmd`, `ctrl`, `option`/`opt`/`alt`, `shift`) plus one key, joined by `+`; the width is in points, 480 to 900, applied on the next summon. A width that is not a number or out of range is ignored with a logged reason (the default stands in and the file keeps the value), since a cosmetic value shouldn't cost the whole file; an invalid hotkey still makes the file invalid. `ai.provider` (`codex` or `claude`, absent or null for the first ready one) is validated the same way. The settings window writes only what changed, merging objects key by key, so keys a build doesn't know survive inside `ai` too, and choosing Automatic removes the field. A missing file or field means defaults and the app never creates the file on its own (the settings window writes it when you change something or open it); unknown fields are ignored so newer files load in older builds; an invalid file logs an error and falls back to defaults. FSEvents on the folder reloads it live and re-registers the hotkey.
- **Extension palette integration (2026-11-06, refactor step 6, behind the switch).** A command's frame is fed by a stream: `CommandRunner.run(invocation, kind) -> AsyncThrowingStream<RunResult, Error>` (WicketCore), whose every element replaces the frame's content, the rule `ResultSource.updates` already had for root sources. `close` closes the palette; `reload` drops the frame and runs the one it was opened from again (so a command answering its own view with `reload` can't loop); a thrown error replaces the content with a failure detail ("<command> Failed", the message, the command; Return copies it), so loading and errors live in the frame, never only in a log. `Extensions` is the first producer (one element per run); a streaming AI answer is a built-in producer behind the same protocol yielding a growing `.detail`, and needs no change to frames: the frame keeps its id and generation across elements, its card content is identified by the frame id (so a replaced detail keeps its scroll position and a replaced list its selection), a detail's card height is fixed, and the pill spins until the stream ends. The dispatcher became synchronous (`ActionOutcome`: `close`, `push(Detail)`, `open(CommandRun)`): Settings and Quit run their effect, every other `run` (extension commands, and built-ins that show something) opens a frame. Opening: typing a keyword and a space in the root pushes the frame at once, the rest of the line becoming a live command's query or a once command's `text` (usually `""`; `todo buy milk` gives `buy milk` only when pasted, so a command that needs the user's words is `live`), and the root keeps the keyword for Escape back; keywords of hidden commands are ignored. An action (Return on a command row, an item's `run`) pushes a live command at once but anything else only when its first result is content, so a toggle that answers `close` never flashes a frame and a `reload` action never leaves its view; meanwhile the session is `opening` (the pill spins, other actions wait, Escape cancels). Live frames run again on every keystroke after 50 ms (a burst sends only the last text; the superseded request gets `cancel`), always as queries; once lists filter locally by title with the shared fuzzy matcher (best match first, the command's order breaking ties), never running again. Request kinds: opening a listed command without `args` is a query, the same as Return on its row; a hidden command or one given `args` is an action, never resent. A live frame with an empty query and an empty list is compact (the placeholder is the prompt); an empty list elsewhere shows "No Results"; a frame waiting for its first content keeps the card's height. An answer without actions copies its title on Return (decoded so). Messages: a `reload`'s in the footer for 2 s, a `close`'s in a small glass HUD capsule centred where the pill was, a checkmark leading, for 2 s (the leading glyph and the reading-time dwell from Tinycast's message pill; Tinycast anchors it near the screen edge, ours stays where the user was looking). Root-mode commands are one `ExtensionRootSource` (Host): after 80 ms without a newer query (like files), each command whose `pattern` matches gets the text, concurrently, and its answer or first 10 items join the root as they arrive in the provider-ordered block; failures are kept for the Extensions screen and logged without text. Tinycast has no keyword-and-space routing (its user aliases are a ranking signal), so keyword routing follows our protocol (Alfred's model). `AppDelegate.extensionCommandsInPalette` stays false until the consent store lands; it now gates both registering commands and the root source, and everything else is wired, so flipping it is the whole change. Verified end to end against the real samples (github-prs on its fixtures, quit-apps read-only, system-toggles listed only, unicode, week-number) in `PaletteIntegrationTests`.
- **Quick AI answer (2026-11-06).** The first built-in producer on the stream-fed command frames, and it needed no change to them: only the router step 6 anticipated (`CommandRouter`, Core: built-ins by `CommandID`, extension commands to `Extensions`). Ask AI is a hidden built-in command (`ask-ai`, once) that the root offers as a static fallback row ("Ask AI", the query as its subtitle, `sparkles`) for any non-empty query; nothing runs until it is picked, so AI stays off the keystroke path. The row's `run` carries the question as its `prompt` argument. Fallbacks get no frecency (and record none), so the row is always last unless the user's fallback order (by its origin, `ask-ai`) says otherwise. `ai <question>` asks only the question and lifts the row to the top (exact tier). That prefix lives in the source, not the registry: a registry keyword opens its frame as soon as the space is typed, and both frame modes are wrong for a question (a once frame runs on the empty text, a live one sends partial queries to the model); so an extension keyword `ai` would win over it, which is acceptable while extensions are off. `AskAIRunner` (Host) checks the provider before each run, never at launch: `ai.provider` from settings (a preference, not consent), else the first ready one, Codex first; a provider found ready is trusted for 60 s, one that isn't is checked every time so signing in works at once, and a failed run drops the trust. A chosen provider that isn't ready is reported, never swapped for another (Tinycast's rule too). Not installed or signed out ends the run with a failure detail saying what to type in Terminal, instead of Codex's 17 s of retries. The frame opens with the question as its title (the pill shows it) and "Asking Codex…" (or the latest activity) until text arrives; deltas append to the markdown, at most about 30 updates a second (a throttle in the runner: the first at once, the rest at the interval's end, the final answer always), and the final message replaces what streamed. Its actions are Copy Answer and Paste Answer (which copies until paste is synthesised); "Continue in Codex" is skipped, since answer runs are ephemeral and there is no session to continue. Errors become the frame's failure; pop and dismiss end the stream, which kills the agent's process tree. The detail keeps its scroll position as it grows (its card content is keyed by the frame's id and the frame keeps its id); Tinycast's Quick AI instead pins a streaming reply to its end until the reader scrolls up, which suits a chat transcript more than a short answer, so we start at the top. Tinycast also asks with Tab from the launcher; that stays an option for later. The answer prompt (`Agent.answerInstructions`) now says to start with the answer, no preamble or closing offers, and that Markdown renders. Settings ▸ AI picks the provider and shows each one's status (ready with its version, signed out with the login command, not installed), checked when the pane opens. `AgentProvider` moved to WicketCore so settings can validate it.
- **Frames (2026-11-06, refactor step 3).** The palette is a session (`PaletteSession`, WicketCore, `@Observable`) over a stack of frames, the root search at the bottom. A frame keeps its id, query, content (root search or a detail; a command's list in step 6), selection, load state (slow work pending) and a generation bumped by every query change; work results are applied only while their frame is on the stack at the same generation, and work is cancelled on pop, dismiss and superseding queries (a pushed frame doesn't stop the root's slow search). Escape clears the text, else pops, else hides; Return, ⌘↩, ⌘K and ⌘1 to ⌘9 act on the top frame (a detail's own actions; without any, Return copies the markdown as docs/extensions.md says). Dismissing resets to an empty root. The pill's glyph and prompt follow the frame (a detail shows its title). Compactness follows the frame: only the root with an empty query collapses to the pill. A detail takes the tallest card (384 pt), since its height would have to be measured; pushing and popping resize at once, the 300 ms shrink delay is for result churn within a frame. The detail view is the first non-list screen: markdown split into blocks in Core (`MarkdownBlock`, from `AttributedString(markdown:)` with full syntax: headings, paragraphs, nested lists, code, quotes, tables, rules), since SwiftUI's `Text` draws only inline styles and runs blocks together; metadata in a 180 pt column beside it; the text is selectable. A `detail` action pushes instead of hiding (an outcome of the dispatcher since step 4).
- **Settings window: the file stays the truth.** An AppKit `NSWindow` with toolbar tabs (`NSTabViewController`), one SwiftUI `Form` pane per tab, because SwiftUI's `Settings` scene needs a SwiftUI `App` lifecycle and Wicket has an AppKit main. Opened by the "Wicket Settings" command or ⌘, in the palette; Wicket becomes a regular app (Dock, ⌘-Tab) while it is open and an accessory again on close, as Tinycast does. The window only reads what the app applied and writes `settings.json` through `Settings.update` (read the object, change only the fields that changed, keep unknown keys, sorted pretty JSON, atomic; an invalid file is reported, never overwritten); the FileWatcher reload then applies it, so there is no second path into the app's state. The hotkey recorder uses a local key monitor for raw key codes and pauses the global hotkey while recording; a combination needs ⌘, ⌃ or ⌥ unless it is an F-key. Launch at login is `SMAppService.mainApp` only, never mirrored into the file, since the system owns it. Panes: General and AI (since Ask AI); more panes are more tabs.
- **Main menu (2026-11-06).** A standard menu built once in AppKit at launch (`MainMenu`): Wicket (About, Settings… ⌘,, Hide ⌘H, Quit ⌘Q), Edit (Undo, Redo, Cut, Copy, Paste, Select All) and Window (Close ⌘W, Minimize ⌘M; the settings window became miniaturizable), every item sent to the first responder. macOS shows it only while the settings window makes Wicket a regular app, so it adds nothing to the accessory app. The palette never lets it act: AppKit offers a ⌘ key to the key window's `performKeyEquivalent`, then to the main menu, and only then to the window's `sendEvent` (checked in-process), so `PalettePanel` claims its chords there (the menu binds ⌘, too), sends editing shortcuts (`EditCommand`, Core) to the field itself, and swallows any other key the menu binds. ⌘Q in the palette does nothing, as before the menu and as in Spotlight and Raycast: a launcher dismissed by reflex shouldn't quit; the Quit command quits. Tinycast binds ⌘Q to Close Window even in its settings, so a reflexive ⌘Q there can't kill the launcher; we keep the platform's Quit, since the user opened the window on purpose and the menu says what ⌘Q does. Tinycast declares its menu as SwiftUI `Commands` (it has a SwiftUI `App`); with an AppKit main, an `NSMenu` built once is the whole job.
- **Panel:** borderless `NSPanel` with `.nonactivatingPanel`, `canBecomeKey`, floating level, joins all Spaces and full-screen apps, no window animation. It takes the keyboard without activating Wicket, so the previous app keeps focus when the palette closes. The controller sets the frame (its height follows the card, see the compact pill) and SwiftUI never drives it (`sizingOptions = []`): Tinycast documents top-edge drift when it did. Everything inside the panel is SwiftUI: a `TextField` with `@FocusState` and `onKeyPress` for ↑ ↓ ↩ ⎋, and a `LazyVStack` of results. An AppKit `NSTextField` variant (Tinycast's choice, for key chords SwiftUI misses) measured the same, so the SwiftUI version won on less code. Standard editing shortcuts are routed in the panel itself, since the main menu exists for the settings window and never acts from the palette.
- **App discovery: fixed folders, not `NSMetadataQuery`.** We scan `/Applications`, `/System/Applications`, their `Utilities`, `~/Applications`, CoreServices/Applications, Finder and the Safari cryptex (`/System/Volumes/Preboot/Cryptexes/App/System/Applications`; `/Applications/Safari.app` is a hidden symlink), one vendor subfolder deep, plus apps embedded in apps (Simulator in Xcode). It takes about 40 ms for about 160 apps, off the main thread, and FSEvents triggers a debounced rescan. A Spotlight query depends on indexing being on and returns copies in Downloads, build folders and disk images. Tinycast reached the same design; it also warns against filtering CoreServices by `LSUIElement`, which hides real apps.
- **Ranking:** our own subsequence matcher (word-start and run bonuses, flat gap penalty, prefix and exact bonuses, weak scattered hits rejected), matched against the displayed name and the file name (so English names work on a localised system). Frecency (half-life 7 days, `~/Library/Application Support/Wicket/usage.json`) adds a capped boost: it breaks close calls but never beats an exact match. Ranking about 160 apps takes well under a millisecond, so it runs synchronously per keystroke.
- **Result sources.** Every feature feeds the palette through a `ResultSource`: a synchronous, memory-only `instant(query)` called on every keystroke, plus optional `updates(query)`, an `AsyncStream` for slow sources (files, extensions) whose elements replace that source's earlier results and whose cancellation stops the work. Sources return `Item`s (namespaced stable id such as `apps:/Applications/Safari.app`, title, subtitle, icon, accessory, relevance, score, actions; Codable, so extensions can send the same shape). The host owns ranking: relevance tiers in order exact (title or alias), answer (computed, e.g. calculator), match (fuzzy), fallback (e.g. Ask AI), then match score plus frecency within a tier. Each query has a revision and late updates for an older one are dropped; the selection follows its item id, so a late result never changes what Return runs. The first action is primary and one dispatcher (`ActionDispatcher`) performs every action and returns what the palette does next. Apps and commands are memory-only sources over a shared `SearchIndex`; search plus merge over 160 apps takes about 0.3 ms in release.
- **Files: Spotlight through MDQuery, not our own index.** `FilesSource` is the first async source: from 2 typed characters and after an 80 ms debounce it runs an MDQuery for every query word as a word prefix of the file name (`kMDItemFSName == "word*"cdw`, case and diacritic insensitive; Spotlight's word mode splits at punctuation and camelCase). Word mode answers in about 30 ms where a substring match (`*word*`) took 100 to 1000 ms. MDQuery over `NSMetadataQuery` because it caps hits inside Spotlight, runs and notifies on our own serial queue rather than a run loop, and `MDQueryStop` ends it when the stream terminates. Spotlight applies the cap before sorting, so we take an arbitrary 500 hits and let the shared fuzzy matcher pick the best 20 by file name, minus a fixed penalty of one prefix bonus (10) so an app or command matching about as well ranks above a file. Scopes are each visible folder in home (so Spotlight never walks `~/Library`; loose files directly in home are missed), iCloud Drive, `~/Library/CloudStorage` and volumes under `/Volumes`; hidden paths, `node_modules`, `build`, `DerivedData`, `Pods`, caches and the insides of apps and photo libraries are dropped (`FileSearch` in WicketCore), and apps are left to `AppsSource`. Tinycast instead crawls its own filename index in a helper process kept current by FSEvents, which needs Full Disk Access and thousands of lines, and in exchange searches by substring, works with indexing off and sees hidden and ignored files. Spotlight already maintains that index for free, so we keep it and took Tinycast's ignore defaults and its rule that files never outrank an equal app match.
- **Look: SwiftUI `.glassEffect` with a tint**, clipped to the rounded shape. On an idle Mac it measured within about 1 ms of a plain `NSVisualEffectView`; the 12 ms gap seen earlier came from a busy machine.
- **Calculator engine (`WicketCore/Calculator`).** `Calculator.evaluate(text, rates:, defaultCurrency:, locale:)` is pure and synchronous: input without a digit or with an unknown word returns nil in about 60 ns, and a real calculation takes about 5 µs (release). It is one precedence-climbing parser over typed values (number, percent, Foundation `Dimension`, ISO currency), with `in`/`to`/`as` conversion as part of the grammar. Units convert through `Measurement`, and their symbols and English names come from Foundation, so the hand table only lists extra spellings. Foundation rounds some factors (pound 0.453592 kg, km/h 0.277778 m/s, US volumes), so those few units use their exact legal definitions. `cups` is the US cup, not Foundation's 240 mL metric cup. Input follows the locale: its decimal separator, and its grouping separator only as valid thousands grouping. A point that can't be grouping is a decimal point everywhere (`2.5`, `1.2345` on a German Mac), while valid grouping follows the locale (`1.234` is 1234 in German); anything else ambiguous (`2,5` in English) gives no answer rather than a guess. Where the comma is the decimal point, `round(3,2)` is round(3.2), so arguments are separated by `;` (any locale) or a comma and a space. Output follows the locale with about six significant digits, more if the input typed more, and never rounding away whole digits; integers stay exact. Trigonometry and subtraction snap rounding noise to 0 (`sin(2pi)`, `1 - 0.9 - 0.1`). The copy value is the bare number with no grouping, to 15 significant digits. Rates are an injected `ExchangeRates` from the ECB daily feed (about 30 currencies against EUR), cached as raw XML in `~/Library/Caches/Wicket/` and fetched once the cache is a day old, by `ExchangeRateStore` on an ephemeral session. Results carry the rates' day, and with no rates a currency query says so.
- **Calculator versus Tinycast.** Tinycast's calculator is about 9.6k lines covering dates, time zones, finance phrases, derived units and generated CLDR currency tables. Our first version keeps the core grammar and borrows these ideas from it: a lone amount already in your default currency converts to USD (EUR for dollars); `+`/`-` answer in the last unit typed while a composite (`3 ft 2 in`) answers in its leading one; absolute temperatures add only on the same scale; a trailing operator answers the prefix; money widens below a cent; and invalid grouping is rejected rather than guessed. We differ in using Foundation's unit names and `Locale.Currency.isoCurrencies` plus eight signs instead of generated tables, and in caching the feed's XML as is. Natural-language phrases, dates and derived units can become extensions.
- **Calculator in the palette.** `CalculatorSource` gives at most one row, id `calculator:answer` so the selection follows it while typing, in the answer tier: the result as title, the interpretation as subtitle, Return copies. A message (`Exchange rates unavailable`) is a row with no actions, so Return leaves the palette open. The default currency is the locale's, else USD. Answers never record frecency: `PaletteModel` skips the answer tier, since a computed row has no habit to learn. Rates start at launch and refresh the palette's results when they change.
- **Keyboard model.** ↑↓ and ⌃N/⌃P move, Return runs the primary (first) action, ⌘↩ the second, ⌘K opens the action panel, ⌘1 to ⌘9 run the first nine rows (hints replace the accessory while ⌘ is held), ⌘, opens settings, Escape clears the field's text, then goes back a frame, then closes (the panel, or the palette). Chords are matched by `PaletteChord` in `PalettePanel` (`performKeyEquivalent`, before the main menu, and `sendEvent`, before the field editor), which binds ⌃N/⌃P itself, and are always consumed; ⌘1 to ⌘9 match the number row by key code so AZERTY works (both from Tinycast). Plain keys stay with the focused field's `onKeyPress`, and Return never goes through `onSubmit`.
- **Action panel: a SwiftUI overlay in the palette, not a child window.** One optional `ActionMenu` on the model (so one panel at most) captures the item on opening, so a late result never changes what it runs; it has its own filter field, takes focus while open and hands it back to the search field on every close, and a click outside closes it. A footer shows the primary action with ↩ and "Actions ⌘K". Titles and icons come from one `ActionPresentation` switch, with the value shown beside generic titles ("Copy 42") until actions carry titles. Tinycast hosts its menus in a key child `NSPanel` so glass renders against the desktop and long menus aren't clipped; our menus are short, and an overlay needs no key-status hand-off around `windowDidResignKey`. Apps and files get Open, Show in Finder and Copy Path; answers get Copy Result and Copy Expression. "Open With…" is skipped: it needs a second-level app list. Show in Finder is its own host-only action, `.reveal(url:)`.
- **Compact pill (2026-11-06).** A 56 pt Liquid Glass capsule; results go in a separate glass card 8 pt below (Tahoe Spotlight's shape), and both glass shapes share one `GlassEffectContainer` so the card morphs out of the pill, with the content layered above the container so a morph never smears it (Tinycast). The card fits its content (rows, divider, footer) up to 384 pt, eight rows, so a lone answer gets a short card instead of a mostly empty one; while ⌘K is open it is at least tall enough for the action panel. The height is computed from the results (fixed row heights), not measured, so it is known before anything is laid out. It grows at once and shrinks only after 300 ms without a taller result: Spotlight file results drop and return a beat after each keystroke, and a fixed card was the earlier answer to that flicker. It appears when there are results; clearing the query collapses it at once, a query that matches nothing collapses it after the same 300 ms (no empty state; since Ask AI, any typed query has at least its fallback row). An answer at the top (a calculation, an extension's answer) is a 60 pt row with the result at 24 pt and its interpretation as the small line below: still a row, with the same selection, actions and footer, and it stays large when the selection moves so the list never reflows under the arrow keys. The controller owns the frame and the window tracks the card, so it never extends past what is drawn: the top-left anchor is resolved once per summon, a taller card resizes the window instantly and animates only the card into the transparent space, a shorter one animates first and shrinks the window in `withAnimation`'s completion (only if no newer height arrived), so AppKit and SwiftUI never animate the frame together and the pill and the card's top edge never move; layout is flushed before ordering front, and a 40 pt transparent margin leaves room for the glass rim and its own soft shadow (layout flush from Tinycast). The window draws no shadow of its own: it traced a shape that didn't match the glass and showed as a thin dark outline, and a 4 pt margin clipped the glass shadow into a faint rectangle. `PaletteMode` (idle only) gives the pill its glyph and prompt; listening and thinking become cases. No mic glyph or hotkey hint until voice exists.

## Concept challenges

- **App search should not use `NSMetadataQuery`** (changed above).
- **One-shot extensions spawned per keystroke will miss the latency target.** Interpreter start-up alone is about 30 to 80 ms (Python, Node) before any work. Recommendation for M2: debounce one-shot queries, measure spawn cost first, and make persistent mode the norm for search-as-you-type. Keep one-shot for commands that take no live query.
- **"Extensions in seconds" oversells it.** An agent CLI run takes tens of seconds to minutes. The promise is "one sentence, no code", not seconds; M3 should time it honestly.
- **Benchmarks need an idle Mac.** The external latency harness posts real keystrokes and takes over the screen, so it can't run while someone is working. In-app timings (`log stream --predicate 'subsystem == "app.wicket"'`) run all the time without that problem.
