# Wicket: concept

> A wicket is the small door built into a big gate. Wicket is a small, fast, native macOS launcher that opens onto your whole Mac and your agents.

This page holds the why: thesis, principles and the decisions with their reasons. How the code works is in [docs/architecture.md](docs/architecture.md); what is built and what comes next is in [ROADMAP.md](ROADMAP.md).

## Thesis

A launcher should be a tiny, very fast native core plus **one extension protocol simple enough that coding agents write extensions for you**. In the agent era, a large built-in feature set and a click-optimised extension store matter less than a documented, performant way to extend. Wicket can write its own extensions with the coding agent the user already has (Codex or Claude Code on their own subscription).

"Launcher" undersells it: the question is what the most integral piece of the OS looks like once agents exist. The direction (owner, 2026-11-06):

- **Many first-class features, not just apps:** files, a smart calculator, AI answers, MCP tools and extensions, the best of Raycast and Alfred kept clean, fast and intuitive.
- **Levelled extensions:** one instant result; fixed native layouts (list, detail, later grid and form); later, custom UIs in Wicket's design language.
- **Extensions by prompt:** the built-in agent knows Wicket's extension system, so "add a feature" is a sentence. Open: does the user ever need to see an extensions folder?
- **AI at the core, not bolted on:** agent CLIs on existing subscriptions, API keys, on-device models for small jobs; chat, quick answers, acting on selected text, building extensions.
- **Voice:** summon and, if no key is typed, just speak. Everything AI and voice is switchable.
- **Release style:** work on `main`; publish an early 0.0.x alpha once it's worth showing.

## The core, and nothing else for now (owner, 2026-11-08)

Get the core idea right before adding anything: **a simple, fast, AI-native launcher.** Six things:
1. **AI through the harnesses we wrap** (Claude Code, Codex), with replies drawn natively.
2. **File search.**
3. **Calculator.**
4. **App launcher.**
5. **Extensions the agent builds on request.**
6. **Voice input:** speaking instead of typing is part of the experience.

Anything else waits until these are on point. That includes new features and polish on what isn't on this list. Existing extras are judged against this list in a scope audit.

**Scope cuts (owner, 2026-11-08):**
- **Removed: prompt commands and Save as Command.** A reusable command is something you ask the agent to build, so extensions stay one concept.
- **Removed: selected-text capture.** It was paused and unreliable, and it needed Accessibility. Passing the Finder folder to the agent stays.
- **Removed: the Shortcuts pane, aliases and per-command global hotkeys,** including Start Listening's. The mic button and ⌘L remain. They come back when there's a real need.
- **Simplified: feature switches.** Only the AI and Voice switches remain, each in its own pane. The Features pane goes.
- **Simplification (owner and lead, 2026-11-08):** see docs/reviews/2026-11-08-simplify.md.
  - **Extensions:** one process per run instead of sessions, no root mode, a static `wicket check`, no rollback, and dependencies vendored instead of managed by Wicket.
  - **Agents:** the harness's own permission policy replaces Wicket's four levels; Allow once or Deny; whole messages only, so no streaming setting; no answer-only mode. The model, effort and speed pickers stay.
  - **Palette:** fixed-height documents and an explicit rerun after an extension changes.
  - **Unchanged:** consent to the exact reviewed snapshot, secrets, and process cleanup.
- **Kept:**
  - Currency and unit conversion (part of the calculator).
  - Links.
  - Text size, Follow Up, run history, and Fix and Change with Agent.
  - Settings, the updater, the menu bar item, the opening hotkey, usage ranking and the `wicket` tool.

## Why build it (research, November 2026)

- **Commercial:** Raycast 2.0 (Aug 2026) moved to WebViews plus Node; power users complain about memory, process count and AI being pushed, and AI moved to credits in Sept 2026. Alfred is steady but slow (Alfred 6 still in closed beta). Monarch is solo, pre-1.0.
- **Apple:** Spotlight on macOS 26 added actions, quick keys and clipboard history, so the casual tier is gone; a new launcher must win on depth, speed and taste for keyboard-heavy users.
- **Open source:** Tinycast (native Swift 6, AGPL-3.0, about 132k lines) is excellent but feature-in-core: about 24k lines of launcher and some 30 built-in features; no App Intents, act-on-selection and non-US layouts not planned. Vicinae (C++/Qt, GPL-3.0) is cross-platform with Raycast compatibility.
- **Our gap:** small core, agent-native extensibility, MCP in both directions, OS-level AI actions such as acting on selected text.

## Principles

1. **The core stays small.** 15 to 25k lines at maturity. A feature belongs in the core only if it needs deep OS integration or must be instant; everything else is an extension.
2. **Speed is a feature, and we measure it.** Hotkey-to-visible, keystroke-to-results and idle memory (helpers included), compared against Tinycast.
3. **One protocol, documented for agents.** One page plus a JSON schema, enough for an agent with no other context to write a working extension in any language.
4. **Native UI only.** Extensions send data; Wicket draws it with AppKit and SwiftUI. No WebViews.
5. **Bring your own intelligence.** No accounts, no telemetry, no hosted AI.
6. **The settings file never grants consent.** Agents and people edit `settings.json`, so anything that amounts to a permission (auto-paste, keystroke listening, exposing an MCP server, enabling an extension) is switched on only through Wicket's UI. Lesson from Tinycast's settings import.
7. **Simple over clever.** Fewer settings, fewer special cases.
8. **Use the newest Apple frameworks** (SwiftUI, Observation, Liquid Glass, Swift Testing, App Intents) over hand-written code; drop to older APIs only where nothing modern works, with a comment saying why.

## Reference policy

- Tinycast (AGPL-3.0) and Vicinae (GPL-3.0) are **references, not sources**. Their docs and issue trackers record many pitfalls (Tinycast's `docs/features/*.md`, `docs/not-planned.md`, `CONTRIBUTING.md`). A local clone may live in `reference/` (gitignored).
- **Design first, then compare.** Work out our own approach, then check theirs before building; if theirs is cleaner, adopt the idea, re-implemented. Record the comparison in a decision below.
- **Never copy code:** it would force our licence to (A)GPL, and the licence is undecided.

## Architecture (decided 2026-11-06)

From two independent advisor memos (Claude Fable 5.1, GPT-6 Astra) and the owner's calls; later architecture reviews kept it.

- **One data model, two execution modes.** Built-in features and extensions produce the same items, screens and actions and render through the same native views. Built-ins run in-process for speed; extensions run out-of-process, so a crash never takes Wicket down. The wire format encodes the same types, so a feature can move out to an extension without redesign.
- **Extension protocol:** versioned JSON-RPC 2.0 over newline-delimited stdio. Requests carry revisions and late answers are dropped. One session model: a process can answer and exit or stay alive, and is reaped when idle; never spawn every extension on every keystroke.
- **UI levels:** an answer; fixed native layouts (list and detail now, grid and form later); later a declarative tree of Wicket's own components. Never load generated SwiftUI bundles into the process.
- **Trust: full freedom (owner's call).** Extensions are any executable and run with the user's permissions, the same trust as the agent that wrote them. Protection is review before enable, staged revisions with rollback, and never auto-enabling downloads. A sandboxed mode can come later if extensions are shared with strangers.
- **Self-extension:** the user's acting agent writes the extension in the extensions folder, guided by the docs; the host-owned checker gates enabling it on Wicket's review; rollback is a retained revision; failures get "Fix with agent", which continues the conversation that built it (2026-11-08, see AI).
- **Agent runtime:** the user's coding agents through their machine interfaces (Codex `app-server`, Claude Code stream-json), one adapter each. No agent loop of our own until needed; API keys later; Apple Foundation Models only for small bounded jobs, never for writing code.
- **AI never sits on the keystroke path.** Deterministic results answer instantly; Run Agent is a deliberate row, and partial queries never go to a model. For natural-language maths, AI may propose an expression; the deterministic engine evaluates it.
- **Ranking across sources:** host-owned relevance tiers instead of comparing arbitrary per-source scores; the highlight stays on the top row until the user moves it (the best result is always the one highlighted), then follows its item, so a late result never changes a row the user chose.
- **Compact by default (owner's call).** Summoning shows only the search pill; a card expands when there is something to show. Doing things (asking, speaking, running) comes first, browsing apps second. Results on an empty query may return as an option.
- **Voice: speak on summon (owner's call).** On-device transcription arms quietly on open; the first keystroke stops it and discards what was heard, so typing is never interrupted (see Voice). Partial transcripts never execute anything.
- **0.0.1 alpha scope:** apps, files, calculator with currency; extensions with answer, list and detail plus useful samples; commands built by asking the AI; quick AI answers; settings; signed build and Homebrew cask. Next: voice, MCP client and server, grid and form, level 3 UI.

## Decisions

Each is the call and its reason; the mechanism is in docs/architecture.md. All dated 2026-11-06 unless noted.

### Shell and look

- **SwiftPM plus `Scripts/build-app.sh`, no Xcode project.** Less to maintain; the script signs with the local Development identity so TCC grants survive rebuilds. Tinycast needs XcodeGen for embedded bundles and asset catalogs; revisit if we do.
- **Minimum macOS 26.** Simplest: the newest APIs (Liquid Glass, `glassEffect`) without fallbacks.
- **Hotkey: Carbon `RegisterEventHotKey`**, default ⌥Space. Still the only public system-wide hotkey API that needs no Accessibility or Input Monitoring permission (Tinycast agrees).
- **Panel: non-activating `NSPanel` hosting SwiftUI.** It takes the keyboard without activating Wicket, so the previous app keeps focus. The controller owns the window frame, never SwiftUI: Tinycast documents top-edge drift when SwiftUI drove it. An AppKit text field (Tinycast's choice) measured the same as SwiftUI's, so SwiftUI won on less code.
- **Look: SwiftUI `.glassEffect`.** Measured within about 1 ms of `NSVisualEffectView`. A pill with a separate card below (Tahoe Spotlight's shape) that morphs out of it. The card fits its content and grows at once but shrinks only after 300 ms, because Spotlight results drop and return a beat after each keystroke. The window draws no shadow: it traced a shape that didn't match the glass.
- **Follow Apple's interface guidelines over custom styling (owner, 2026-11-07).** Nested shapes are concentric by construction: a selection's radius is its container's minus the inset (card 22, inset 10, row 12), the same on every row; `ConcentricRectangle`'s per-corner radii made the top row lopsided. Rows are one line (subtitle beside the title, middle-truncated), so every row is the same height, and the card holds whole rows, never half of one. Compared side by side with Raycast on screen (2026-11-07), without copying its look.
- **Action panel: an overlay in the palette, not a child window.** Most menus are short, and an overlay needs no key-status hand-off; a long one scrolls inside the card instead. Tinycast uses a child panel so long menus aren't clipped.
- **Keyboard model:** Return, ⌘↩, ⌘K, ⌘1 to ⌘9, ⌃N/⌃P, Escape goes back. ⌘1 to ⌘9 match the number row by key code so AZERTY works (from Tinycast).
- **Escape goes up one layer; repeated presses close (owner, 2026-11-08).** Reverses "Escape closes from any depth; ⌘[ goes back" from the same day: in a pushed page (the gallery extension) the owner found no visible way back, since ⌘[ is a key nobody guesses. Raycast's model: Escape closes the action panel, stops listening or a command being opened, else pops the top frame whatever its text, else clears the root's text, else hides. Clearing the root's text before hiding is Raycast's default too, and a mistyped search costs one press instead of a reopen. One key for back, so ⌘[ is gone; the footer says "Back esc" in a pushed frame. The hotkey still closes from any depth.
- **Main menu only for the settings window; inert in the palette.** ⌘Q in the palette does nothing, as in Spotlight and Raycast: a launcher dismissed by reflex shouldn't quit. Tinycast rebinds ⌘Q to Close even in settings; we keep the platform's Quit there, since the user opened the window on purpose.
- **A menu bar icon, on by default (2026-11-08).** Without a Dock icon, the owner couldn't tell Wicket was running or reach Settings without the hotkey. Its menu is only Open Wicket (with the hotkey as its hint), Settings… and Quit, on the same paths as the hotkey and ⌘,. `"showInMenuBar": false` hides it: a way in, not a permission, so the file may set it; opening the app again still shows the palette. Tinycast and Raycast have the same switch; Tinycast also puts features in the menu, which we leave to the palette.
- **App icon:** the warm ivory open doorway on graphite (`Resources/AppIcon.icns`, from `AppIcon-master.png`).

### Settings

- **`~/.config/wicket/settings.json` is the truth, reloaded live.** Plain JSON that people and agents edit. The app never creates it on its own; unknown keys are kept, so newer files work in older builds.
- **Settings window writes only the file, plus the consent stores (permission levels, voice).** It reads what the app applied and writes changed fields; the reload then applies them, so there is no second path into app state. AppKit window with SwiftUI panes, because SwiftUI's `Settings` scene needs a SwiftUI `App`. Launch at login stays with the system (`SMAppService`), never mirrored into the file.
- **Features can be turned off** (`"features": {"files": false}`), keyed by source id. A feature that is off does no work at all. Commands are not a feature, since Settings and Quit live there and hiding them hides the way back. Tinycast has a flag per feature; ours is the same effect from one filter, since every source already has a stable id.

- **Page text size is one setting in named steps (owner, 2026-11-08).** `"textSize"`: small, medium (default), large, larger, body 13/15/17/19 points, with headings, code and labels scaled in proportion; small is the original look, which the owner found too small for answers. Named steps fit a picker and can't produce odd sizes. Only pages (details, Run Agent's answer) follow it; result rows keep their fixed sizes, since their height sizes the card and they were not the complaint.
- **Every field fails alone; a broken file changes nothing (2026-11-06).** A bad value, including the main hotkey, is ignored with a logged reason and its default stands. A file that isn't valid JSON (often an agent mid-write) keeps the last good settings rather than resetting everything and restarting feature work.
- **One ordered apply per snapshot (2026-11-06).** The app logic is a library (`WicketApp`) so it can be tested; settings are applied as one coherent snapshot with system side effects behind seams. A command that leaves the registry (feature off) stops its runs and the palette goes back to where it was opened, without a failure page.

### Search and ranking

- **Apps: scan fixed folders, not `NSMetadataQuery`.** About 40 ms for 160 apps, refreshed by FSEvents. Spotlight depends on indexing and returns copies in Downloads, build folders and disk images. Tinycast reached the same design.
- **Ranking: our own subsequence matcher plus frecency** (7-day half-life, capped so it breaks close calls but never beats an exact match). Under a millisecond for all apps, so it runs synchronously per keystroke.
- **Files: Spotlight (MDQuery) word-prefix search, not our own index.** Word mode answers in about 30 ms where substring took 100 to 1000 ms; Spotlight maintains the index for free. Tinycast crawls its own index in a helper, which needs Full Disk Access and thousands of lines, in exchange for substring search and hidden files. We took its ignore defaults and its rule that a file never outranks an equal app match.
- **Ordering within a tier:** fallbacks in the built-ins table's order (a fixed menu; a user-set order waits for a concrete need, 2026-11-08), then the host's items by score plus frecency, then each extension command's items in the order sent. The host can judge its own matches but not an extension's, so an extension answering everything can't push the app the user typed off the top; a sure extension uses the answer tier. Fallbacks and computed answers get no frecency, since a fixed menu shouldn't move.
- **Selection rules:** a vanished selection stays on its row (like Mail after a delete), truncation never drops the selected item, and only a change of query text resets it to the top.

### Calculator

- **Pure, synchronous engine over Foundation units.** About 5 µs per calculation, nil in about 60 ns for non-maths, so it runs on every keystroke. Unit names come from Foundation, so the hand table only adds spellings; units Foundation rounds use their exact legal definitions.
- **Locale-aware input that never guesses:** ambiguous input (`2,5` in English) gives no answer rather than a wrong one.
- **Rates from the ECB daily feed**, cached a day. Tinycast's calculator is about 9.6k lines with generated CLDR tables, dates and finance phrases; we kept the core grammar, borrowed its conversion conventions (a lone amount in your default currency converts to USD, `+`/`-` answer in the last unit, a trailing operator answers the prefix), and leave phrases and dates to extensions.

### Commands

- **One command identity (`CommandID`) for built-ins and extension commands,** so search, keywords and later deeplinks and MCP need no plumbing per kind. Extension item ids are namespaced by origin, so two extensions can't share a selection or frecency entry.
- **Only the host can name a built-in:** a wire `run` resolves against the sender's own extension.
- **Keyword collisions:** a built-in keeps its keyword (what Wicket ships behaves the same on every Mac); among extensions the first in registry order wins, so the winner never depends on install order.
- **Keyword and a space opens a command's frame** (Alfred's model). Tinycast has no keyword routing; its aliases are only a ranking signal.
- **One invocation policy for every way in (2026-11-06).** A command declares how it takes text (none, immediate, submitted, live) and whether a run may be repeated; rows, keywords, `run` actions and `wicket run` resolve through one Core function, so a command behaves the same however it is reached and the next way in (deeplinks, MCP) needs no rules of its own. It replaced six name checks for Run Agent and rules that drifted between keywords, frames, the CLI and the checker.
- **Run Agent is an ordinary submit-text command with the keyword `ai` (2026-11-06).** Submit-text is the frame mode a question needs: its keyword opens a frame that waits for Return, so it never runs on empty text or on a keystroke. As a registry keyword a built-in keeps `ai` against extensions, so an extension can no longer take Run Agent's prefix. Its root row is a generic fallback over submit-text commands, so web search will be one more registration. Supersedes "a fallback row plus an `ai ` prefix, not a keyword".
- **No Search the Web; typed addresses get a strict link row (owner, 2026-11-08).** Search the Web (a second fallback with a settings search address) is removed: Run Agent answers questions and searches when it needs to, so a native web search row only adds a choice. Run Agent is the one fallback row. A typed address still gets an "Open" answer row (feature Links), but only when it is unambiguous (a scheme, or a known top-level domain that isn't a common file extension), since a wrong guess would sit above the user's files. Supersedes "web search is a fallback plus a strict link row".
- **Built-ins are data, and the host's verbs are built-ins (2026-11-06).** Each built-in is one table entry (its registered command and its runner), so the many coming ones (approve, roll back, fix with agent, clipboard history) each touch one place instead of five. No new `Item.Action` cases: anything the host does for the user is a built-in reached by `run`, so it gets search, keywords and later deeplinks and MCP for free.

### Extensions

- **Protocol v1** ([docs/extensions.md](docs/extensions.md), [schema](docs/extension.schema.json)): two methods, `run` and `cancel`, and no handshake: the version is in the manifest, context in environment variables, shutdown is stdin close then SIGTERM then SIGKILL, as in MCP's stdio rules. Modes `once`, `live` and `root` (with a `pattern`, so root extensions aren't woken for unrelated typing). A clean exit with unanswered requests means "restart me", which unifies one-shot scripts and persistent processes. Validated by a fresh agent building a working extension from the page alone.
- **Secrets declared in the manifest, kept in the Keychain, passed as environment variables.** `session.jsonl` fixtures are the checker's format.
- **One runtime for the app and the CLI** (`WicketHost`), so the CLI and the app share one session implementation. The tool lives in `Contents/Helpers`, since `MacOS/wicket` collides with `MacOS/Wicket` on case-insensitive volumes. The app tolerates protocol slips that lose no answer; the checker fails on them.
- **`wicket check` is the approval gate and always isolated (2026-11-06).** Placeholder secrets, no inherited environment, a sealed read-only copy, `sandbox-exec` with no network and no writes outside scratch, fixtures required; it fails closed if the sandbox can't be applied. Generated code must not run with the user's secrets and permissions before review. `wicket run` stays the unsandboxed developer path. `WICKET_CHECK=1` tells an extension to answer from canned data in its own folder. It reads none of the user's files (homes, other volumes, temp folders) except the program `run` names and its install folder (2026-11-07): unapproved code could otherwise copy them into checker output, and allowing the program's own links and folder covers uv, pyenv and nvm without listing layouts. Limit: other tools under home don't run in a check.
- **Never resend anything that may have changed state.** After a clean exit, only runs safe to repeat go to a fresh process; others fail, since the process may have read them and already written files or called an API. Every way of giving up on a process escalates to SIGKILL.
- **Retry is a declared contract, never inferred (2026-11-06).** Live and root runs are searches, so they may be resent; a once command only if its manifest says `repeatable`. Inferring it from visibility (a listed command without args counted as a query) could run a toggle twice. The flag exists because a one-shot script's process can exit just as the next request is written (a list re-run after an action's `reload`), and only the author knows the command just reads.
- **Approval is per revision, owned by Wicket (owner, 2026-11-07).** The user approves an extension's exact revision once; any code change needs approval again. Approvals live in a host store only Wicket's UI writes, and it fails closed. Reason: an agent can rewrite an extension at any time, and approving a name would silently approve its next version.
- **Extension commands are in the palette exactly when approved (2026-11-07).** The gate is in Host, not the App: the active catalog holds only approved revisions, and anything else is refused (`notApproved`) before a process starts, so the CLI, deeplinks and MCP can't pass around it. Replaces "off in the palette until the consent store lands" and its switch.
- **A changed folder keeps running its approved revision until the new one is approved (2026-11-07).** The new revision is listed as changed and runs nothing; the approved one keeps working, since an agent editing an extension shouldn't break it mid-edit, and rollback is approving a revision Wicket still keeps. A folder that becomes invalid keeps its approved revision running for the same reason.
- **Move to Trash, without a confirmation, forgets everything but the data (2026-11-08).** The folder goes to the Trash, which is the undo, so the page needs no dialog; approvals and sealed revisions go with it, so nothing runs or lingers and a folder put back needs enabling again. The data directory and secrets stay, since deleting them couldn't be undone.
- **Enable acts only on a screen Wicket drew (2026-11-07).** It needs a token the review screen issued in this run of the app, after a passing check, and never written anywhere, so no settings.json binding, deeplink or other process can approve, and nothing is approved that the user wasn't shown checked.
- **Command frames are fed by a stream of content**, so a streaming AI answer and an extension use the same frames. A `reload` re-runs the frame it was opened from, so a command answering its own view with `reload` can't loop. Failures show in the frame, never only in a log.
- **An action opens a frame only when its first result is content,** so a toggle answering `close` never flashes a frame.
- **One content model: a run shows a `Screen`, closes or reloads; a frame above the root is a screen with or without a run (2026-11-06).** Results and screens repeated answer, list and detail, and a pushed detail repeated a command's detail, so every frame, sizing and pill rule had two cases and grid or form would have added two more. The wire format didn't change. A pushed page has no run, so a reload landing on it does nothing rather than inventing one.
- **Close messages in a glass capsule where the pill was.** The checkmark and reading-time dwell are from Tinycast's message pill; Tinycast anchors it near the screen edge, ours stays where the user was looking.

- **A revision is the folder's SHA-256, and a run from an older one is refused (2026-11-06).** Approvals and rollbacks need an exact identity, and a row shown by replaced code must never run new code silently ("the extension changed; run it again"). Links must stay inside the folder, or code the hash never saw would run; tool state and regenerable caches are skipped, so an agent's working files don't change what was approved; dependencies count, since they run. Rules in docs/architecture.md (Revisions).
- **What runs is a sealed revision, never the authoring folder (2026-11-07).** Discovery seals a read-only, hashed copy of each folder in host storage, and checks and sessions use it, so what was checked, approved and runs are the same bytes while an agent keeps writing. Dependencies are sealed with the code, so a virtualenv (absolute paths) can't be: Python packages come through uv (below) or are vendored. Discovery (every folder) is separate from the active catalog (what may run), so consent is one activation function. Each extension keeps its approved and previous approved revision for rollback, tracked in the approvals store, since "the newest other folder" was often an agent's unapproved draft; other drafts are pruned.
- **Python packages come through uv, locked, in Wicket's own uv storage (owner, 2026-11-07).** A PEP 723 script run by `uv run --script` with its `uv lock --script` lock, which the author (an agent included) writes; a missing or stale lock fails rather than running drifted dependencies. Wheels only, since building an sdist runs package code; uv-managed Pythons only, so the checked interpreter is the one that runs (uv otherwise took the user's Python from PATH). A check installs into a clone of Wicket's cache and replays offline, so no check can change what approved extensions use. `uvx` and `uv tool run` are refused (no lock), and Wicket's own uv steps never use a `uv` an extension names. It costs about 10 ms per process start (22 against 12 ms for `python3`). Mechanics in docs/architecture.md (uv extensions).
- **A changed revision re-runs searches and stops everything else (2026-11-07).** Every run binds the revision active when it starts. When the catalog changes it, a run that is safe to repeat (a search) runs again on the new code, since that can do no harm; any other stops with "the extension changed; run it again", since re-running it could change something twice.
- **One diagnostics store, one message channel (2026-11-06).** Every producer (discovery, sessions, failed runs, the hotkey, keyword conflicts, settings) reports into one bounded store, so the panes, the Extensions screen and "Fix with agent" read one place instead of copies. Extension text is the extension's own words with what the host knows redacted (secret values, the session's recent queries) before it is stored and before it is cut, and nothing in it is logged; anything else it writes stays as written, so the store claims no more privacy than that. Transient messages have one channel (`Messages`) that the palette controller presents, not the session's request callback, because paste-back, voice and onboarding post from outside any command.
- **A process has ended only when everything it started has (2026-11-06).** Tree membership is "still linked to the child": its process group, holders of its pipes, parentage, and anything seen as a member before, because macOS has no subreaper or inheritable tag. Leftovers of a process that exits by itself are stopped before the next one starts; deliberate daemonising is the sandbox's job. A finished agent run is stopped gracefully, a cancelled one gets SIGTERM at once.
- **An agent run is complete only when its process tree is gone, and quitting waits for that (2026-11-07).** Otherwise Wicket could seal and offer an extension a child is still writing, and quitting would orphan agents and extension processes mid-write. The final answer is held until the tree exits, bounded by a grace (then SIGTERM, which the run reports); quitting is bounded at 2 s so a process that won't die can't keep Wicket from quitting.

### AI

- **One AI, acting through the user's own agent and its permission settings (owner, 2026-11-08).** Ask, Do and Make stop being separate choices: one AI entry answers, researches or acts (plain web search, kept as a shortcut at first, was removed the same day; see above). Actions run in the user's Claude Code or Codex under the permission mode they set there (auto included), or the level they pick in Settings ▸ AI (below); when the agent asks, Wicket shows the question in the palette. Reason: agents are capable now, a plan-and-Run gate on every action is friction, and the harness's settings are the user's own policy, on their subscription. Wicket adds no safety on top of auto-approved actions; the user owns that choice. Stable mechanics still compile into commands that run without a model; the agent does work that needs judgment. Codex and Claude Code both act; Claude's prompts come over its stream-json control channel. Supersedes "the model is the compiler, not the runtime" and Do's plan-first rule; advisor verdicts in docs/reviews/2026-11-08-ai-native.md.
- **Run Agent on top when the typing reads like a request (2026-11-08).** If the query reads like a question or instruction (ends with "?", starts with a question or instruction word in English or German, or has four plain words) and nothing local is a strong match (exact or answer tier, or a host match scoring like the query's words in order), the lead fallback moves to the top, so Return asks the AI without picking a row. A rule, not a model: a string check costs microseconds on the keystroke path, and it lives in one pure function so an on-device classifier can replace it. Extension matches never count as strong, since the host can't judge them.
- **The AI builds commands when asked; there is no Make a Command (owner, 2026-11-08).** "Build a command that shows the weather", "change my invoices command" or "what can you do?" go to the one AI entry, like the Pi agent harness extending itself: every acting run is told where Wicket's commands, extensions folder and bundled guide are (read on demand, not 7k tokens pasted into every run; see the agent.md decision below). When the run ends, the extensions it added or changed are offered as the answer's first action, "Review and Enable", on the existing review: per-revision consent is unchanged, and the new command is in the palette at once, no restart. Fix with Agent is a Run Agent run with the failure, so there is one pipeline, not a second build job beside acting. This supersedes the host-owned build job, its staging folder, install-with-Trash and the network-off build sandbox: the user's agent configuration is the policy here too. The review is offered even when the run failed or was stopped, since what it wrote is still there. Codex and Claude Code build commands; with Apple, a request to build a command gets an answer.
- **Wicket's agent instructions are a Markdown file the user owns; no harness of our own (owner, 2026-11-08).** Wicket adds context and the user's agent does the work. What every acting run is told about Wicket (how to reply, how to add a command, the check-fix-repeat loop) is `agent.md` in the settings folder, editable like settings.json and opened from Settings ▸ AI; only what Wicket alone knows is generated per run (absolute paths, the command list). Without the file the bundled default applies, so updates improve it for everyone who hasn't edited it, and deleting it is how to go back. It is instructions, not consent: nothing in it can enable an extension. From the Pi comparison, runs also get the whole authoring kit (guide, schema, samples with fixtures, bundled in the app) and a full command list (ids, input, folders) written to a file the agent reads on demand, so the per-run prompt stays short.
- **Run Agent, not Ask AI (owner, 2026-11-08).** The one AI entry acts, so its name says so (`builtin:run-agent`, feature `ai`). settings.json's old `ask-ai` feature key still loads and is rewritten on the next change from Settings.
- **Model, effort and speed per agent (owner, 2026-11-08).** Preferences in settings.json, each defaulting to the agent's own configuration, except speed, which defaults to regular and is forced: some Codex models are fast by default, and faster spends more of the user's plan. The pickers list what each CLI reports (Codex `model/list`, Claude Code `initialize`, neither calling a model), so they never go stale; Codex 0.167 has one fast tier, so there is no "ultra fast". Only acting runs use them; `wicket agent ask`'s answer runs keep their fixed setup.
- **Permission levels are consent, outside settings.json (owner, 2026-11-08).** T3 Code's four levels (Supervised, Auto-accept edits, Auto, Full access) mapped onto each CLI per run. A level decides what an agent does unasked, so (principle 6) it lives in a host file only Settings ▸ AI writes; a `permission` in settings.json is ignored with a warning. Same levels and mapping as T3 Code, re-implemented; we set Codex's per turn, since Codex resets the reviewer on every turn. The palette's prompts name the active level.
- **Agent answers show only what the agent writes (owner, 2026-11-08).** Its messages along the way and its final answer, in order; no tool use, no thinking. Simpler to read; tool lines may come back later as an option.
- **Answers don't stream by default (owner, 2026-11-08).** `ai.streamAnswers` is off: the page shows the agent working, each message once it is whole, then the answer at once, since a half-written answer is rarely useful to read in a launcher. Approvals still show at once; streaming stays one switch for those who like it.
- **Agent replies are markdown with native component tags (owner, 2026-11-08, round 4; supersedes the JSON screen vocabulary through structured output).** The agent writes an ordinary markdown reply and may use a fixed catalog of plain, block-level tags (`<card>`, `<columns>`, `<stat>`, `<chart>`, `<image>`, `<file>`, `<url>`, `<timeline>`, …); Wicket parses them and draws native views. Why: the first iteration's fixed screen slots felt underwhelming, and models are fluent in markdown with tags (Markdoc, MDX); prose and components interleave naturally and stream. Plain markdown in the final message, no harness structured output: a schema could only guarantee "a string" while costing streaming, double output and cache; it stays a one-line fallback. Wicket stays in control: whitelisted tags and attributes, layout bounded (columns, cards, no sizes or colours, a semantic `tone` only), unknown tags shown as text, every action through `ActionPolicy` (agent content still only presents). Agent markup is rendered tolerantly; extension markup is linted strictly by `wicket check`. One scrolling document with focusable targets in reading order; typing on a document starts a Follow Up. Earlier owner calls stand: ⌘↩ is Follow Up, "Show online content" on by default, choices later as Follow Up messages never consent. History and designs: docs/reviews/2026-11-08-agent-ui.md (rounds 1 to 4).
- **Composed screens stay whole and keyboard-simple (2026-11-08).** A long summary expands by navigation (Read Summary pushes it as a page), never inline, so there is no third keyboard model; Read Summary is the palette's, added only when something is hidden, and never takes ⌘↩ from the row. Rows stay whole under any summary, facts and section titles, so the eight-row card holds. A page's metadata goes beside the text only when the text is taller, by measurement, since a producer can't know the width. Quick Look waits for an on-screen spike: the non-activating palette and `QLPreviewPanel` both want the keyboard.
- **Markup is parsed by hand, tolerant for agents and strict for extensions (2026-11-08).** A byte-level scanner plus a builder held to the catalog, not an XML or HTML parser: agent markup is never well-formed, and the rules (tags only at block position, code opaque, an unclosed tag closed by its parent) are Wicket's own. Agent problems never fail a reply; `wicket check` reports every one as an error. A few spellings models reach for (`<img>`, `<link>`, `type`) are read but never advertised, so the agent learns one spelling.
- **One file per component, one registry (owner, 2026-11-08).** Each tag's spec, building, Copy Answer text, targets and limits live in its component's file, registered in `Markup.components`; the agent's instructions, docs/markup.md, the lint and the tests are generated from or checked against it. No switch over tag names anywhere else, so the catalog can grow without the codebase growing around it.
- **Extensions use the same markup, not a parallel vocabulary (2026-11-08).** `detail.markdown` and `list.summary` accept the agent's tags; protocol stays 1, since plain Markdown is valid markup. `list.facts` stays until the app draws a summary's `<facts>`, then goes.
- **Links in answers never run anything (2026-11-08).** Clicking one goes through Wicket's own Open, so the palette closes as it does for a row and a missing file says so. Answers are agent output a prompt injection can steer, so an app, script or executable is revealed in Finder instead of opened, and only web, mail and file links are followed.
- **Follow Up continues the agent's own session (owner, 2026-11-08).** A finished Run Agent answer offers Follow Up (⌘↩, Paste Answer moves to the panel); it opens the pill as "Follow up", typed or spoken, and the question resumes the same Claude Code session or Codex thread with the conversation's folder, model and permission level, even if Settings changed since. Resuming the harness's session, not pasting old text back, keeps what the agent did and read, not just its words. Persist and resume, not a process kept alive: nothing idles, nothing to kill on quit, and each turn stays one process tree with its existing completion and cancellation. The cost: acting runs now land in the user's normal Claude Code and Codex history (it is their agent); `wicket agent ask`'s answer runs stay ephemeral. The follow-up's answer shows alone, titled by its question: Escape walks back through the thread, so a compact transcript would only repeat it. Follow Up lives as long as the palette's frames, so a dismiss ends it.
- **Search phrases reuse alternate-name ranking (2026-11-08).** Tinycast treats extension keywords as inclusion-only; we score phrases just below equivalent titles, using the existing matcher so precise intent can outrank a weak title hit without new ranking rules.
- **Settings ▸ AI is one provider and its four fields (owner, 2026-11-08).** One picker, "Claude" or "ChatGPT" (the subscription people know, not the CLI), listing only providers that are installed and signed in; below it Model, Reasoning effort, Speed and Permissions for that one, remembered per provider. No "Default" entries: Wicket always names a model (Claude's `sonnet` alias, ChatGPT's GPT-6.1 Terra), effort medium, speed regular, so what runs is what the pane shows. Permissions default to Auto, and "the agent's own settings" is gone; Auto with nothing chosen (or a damaged store) is the product default, not a grant read from the file. Where Claude's auto mode isn't available to the account, Claude Code falls back to asking by itself, so we say so rather than add a fallback of our own. With none chosen the first ready one answers, Claude first.
- **No Apple Intelligence provider (owner, 2026-11-08).** Run Agent is always Claude or ChatGPT: a third choice that can only answer made the pane and the behavior depend on which one was picked. Apple's on-device model may return for small internal jobs (an intent classifier, quick rewrites), never as a choice.
- **Codex through `app-server`, not `exec --json`:** no slower for one-shot runs (about 0.2 s setup) and it gives typed items, token usage, a sandbox per turn and approvals as requests. Claude Code through `-p` stream-json, both ways for acting runs (`--permission-prompt-tool stdio`), as the Agent SDK does; no SDK dependency, since the protocol is a few JSON lines.
- **Tested against one major.minor per CLI** (Codex 0.167, Claude Code 2.1); other versions still run, with an "untested version" warning, since both interfaces change between minors.
- **Locked-down runs:** answer runs (`wicket agent ask`) get no user setup: no tools, and user hooks, plugins, MCP servers and memories switched off. Acting Run Agent runs, building commands included, run under the user's own agent configuration, its hooks and MCP servers included, because that configuration is the user's policy (2026-11-08).
- **Claude's "Allow for Session" stays in the session (2026-11-08).** Claude Code suggests permission updates with each prompt, some destined for the folder's `.claude/settings.local.json`; Wicket applies them with the destination set to the session, so answering in the palette never writes the user's settings. Claude's question tool (AskUserQuestion) is declined, since the palette has no form for it; the agent asks in its reply.
- **Approvals say exactly what they allow (2026-11-08).** A command shows where it runs, a network request its host and protocol, a file change paths relative to the run's folder (absolute outside it) and any folder it asks to write under for the rest of the run, since a base name could be any file. An approval answered twice or after its run ended changes nothing rather than covering the live answer with a failure.
- **Status checked before each run, not at launch:** a logged-out Codex otherwise retries for about 17 s. A chosen provider that isn't ready is reported, never swapped for another (Tinycast's rule too).
- **Run Agent sees what you had selected, never the clipboard (2026-11-08).** The selected text (Accessibility) or Finder's selection (Apple events) is captured after the palette shows, so a summon costs nothing, and only if the permission was already given: a prompt at summon would take the keyboard from the palette, so Settings ▸ AI asks instead. Reading the clipboard makes macOS alert. A chip in the pill says what was captured and Backspace drops it; only commands that declare they use it get it.
- **Each extension keeps its recent runs on disk, and `wicket log` reads them (owner, 2026-11-08).** A weather extension the agent built passed its check (canned data) and failed on its first real run, and nobody could see why: the error lived only in memory. Now every run, however it ends (ok, the extension's own error, an answer Wicket rejected, a crash, a timeout, a refusal), is recorded with why, so the user, Copy Diagnostics and the agent itself can read it later. The text a run was sent is kept only for failures, since reproducing one needs its input and a success's input (every live keystroke) helps no one; it stays in Application Support, is never logged, and goes with Move to Trash. Successes in a row fold into one entry, so a burst of searches can't push a failure out. The agent must also run a networked, file or secret-using extension for real (`wicket run`) before saying it is done, since the check only proves the faked path.
- **Fix and Change with Agent continue the conversation that built the extension (owner, 2026-11-08).** The agent that wrote it knows why it is the way it is, so its session (Follow Up's resume, persisted per extension in Application Support, never in the sealed folder) is resumed with the failure or the request, and a new conversation starts when there is none or it can't be resumed. The permission level is the one chosen now, not the build's: it is consent, and a remembered conversation can be weeks old. Fix with Agent is offered wherever an extension's own code fails (a failed check, a command's failure page, an extension with recent failures), never for Wicket's refusals; consent is unchanged, since the run's changes go through Review and Enable.
- **Answers keep their scroll position at the top as they stream.** Tinycast pins a streaming reply to its end, which suits a chat transcript more than a short answer. No "Continue in Codex": answer runs are ephemeral.

### Voice

- **Summon and speak, into the search field (owner, 2026-11-08).** Words appear in the field as they are said, and listening continues through pauses until the user presses Return, types or presses Escape (owner, 2026-11-08: stopping at a short silence cut people off mid-thought); then the normal flow applies (local results, the AI row on top for a request) and nothing runs until Return. Typing or Escape stops listening and keeps the words. Speech is just another way to type the query, so routing stays one rule for both; a spoken keyword never opens its command mid-sentence.
- **Apple's on-device SpeechAnalyzer and SpeechTranscriber.** Live partial results, German and English among many languages, no model to ship, and it runs in a system process: Wicket's idle memory is unchanged with voice off, and listening asks only for the microphone (no speech recognition permission). Tinycast ships its own Core ML models in a helper process for system-wide dictation into other apps, a different job; we took its rules that the switch is consent and that only a deliberate act asks for the microphone.
- **Turning voice on, and listening on every open, are consent.** Kept in a Wicket-owned file in Application Support, written only by Settings ▸ Voice, failing closed (principle 6): an agent editing settings.json must not be able to open the microphone. The microphone is asked for when the user turns voice on there, never at a summon, where its dialog would take the keyboard from the palette.
- **On open the microphone arms quietly; the palette shows listening only once words are heard (owner, 2026-11-08).** Most summons are typed, so a listening UI on every open was noise: a small filled mic glyph is the only sign, the first key turns it off and drops anything heard, and the first words switch to listening. By hand, a mic button in the pill and ⌘L (L for listen; free in the field and the menu) start or stop listening, because a command with an optional hotkey wasn't discoverable.
- **Voice never looks like the primary input (owner, 2026-11-08).** No "Listening…" prompt: the field keeps its usual prompt until words arrive, and a small moving waveform replaces the magnifying glass only while speech is actually being transcribed (listening, not armed). Armed, only a transcript with a letter or digit counts as words, so noise transcribed as punctuation keeps it quiet.
- **Press, not hold.** The mic button and ⌘L toggle listening: a held key would need key-up tracking for one extra mode, and Return, a key or Escape already ends the utterance.
- **The language is the first preferred language transcription supports,** region first, then the language's likely region: Apple's own fallback mapped "en" to Singapore English. One language per utterance (SpeechTranscriber's limit); a picker waits for a need.

### OS integration

- **Paste-back types ⌘V into the app frontmost at summon.** The key comes from the current keyboard layout, so Dvorak, AZERTY and QWERTZ paste; Tinycast posts the ANSI key code. Accessibility is asked on a paste, never at launch, at most once per session (Tinycast asks every paste). Activation is awaited rather than a fixed delay, and if the target doesn't come front we only copy, rather than type into the wrong app. **The clipboard is not restored:** reading it triggers macOS's pasteboard access alert and a restore races the target's read; revisit if `NSPasteboard.accessBehavior` allows it.

### Release (2026-11-08)

- **A notarized DMG on GitHub Releases, a Homebrew cask, Sparkle for updates.** Installing should be like any Mac app. Sparkle is the first third-party dependency: in-app updates are a concrete need, it is the standard, and writing a signed updater ourselves would be more code than the core feature it serves. It costs about 0.4 MB of idle memory while running (21.3 versus 21.0 MB, `vmmap`) and nothing on the palette path. Automatic checks are on by default (`SUEnableAutomaticChecks`, so no consent prompt): a check is one GET of a public file, no system profile.
- **The appcast is `appcast.xml` on `main`, read raw from GitHub.** One file in the repo, its history in git, no Pages site or extra branch; the release script adds the item and it goes live with the push after the DMG is uploaded, so the feed never points at a missing file. A latest-release asset would need the whole feed regenerated each time.
- **Wicket Dev beside the released app.** Local builds are Wicket Dev (`app.wicket.Wicket.dev`, a DEV badge, ⌃⌥Space, its own config and Application Support folders, no updater), so the owner can run the installed Wicket and work on the next one at once. One `Edition` read from the bundle id, not a compile flag: the same binary is tested either way and the bundled `wicket` tool follows its app.
- **Versions start at 0.0.1; the build number is one past the newest in the appcast,** which is what Sparkle compares, so it can never go backwards. The cask lives in the repo as the source for the `pietz/homebrew-wicket` tap, with `auto_updates` so Homebrew leaves updates to Sparkle.

## Open concept challenges

- **Interpreter start-up versus live queries.** Through a session, a Python extension starts and answers in about 12 ms with `python3` and 22 ms with `uv run --script` (2026-11-07, warm); the protocol lets a process stay alive and live queries are debounced. Node and heavier imports aren't measured yet.
- **"Extensions in seconds" oversells it.** An agent run takes tens of seconds to minutes: a week-number command took Codex about a minute end to end (2026-11-08, headless). The promise is "one sentence, no code".
- **Benchmarks need an idle Mac.** The latency harness takes over the screen; in-app timings (`/usr/bin/log stream --predicate 'subsystem == "app.wicket"'`) run anytime.

## Open decisions

- **Licence:** MIT versus GPL/AGPL; leaning MIT for adoption.
- **Name:** Apache Wicket is a minor clash; wicket.app is for sale and the plain GitHub org is taken (`wicket-app` or `getwicket`). Trademark check before going public.
