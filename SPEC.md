# Wicket spec

Updated 12 Nov 2026, for Wicket 0.1. This is the design of the app in this repository, in enough detail to rebuild it. It replaced the 0.0.x line, which this document calls the first Wicket (about 20,000 lines; see [COMPARISON.md](COMPARISON.md)). Open problems are in [ISSUES.md](ISSUES.md) and planned work in [ROADMAP.md](ROADMAP.md).

## Idea

Wicket is a small native macOS launcher built for a world where everyone has a coding agent.

1. A native Swift panel shows results and answers with a handful of native views.
2. An extension is any program that reads a JSON request and prints a JSON view. Built-in features follow the same contract.
3. Your existing agent is one keystroke away, answers in markdown, and can write new extensions for you.

The loop that makes it grow: you ask the agent, it answers, and when the answer is worth keeping it writes an extension that from then on runs instantly, without a model.

## Rules that keep it small

- **The fast path never waits.** Typing never starts a model. Root typing starts a script only for a matching extension pattern; typing inside a chosen command reruns that command, unless it is a `submit` command, which runs only on Return.
- **Lean on existing parsers.** Agents write markdown with a few tags. Extensions write JSON. Wicket avoids owning a scanner, parser or validator where the platform already has one.
- **Rich answers are worth their code, the machinery around them is not.** The first Wicket spent about 3,700 lines on its tag language, most of it on scanning, parsing, validating and building. Plain markdown cost 164 lines. The rewrite keeps the tags and looks for the cheapest honest way to draw them.
- **One agent protocol.** No model loop of our own and no per-agent integration code.
- **Trust in one rule.** An extension runs if its source is on. Enabled means trusted. There is no approval step.
- **Line budget.** The rewrite aimed for about 6,000 lines of source and under 8,000, rich answers included; it ships at about 6,400 formatted Swift lines plus 200 of resources.

## What is fixed and what is hackable

| Layer | Who changes it | How |
| --- | --- | --- |
| Panel, hotkey, renderer, the view contract | Wicket itself | Compiled Swift. Change it by contributing or forking |
| Built-in providers (apps, files, math) | Wicket itself | Compiled Swift, but each can be switched off and replaced by an extension |
| Extensions | You and your agent | A folder with a manifest and any executable |
| Agent instructions and docs | You and your agent | Plain files in the Wicket folder, read by the agent |
| Preferences | You and your agent | Native Settings window backed by one plain config.json file |

Extensions are ordinary programs with your user access, so they need no special bridge to reach the system: a window manager extension can call the macOS APIs itself. They are not sandboxed.

## Input

- Typing filters results from built-in providers, the names of extension commands and the items extensions list in their manifests.
- Results are ordered by how well they match, never by a source order the user sets. Learned usage only breaks ties inside a tier of the root search; it plays no part inside a chosen extension command, for fallbacks or for computed answers, which are never recorded. See Result order below.
- "Ask agent" is always a row. It is on top when nothing matches strongly, so a sentence goes to the agent, and also when the input ends with a question mark. A strong match is a math result, a nonempty successful pattern result, or any name match that is exact or a prefix from the start of a word of a title, alias, extension name or keyword. With empty input, the most used apps come first and Ask agent follows them. The row belongs to Wicket itself, not to the source list, and cannot be switched off.

### Result order

One pure function (`Ranking.compose`) orders everything at the root of the launcher. The panel and headless mode both use it, so there is one copy of these rules. A name tier is 2 for an exact match, 1 when the input is a prefix of the name from the start of any of its words and 0 otherwise, over a row's title and aliases (keywords) or an extension's name and keyword, folded for case, diacritics, width and spaces (`Ranking.tier`). Words start where the fuzzy matcher's do (`SearchKey.boundary`): after a space or punctuation, at camelCase, and between letters and digits, so `pass` is a tier 1 match of Proton Pass and 1Password, not only of Passwords. Within a tier the fuzzy score still puts a whole-title prefix above a later word's, since the start of the name earns more than the start of a word. Usage decays over time and is stored per complete input, so a pick for "c" does not affect "cl". The empty input ranks by each row's use under every input together (`UsageStore.totals`): picks are made after typing, so its own history stays nearly empty, which once left it alphabetical.

1. A math result.
2. Pattern extension results: extensions whose `match` regex ran and returned items. Each extension's items stay together in its own order: exact or prefix title/alias, then usage for this exact input, then returned order. Several pattern extensions are ordered by extension name. This is the only place an extension's items are ordered by usage.
3. Name matches: app rows, file results (by file name), extension command rows (name, keyword), extension items (title, keywords; at most the best 20 per extension, `ExtensionCommand.rootItems`) and the host's rows: Settings (alias "preferences") and, while clipboard history is on, Clipboard History (alias "pasteboard"). Sort by tier, then usage for this exact input, then files after every other kind, then fuzzy score, then kind (apps, extension commands, extension items, host rows), then title. Usage never lifts a row into a higher tier. Files come last within their tier because a file's name says least about what the user wants: typing `pass` once listed twenty `pass*` files above 1Password and Proton Pass (owner, 0.2.2). A file picked before for this exact input still rises by its usage, and a file whose name the input starts at a word is a strong match like any other. For `pass` with those apps, the Password command and some `pass*` files the order is Passwords, Password, then 1Password and Proton Pass, the files, Ask agent, then loose matches such as Podcasts.
4. Ask agent: on top when nothing is strong or the trimmed input ends with `?`. Otherwise directly after the last tier 1 or 2 row and before the loose (tier 0) matches, so it stays visible. Files are the last tier 1 rows, so Ask agent follows at most eight of them (`FileSearch.shown`).
5. Fallback extensions (`fallback: true`), only when nothing is strong, directly after Ask agent, ordered by name. They replace their own command row. Empty input never shows fallbacks.
6. Failed pattern runs and invalid manifests of enabled extensions come last as error and repair rows.

Apps, files and extension items reach `compose` through one door: a list of `Ranking.Names`, each a source's rows already filtered to the input with its kind. Every name match is scored by its title and keywords in the same way; only the command and host rows are made inside `compose`. Files and items are empty for empty input (their sources have no best match for nothing), so with empty input the list is at most 20 apps (`Ranking.emptyApps`, a constant), the most used first and then by name, then extension commands, then Ask agent; a new install still shows twenty apps by name. Typed input and the rows inside a command are never capped. Pattern extensions that match empty input put their rows first.
- **Measured** (release build, 400 apps, 600 usage entries, best of 50): composing the empty input took 0.59 ms listing all 401 rows before, and 0.99 ms for the 21 rows now; the extra is decoding the usage keys for the totals, and the panel draws 21 rows instead of 401.
- Selection follows the first result until the user moves it by keyboard or mouse within the query. After that, keep its identity across refreshes and late arrivals. A new query selects the first result. Defer missing-row fallback while same-query extension results are pending. Once settled, select the previous index, clamped to the last row. Keep the selected row visible.
- Enter runs the selected row. Cmd+Enter asks the agent unless a permission is pending. Then Cmd+Enter allows once, Esc denies, and plain Enter does nothing. IME composition owns its keys before any launcher shortcut. Esc cancels a running answer and stays in the conversation; otherwise it goes back one level, then closes.
- After an agent answer, the input belongs to that conversation until Esc.
- **Argument slots:** while slots are shown (below), Tab moves from the input to the first slot, through the others and back to the input, and Shift+Tab goes the other way (`PaletteKeyAction.focus`, `LauncherModel.moveFocus`). Where no slots are shown, and while a permission is pending, Tab stays AppKit's, so the confirmation card's buttons keep it. From any field Return runs what Return runs, arrows move the selection and Escape keeps its order; every key still stops voice first and composition still owns its keys. The model holds which field has the keys (`focusedArgument`, nil for the input), set by Tab or a click; only a declared name counts, so when the slots go away (the selection moves at the root, Escape, the panel hides) the input takes the keys back. A click on the selected command row with a filled draft enters it like Return (`LauncherModel.click`). Speech goes to the input only.

### Launcher

- **Apps:** a `SearchIndex` built once per scan holds each app's prepared name and alias keys and only filters: it returns the apps the input fuzzy-matches, or all of them for empty input, unordered. Ranking happens once, in `Ranking.compose` (Result order above).
- **Files:** filenames from the Spotlight index, with no index of our own (see File search below).
- **Math:** a small hand-written parser (`Math.swift`) for arithmetic, parentheses, powers (right-associative, tighter than unary minus) and percentages. It needs an operator; bare or signed numbers, dates (`2026-11-10`, `11/11/2026`, `11.11.2026`), versions (`1.2.3`) and phone numbers (`555-1234`, `+1 555-123-4567`) give no row. No implicit multiplication, functions, units, currencies or dates; units and currencies are extensions.
  - **Percentages** read the way people say them: `200 + 10%` is 220, `200 - 10%` is 180, `10% of 200` and `50 * 10%` are a share (20, 5), `15%` alone is 0.15, and `10% + 5%` is 0.15. Only a bare percentage on the right of `+` or `-` changes the left side; `200 + 10% * 2` is 200.2.
  - **Decimal marks:** `.` and `,` are both accepted, whatever the locale. With both in a number, the last is the decimal mark and the other groups thousands (`1.234,5` and `1,234.5` are both 1234.5). One kind used repeatedly groups (`1,000,000`). A single mark is a decimal mark (`3,5 * 2` is 7), except the ambiguous case of one mark before exactly three digits (`1,000`, `1.000`), which groups only when the user's locale groups with that character: `1,000 + 1` is 1001 in en_US and 2 in de_DE. Groups must be three digits after a first group of one to three that does not start with 0, so `0,500` is a half and `1,23,456` is no number.
  - **Results** show in the user's locale with grouping (`1.234,5` in German); Enter copies the same number without grouping (`1234,5`), so it pastes into the user's spreadsheets and back into Wicket.
- **Panel:** 640 points of content plus 40-point margins on each side, horizontally centred on the screen under the pointer, top edge about one fifth down, up to eight visible rows. Input is cleared on dismissal.
- **Panel stability:** the input row must stay still while results change. Built-in results are published together and the previous list stays until then; matching extensions add their complete views when ready, and file results as their batches arrive; the layout is anchored at the top; window and content height come from one policy and are never derived from each other. The list card grows at once but shrinks only after the list has stayed shorter for 300 ms (`LauncherModel.sizedRows`), so file results arriving after the apps do not make it collapse and grow again while typing; the hold is for one screen only, so a list for another screen (root or a command) and hiding the panel size it at once.
- **Switching screens is one step** (`LauncherModel.arrive`): entering a command, leaving one, and ending a conversation keep the screen being left exactly as it was (input, rows, height) until the new screen's first content is there, then content and height change in the same publish. A command's first content is its first view; a page's is its body rendered and measured offscreen in the shared web view (`preparePage`, `AnswerRenderer.render`), so it appears at its height; the root's is its built-in results. A command answered without a process (manifest items, the clipboard history) switches before Return returns. After 150 ms (`arrivalDeadline`) the new screen shows anyway at its own height, a one-row card saying Running…, so a slow process never makes Return feel dead; the view then grows into it. Typing during the wait switches at once and what was added to the old input goes to the new one; Escape calls an entry off and stays, and waits for a way back already on its way. Opening a conversation needs no wait: its first content is the question.
- **Argument slots:** the selected command row's declared arguments at the root, or the open command's, follow the input's text directly in the search pill, like `Caffeinate [hours] [minutes]`, one per argument in manifest order: an AppKit field like the input (`SearchField`, so IME, paste and editing shortcuts work), 15 points, in a 28-point rounded field with an 8 percent primary fill, as wide as its value or placeholder between 24 and 150 points, labelled for accessibility by its placeholder or name. Fixed sizes, like the input. The input is as wide as its text, or its placeholder when empty (inside a command, the command's name), measured by a hidden SwiftUI `Text` under the field, up to the room the slots leave (`InputBar`, a `Layout`); past that the slots stay at the end, fully visible, and the input scrolls. No field sizes itself: `SearchField` takes exactly the width it is given and clips its text. The input's start never moves, and a click on the free space after the slots gives the input the keys. Without slots the input takes the whole width, as before. Marked IME text is not in the measured text until committed, so while composing past the measured width the input scrolls inside it. They sit next to the text because that is where the eyes are (owner, 0.2.1); the first version put them at the trailing end for fear of AppKit's scrolling racing a growing field, which an offscreen test of typing, long text and replacing it did not show (`slotsFollowTheTypedTextUpToTheEnd`).
- **Panel look, modelled on the first Wicket:** a separate 56-point search pill, an 8-point gap, a result card with 22-point corners, 40-point rows, 12-point selection corners, 26-point icons, 14 and 13 point title and subtitle, and a prominent 24-point calculation result.
- **Layering:** only glass surfaces belong inside `GlassEffectContainer`. Input, rows, headers and footers sit above it in a sibling stack. Keep a 40-point transparent margin and disable the native window shadow. `PaletteLayout` owns all dimensions for window, content and answer sizing. Glass tint is `0.55 * (1 - backgroundTransparency)`.
- **Visual checks:** the app ships no capture or fixture mode. Panel captures are an opt-in test, `WICKET_CAPTURE_DIR=<folder> swift test --filter panelCapture`, skipped otherwise. It draws every state offscreen in light and dark with solid surfaces, using the test fakes, orders no window front, makes none key and posts no event, then reads each PNG back with text recognition and checks the expected text. Solid offscreen surfaces prove foreground and layout, not glass, focus or compositor shadows; those need the user's eyes on a real window.
- **Hotkey:** Option+Space by default (Control+Option+Space in Wicket Dev, see Editions), configurable; an existing config wins. Launch at login is available in Settings. A login-item launch stays hidden. A manual launch shows the panel without listening.

### File search

Files and folders by name, from the Spotlight index through the MDQuery C API (`FilesProvider.swift`). Wicket keeps no index of its own: Spotlight already maintains one, and a crawler of our own would need Full Disk Access and thousands of lines. MDQuery rather than `NSMetadataQuery`, because it caps hits inside Spotlight (`MDQuerySetMaxCount`), notifies on our own serial queue instead of a run loop, and stops synchronously; `mdfind` as an extension was slower (p50 125 ms, p90 704 ms, process start included) and its ranking and missing reveal action did not fit (research report of 11 Nov 2026).

- **When:** from two folded characters, 80 ms after the input stopped changing. Nothing runs for shorter input. Each word of the input must be a word prefix of the file name, case and diacritic insensitive (`kMDItemFSName == "word*"cdw` per word, joined with `&&`; Spotlight's word mode splits names at spaces, punctuation and camelCase). Word mode answers in tens of milliseconds where a substring match took 100 to 1,000 ms.
- **Where:** each visible folder in home as its own scope, so Spotlight never walks `~/Library`; iCloud Drive (`~/Library/Mobile Documents/com~apple~CloudDocs`); `~/Library/CloudStorage`; mounted volumes under `/Volumes`. Scopes are read per query, so new folders and volumes appear. Loose files directly in home are missed, because a scope must be a folder.
- **Noise:** a path below its scope is dropped when any component is hidden (starts with `.`), is `Library`, `node_modules`, `build`, `DerivedData`, `Pods`, `__pycache__` or `Caches` (any case), or is an `.app` or `.photoslibrary` package or inside one. Apps are left to the apps provider.
- **Ranking:** Spotlight applies its 500-hit cap before any sorting, so the candidates are an arbitrary sample. The shared fuzzy matcher scores each file name; the best 8 (`FileSearch.shown`; score, then shorter name, then path) become rows: the file name as title, the folder as subtitle (`~/Documents/Taxes`, `iCloud Drive/Notes`, `/Volumes/Disk`) and the path as row ID, so usage is learned per file. `Ranking.compose` then ranks them as name matches (Result order).
- **Batches:** every Spotlight progress notification publishes all hits gathered so far, so rows refresh as batches arrive and each batch replaces the previous one; the query gathers once and never watches for changes. A keystroke keeps the previous file rows until the first batch for the new input replaces them (ranking drops those the new input no longer matches, and a query that ends without a batch clears them), so files do not vanish and return while typing. The file type comes from the value list Spotlight gathers with the results, because copying an attribute per hit costs an IPC round trip (about 0.4 ms) each.
- **Actions:** open, then reveal in Finder. A file that `OpenPolicy` refuses, such as a script or an installer, only reveals. The row shows the system icon of the file.
- **Cancellation:** a new input, an address, a conversation or hiding cancels the task that reads the batches; ending its stream stops the query, also during the debounce, and the generation check drops anything late. File search is pending for selection like a running pattern extension. Headless `--query` waits for the query to finish, so its output includes files.
- **Measured** on 11 Nov 2026 (macOS 27.2.1, Mac in use, release build, 30 realistic prefixes from the research report, run twice through headless `--query`): the first batch arrives a median of 87 to 89 ms (p90 132 to 134 ms) after the debounce, with 500 candidates in the median first batch, so files appear about 170 ms after the last keystroke. The app logs `files: first batch N of M in T ms` (counts and timings only) under subsystem `app.wicket`, category `files`. Twenty file rows added about 0.2 ms to one `Ranking.compose` over all 158 apps; the root now takes eight.
- **Switch:** `files` is a built-in source in Settings, Sources.

### Clipboard history

The texts the user copied, searchable in the panel and pasted back with Return (`ClipboardHistory.swift`). A core feature, since an extension cannot watch the pasteboard, and opt-in: the `clipboard` source, the one source that is off by default, switched on in Settings, Sources, or with `{"id":"clipboard","enabled":true}` in `providers`.

- **Watching:** while on, a task polls `NSPasteboard.general.changeCount` every 500 ms (250 ms tolerance), which reads no contents; macOS has no change notification. Only a changed count reads anything, and the count at switch-on or launch is taken as seen, so what was already on the pasteboard is not kept. Off cancels the task.
- **Skipped:** items marked `org.nspasteboard.ConcealedType`, `TransientType` or `AutoGeneratedType` (password managers and other apps mark secrets this way; the types are checked before the text is read), blank text and text over 256 KiB. Text only; images and files wait for real use. Wicket's own copies and pastes are kept like any other copy; pasting a kept text moves it to the top.
- **Pasteboard privacy:** macOS 15.4 and later may ask the user before an app reads the pasteboard programmatically (`NSPasteboard.accessBehavior`). Wicket reads only when the behavior is `default` or `alwaysAllow`: under `ask` every copy would raise an alert, so nothing is read and Settings says to allow Wicket under Paste from Other Apps in Privacy & Security; `alwaysDeny` reads nothing either.
- **Storage:** `clipboard-history.json` in the private folder, `Edition.privateDirectory()`: `~/Library/Application Support/app.wicket.Wicket` (`app.wicket.Wicket.dev` for Wicket Dev), or `<folder>-private` beside a `WICKET_CONFIG_DIR` override. It is outside the Wicket folder because the agent works there and could read it. The folder is created 0700, so no other user can reach the file; every save is an atomic write. Newest first, written off the main path by the same latest-value writer as usage; a failed save logs only an error code. Copying a kept text again moves it to the top with its ID. Retention is fixed at the newest 500 texts for 30 days, applied on every capture and poll, on each configuration (so at launch, also while switched off) and whenever the panel opens; the check costs one date comparison when nothing expired, and never touches the pasteboard. Switching it off keeps the file; Clear History in Settings (with a confirmation) deletes every entry, and each row's Delete deletes one. Nothing is logged but counts and timings (category `clipboard`).
- **Panel:** a host row, Clipboard History (alias `pasteboard`), offered as a name match beside Settings while the feature is on, so `clip` finds it. It is the reserved address `clipboard` (`wicket://clipboard?input=…` too), which opens it as an ordinary command: `ClipboardHistory` is a `Provider` answering `ProviderRequest`s through the same command path as an extension, with the newest 100 matches, every typed word somewhere in the text (case and diacritics ignored, `localizedStandardContains`), each row showing the first line, its age and its line count. Return pastes the exact text into the previous app (newlines kept; an extension's paste loses them when decoded), and the context menu also copies or deletes. Delete is the row's own run action, `{"type":"run","title":"Delete","arguments":{"delete":<id>}}`, exactly as an extension deletes: the chosen request deletes that clip and answers with the updated list. Items are ordered like any command's (title matches to the input first, otherwise the provider's order, here newest first). A command whose source is switched off shows how to switch it on. Picks inside it are not learned, like any command. Root search never shows clipboard entries: they would crowd every query.
- **Measured** (release build, 500 entries of about 1 KB): building the view takes 0.9 ms for empty input and 8 ms at worst for a word that matches nothing, which scans every text.

## Voice

Voice is enabled by default. Opening the launcher through the hotkey, menu or app reopen arms voice immediately after the panel is presented, before layout, focus and results refresh. Set `voice.enabled` to false to turn it off. App startup never arms voice. A login-item launch stays hidden and never requests microphone permission. There is no voice shortcut or language override.

- **Presentation:** idle, starting and listening states. The search pill has a microphone button with Start listening and Stop listening accessibility labels. Startup says “Starting voice…”. Capture says “Listening…”. Voice status or its last error takes precedence in the footer. Clicking the mic can stop or intentionally restart voice for the current opening.
- **Keys and ownership:** every key-down cancels capture before normal routing, including arrows and IME keys. Native edits, paste and IME edits stop it too. Typing takes over for this opening. Queued or late transcripts cannot overwrite it. Reopening arms a fresh session. Return runs the selection and Cmd+Return asks the agent. Escape stops capture and retains the transcript on its first press, including during startup. Standard editing shortcuts keep their usual behavior. Speech and silence never submit a question.
- **Input:** starting preserves existing text. The first transcript with a letter or number replaces it. Later updates replace the whole field with the accumulated transcript and put the native editor caret at the UTF-16 end. Volatile results revise the current tail. Final results append a segment and clear that tail without ending capture. Trim surrounding whitespace and trailing `.` or `。`; retain question marks. Join Chinese and Japanese segments without added spaces, other languages with a space.
- **Results:** built-in results update with every accepted transcript. Extension patterns and chosen commands wait for 350 ms without another transcript before starting a process. A newer transcript cancels the pending or running request. Command names remain searchable without running them. Conversation follow-ups use the same input field.
- **Availability and focus:** agent busy state and agent permissions stop capture immediately and prevent arming. Resolving them does not rearm it. Extension execution alone leaves voice available. Hide, quit and config disable stop capture. Hide orders the panel out immediately. Teardown continues in the background; a new capture waits for it. Losing key status normally hides the panel. Only an actual microphone consent request may borrow focus; finishing that request restores the visible panel's key status, including after denial.
- **Permission:** the first enabled opening checks a nonempty bundle `NSMicrophoneUsageDescription` and uses `AVAudioApplication.requestRecordPermission` when needed. No speech-recognition permission is requested. Denial shows a quiet hint and suppresses automatic retries on later openings. After changing Microphone permission in System Settings, an intentional mic click retries. Success clears that suppression. Permission waiting does not consume either deadline and never blocks typing.
- **Language and models:** use Apple's macOS 26+ on-device `SpeechAnalyzer` and `SpeechTranscriber`. Choose the first supported macOS preferred language, preferring its explicit region, then its likely region, then any supported region. One locale serves the session and segment joining. Use volatile/fast results, user-initiated priority and lingering model retention. Check installed assets before capture. A required installation request fails with a hint; never download automatically. Whether Dictation settings install this exact analyzer asset remains unverified.
- **Privacy and laziness:** no audio files, disk recordings, network recognizer, server fallback or bundled model. Audio stays in the on-device pipeline. Construct the voice state and backend only on an enabled owner opening or intentional mic restart. Once constructed it is kept: disabling voice stops it rather than discarding it, and it holds no hardware until it starts. Enabling config alone does no runtime voice work. Settings can read microphone permission without requesting it or listening. Once per session, at its first transcript or end, the existing background writer saves the last session latencies to `voice-timing.txt` in the Wicket folder: panel open to first audio buffer and first transcript. No transcripts or audio are logged.
- **Limits:** bound startup and transcript inactivity at 60 seconds, resetting on ready and accepted transcripts. The absolute limit is five minutes. Exclude time spent waiting for microphone consent from both limits. A startup timeout says “Voice didn't start. Check permissions and try again.” Listening timeout stops quietly and retains text. These limits are fixed, not config keys.
- **Capture:** prepare and start off the main actor, outside the ownership lock. Opening runs in the background. The state lock covers only ownership. Asynchronous stop waits for opening and teardown in the background. It never holds panel visibility or blocks the main actor. A stopped session cannot open again; cleanup is consumed once. Set the input through `auAudioUnit.setDeviceID`, validate matching nonzero input/output formats, and install the tap using the node format. Tap Float32 PCM in 2,048-frame buffers. Average multichannel samples to mono, including interleaved/discrete layouts. Resample to the analyzer's best compatible format with `AVAudioConverter`. Supply each input buffer once, then `noDataNow`.
- **Microphone:** `voice.microphone` stores a stable device UID. Missing, empty or unavailable means Automatic. Prefer a wired default input, then built-in, then USB and other wired inputs. Only then fall back to the system default. Virtual, aggregate and Continuity inputs require an explicit choice, even when they are the default. Set only the engine input audio unit, never the system default.
- **Device changes:** ignore notifications while the engine is running. If a change stops it, end capture and show a short retry hint. Never restart capture automatically.

Failures stop capture and show short text:

| Cause | Message |
| --- | --- |
| Microphone denied | Microphone denied. Allow Wicket in System Settings. |
| Missing/unusable input | No microphone. Check Sound → Input in System Settings. |
| Unsupported service, language or analyzer format | No on-device speech for your preferred languages. |
| Missing asset | Speech model missing. Check macOS Dictation settings. |
| Missing bundle usage text | Open the Wicket app bundle to use voice. |
| Device change stopped capture | Microphone changed. Open Wicket again to retry. |
| Conversion failure | Couldn't convert microphone audio. Check Sound → Input. |
| Other stream error | Couldn't listen. Try again. |

`@MainActor Transcriber` is the hardware boundary: `start() -> AsyncThrowingStream<VoiceUpdate, any Error>` and `stop()`. Updates are `permission(Bool)`, `ready` and `transcript(String)`. Stop releases capture immediately. `VoiceInput` owns deadlines and a generation token that rejects stale updates. Stream completion stops normally. Termination cancels the backend worker away from the audio callback. Fake streams and synthesized PCM cover ownership, device choice and conversion without hardware or consent.

## Settings

Typing `settings` offers a built-in Settings row beside Ask agent. It opens the same native window as Settings… in the menu bar or Cmd+, while Wicket is active. Use an AppKit toolbar tab controller with native SwiftUI grouped forms, 560 by 480 points of pane content. Keep the selected tab while open. Closing returns the app to accessory mode. The main menu supports Cmd+W and Cmd+Q. Open Config Folder remains a secondary action.

| Tab | Contents |
| --- | --- |
| General | Launcher shortcut recorder, background transparency, Text size, launch at login and config-folder access |
| Voice | `voice.enabled`, Microphone picker (Automatic or input device), Bluetooth help, listening and typing explanation, read-only microphone permission status and a Microphone System Settings link |
| Agent | Claude or ChatGPT, model, effort, permission mode, speed, Stream answers and runtime status |
| Sources | On/off switches, extensions-folder access, and Clipboard history: its switch, a pasteboard-privacy hint when macOS would ask, the saved count and Clear History |

`config.json` is the single source of truth. There is no UserDefaults copy or separate preferences store. `ConfigurationFile.edit` is the sole path for settings edits. Read the latest bytes, validate them, patch the JSON object, validate again, then atomically replace the file. Preserve unknown root, nested and provider-entry fields. Preserve the provider list as written. Initial creation uses `Configuration()` for defaults. Write readable decimals and unescaped slashes. Keep transparency local while dragging; commit once on release, rounded to 0.01.

Watch the exact config file, including atomic replacements. Publish the last good values to the launcher and settings. An invalid file stays untouched and disables preference editing while tabs and folder access remain usable. External repair restores editing live. A write failure has a separate message and leaves the controls usable for retry.

The shortcut recorder uses a local raw-key monitor so Option combinations and command equivalents survive. Pause Wicket's global registration during recording. Escape, app deactivation, leaving the pane or closing its window stops recording and removes the monitor. Resume registration before handling the recorded choice. Register a replacement before persisting it. A conflict keeps the previous working registration and file value, with feedback in Settings. If saving fails, restore the previous registration. Refuse Command plus a single letter, including Shift variants, to protect editing and app commands; ask for Control or Option instead.

Launch at login uses `SMAppService.mainApp.status`, register and unregister. It has no config key. Show pending approval with a Login Items link. Show readable macOS errors, including the possible refusal of an ad hoc build. Launch detection reads the open-application Apple event's login-item marker. Login startup does not present the panel; other launch-time presentation never arms voice.

Opening Agent settings asks both installed CLIs for their models concurrently, in disposable folders, without a model call: Claude answers the stream-json `initialize` request, Codex answers `model/list`. Each listing has a ten-second deadline and every process shuts down through ProcessTree. Cache the lists separately in `agent-options-claude.json` and `agent-options-codex.json`; refresh after one hour, on opening or changing agent. Show loading and readable failure states, and keep saved values. Only discovery populates the cache. Writes run on the main actor, without suspension between reading and writing. Switching agent clears model, effort, mode and speed while retaining unknown fields and the streaming preference.

The tab and its section are titled "Sources", with the help "Turn off sources you don't use." There is no reordering: the list order never affects results.

Provider IDs come from the built-in defaults and discovered extensions, not a second settings list. Sources lists the config list first, then the built-ins and discovered extensions it omits (on; extensions sorted by id). The switch writes `enabled` for that source and nothing else writes provider entries. A new extension is on as soon as it appears.

## Provider contract

Built-in providers and extensions share `view(for: ProviderRequest) async throws -> ProviderView`. The request, view, items and actions are plain Codable values. The host owns trigger scheduling, selection and usage. Ask agent is a host row.

Every row carries a real action, the host's own included: an extension's command row, fallback, detail and error rows, Settings and Ask agent. One function, `LauncherModel.activate`, does what Return, a button, a menu item or a link asks for, so a row's `id` is only its identity and nothing infers behavior from it. The host's own action that must not be public, `send`, which sends a question at once (unlike the public `agent` action and `<item ask>`, which only fill the input), has a wire spelling for headless output but is never decoded: an extension cannot write it.

```json
{"input":"","arguments":{"hours":"4","minutes":"30"},"chosen":true}
```

`input` is required. `arguments` is an object of strings, empty when omitted: the values the user filled into the command's declared arguments and those a run action set, under one namespace. It is request data, never extra executable argv. `chosen` is a boolean, false when omitted, always written by Wicket: true only on the one request caused by the user activating something, that is Return, a click or a menu item on an extension's command or fallback row, on a `run` action (an extension's JSON, a manifest item, or the host's own, such as clipboard history's Delete), or Return in a `submit` command. It is false on typing reruns, refreshes, pattern runs, the host's Show details and error rows (they show what a pattern produced, as a link would) and every address spelled as a URL (`Address.link`, set where a URL is parsed and on those two host rows). Arguments persist for typing (stay in the hourly view), so they cannot mark intent; `chosen` does, and only a chosen request may have side effects. The view is one object with optional `body`, `items` and `actions` (see Views). Unknown action kinds, wrong types, missing required fields and empty or duplicate item IDs fail decoding. Extra keys are tolerated, so a stray `type` is ignored. Results for an input that is no longer current are dropped.

A row requires `id`, string `title` and an `actions` array, which may be empty. Optional fields are `subtitle`, SF Symbol `icon`, string-array `keywords` (aliases) and boolean `prominent`. A prominent first row gets the large calculator presentation; a first `open` or `reveal` action for a file gets its native file/app icon. Return uses the first action. Every action is available in the row context menu; view actions have a native Actions menu in the header. Every action takes an optional `title`, its name in those menus; without one it is named by its kind, and a run is Run for its own extension and Open for another target. `RowAction` is one Codable struct, a `title` and a `kind` (the enum below), with static constructors such as `.run(address, title:)`.

| Action JSON | Effect |
| --- | --- |
| `{"type":"open","url":"https://example.com"}` | Open an allowed URL |
| `{"type":"reveal","url":"file:///Users/me/Documents/a.pdf"}` | Show an existing file or folder in Finder and close the launcher |
| `{"type":"copy","text":"hello"}` | Copy and close the launcher |
| `{"type":"paste","text":"hello"}` | Copy, restore the previous app and send Cmd+V |
| `{"type":"run","extension":"weather","input":"berlin","arguments":{"view":"hourly"}}` | Go to an address (below), with a chosen request. Every field is optional; `{"type":"run","title":"Delete","arguments":{"delete":"42"}}` runs the originating extension again and replaces the arguments for later edits in this command |
| `{"type":"agent","text":"Explain this"}` | Fill the input with this text and send nothing; the user presses Return. In a conversation that is the follow-up; elsewhere an open command is left and an empty conversation opens with the text as its unsent first question (no process starts until Return; Esc drops it). It is the address `agent` with an input |

Open accepts a `wicket://` URL too, which is the address it names, with the outsider rules below.

### Addresses

An address is a request plus its target: `{extension?, input?, arguments?}`. Omitted means "this one, as now": no `extension` is the extension that produced the action, no `input` keeps what is typed when that command is already open (empty when entering another one), no `arguments` means none. Going to an address ends a conversation, stops running work and enters the extension, which runs with that request, a `submit` command too. The input replaces the typed one; the arguments persist until replaced or the command is left. An unknown extension changes nothing and shows a message.

`extension` is a folder name (`weather`, or `extension:weather`). Three names are reserved: `agent` fills the input and never sends (outside a conversation it opens an empty one with the text as a draft, so Return asks and Esc discards it), `settings` opens Settings, and `clipboard` opens the clipboard history command (while its source is off, the command says how to switch it on). A folder with any of these names is reported as a discovery problem, never run. An empty `extension` (a URL without a target) is a root query, while an omitted one means the producing extension.

The URL spelling is for outsiders: `wicket://weather?input=berlin`, `wicket://agent?input=Why`, `wicket://settings`, `wicket://clipboard` and `wicket://?input=calc` (no target is a root query). It is parsed leniently: the target is the host, or else the path (`wicket:weather` works), unknown query items are ignored, and the input is percent-encoded (`+` stays a plus). A URL has no arguments, and its address is marked as a link where it is parsed, so its request is never chosen. The same resolver serves an external URL (the app registers the scheme and opens the panel on it), a `wicket://` link in any body, an agent `<item open="wicket://…"/>` and an extension's `open` action with such a URL. Wicket Dev registers `wicket-dev://` instead, so it never takes the released app's links; both schemes parse everywhere, and a click inside the panel resolves in-process either way.

**Consent.** Outsiders (agent items, links in any body, external URLs) set the extension and the input and never `arguments`: exactly what the user could type. An address from outside opens the panel on that command with the input filled, which runs a request with an input, no arguments and `chosen` false, so the contract requires that such a request has no side effects (typing already reruns the command on every keystroke); the effect of anything stays behind something the user activates with Return, whose one request is chosen. An extension's own rows may set arguments on any extension, as a run action always could; a chosen request is caused by the user, never by whoever spelled the address. Addresses name views, never effects: there is no `wicket://settings/set?…`.

Open accepts http, https and mailto, or existing file URLs for apps, folders and nonexecutable documents. Resolve symlinks before checking. Reject executable files and these suffixes, even on directories: `.command`, `.pkg`, `.mpkg`, `.dmg`, `.sh`, `.bash`, `.zsh`, `.py`, `.js`, `.scpt`, `.applescript`, `.workflow`. Decoding accepts any well-formed URL for open and reveal; `OpenPolicy` checks only when the action runs (`LauncherModel.activate`), because files change between the view and the choice, and a decode-time check made one vanished or unsafe file fail the whole view. A refused open or reveal does nothing but show a short message: the file no longer exists, Wicket does not open scripts, installers or executables, or the scheme is not one it opens.

Reveal accepts any existing file URL, executables and scripts included, because selecting an item in Finder opens and runs nothing; like open, it is checked when it runs. Agent items have no reveal.

An extension's paste loses all newlines when it is decoded; the host's own paste (clipboard history) keeps the text exactly. Paste requires Accessibility access already granted and a live previously frontmost app other than Wicket. Otherwise show an error without requesting permission or sending keys. After restoring that app, send Cmd+V only to its PID and only if it is still frontmost.

## Config

One plain `config.json`, read at start and reloaded when it changes, including atomic replacement. Watch the exact file, not unrelated usage or extension writes. An invalid edit keeps the last good state.

- `hotkey`, default `"option+space"`. Use modifiers joined with `+` and a key. Require Command, Control or Option, except for function keys. Refuse Command-letter registrations, including Shift variants, to protect editing and app commands.
- `backgroundTransparency`, from 0 to 1, default 0.15. Zero is the strongest tint.
- `providers`, the on/off record of each source: `[{"id":"math","enabled":true},{"id":"apps","enabled":true},{"id":"files","enabled":true},{"id":"clipboard","enabled":false}]` by default. IDs are unique and nonempty. A source's entry decides; a built-in or discovered `extension:<folder-name>` missing from the list takes its default, which is on for every source but `clipboard`, so a built-in added later (such as `files`) reaches a config file written before it. The order of the array does not affect results, so existing files keep working. Nothing writes config on discovery. Switching one in Settings writes its `enabled`. Clipboard history's limits are fixed, not config keys.
- `voice.enabled`, boolean, default true, including missing or empty voice configuration. False disables listen-on-opening. Live disable stops capture immediately; enabling alone does not prompt or record.
- Agent, for example `"agent":{"name":"claude","model":"sonnet","effort":"low","mode":"default"}`. Omitted agent defaults to Claude. Defaults are Sonnet or the latest advertised Terra, low effort, Auto permissions and Regular speed. `speed` accepts `off` or `on`; `streamAnswers` defaults to true.

The Wicket folder is `~/.config/wicket` (`~/.config/wicket-dev` for Wicket Dev, see Editions). `WICKET_CONFIG_DIR` overrides it for the app and headless mode; `Edition.configDirectory` is the one place that resolves it.

| Wicket folder | `config.json`, `usage.json`, `voice-timing.txt`, `theme.css`, `instructions.md`, `agent-options-claude.json`, `agent-options-codex.json`, `extension-contract.md`, `extensions/`, `examples/` | The agent works here and can edit these files |

## Agent

Wicket runs the user's installed `claude` and `codex` command line tools and speaks each one's own JSON-lines protocol over stdio. It bundles nothing, installs nothing and stores no credentials. If a tool is installed and signed in, it works.

- **Agents:** Claude and ChatGPT in the interface, mapped to Claude Code (`claude -p` with stream-json both ways) and Codex (`codex app-server`, JSON-RPC without the `jsonrpc` field). Wicket looks for each executable on PATH, then in `~/.local/bin`, `~/.npm-global/bin` and the Homebrew folders. A missing tool says how to install it and sign in. Settings shows each tool as installed or not, and whether it is signed in: opening the Agent pane runs each tool's own status command (`claude auth status --json`, `codex login status`) alongside the model listing and remembers the answer. A question never waits for that check; it just runs the agent, and a signed-out run fails with Sign in first and the tool's sign-in command, recognized from the tool's own error: Claude's `authentication_failed` assistant message, or the first Codex error with HTTP status 401 (Codex would otherwise retry for about twenty seconds).
- **Translators:** one small process connection frames JSON lines (4 MiB per message, Dispatch-queue reads, ordered stdin writes, stderr tail, an unexpected exit is a failure). One translator per CLI turns its messages into the same few events (session, text, tool, permission, finished, failed) and turns decisions, prompts and cancel into lines to send. Translators hold no process, timer or UI, so recorded traffic tests them.
- **One process per question:** each question starts its own CLI process, which ends when the turn ends, however it ends. A follow-up starts a new process that resumes the session (Claude `--resume <session-id>`, Codex `thread/resume`). Nothing runs between questions, and a changed setting just applies to the next launch.
- **Claude:** flags set the model, effort, permission mode and fast mode at launch. A prompt is a user message. Text arrives as partial-message deltas. Each permission question is a `can_use_tool` control request, answered allow (echoing the tool input) or deny. Cancel is an `interrupt` request. AskUserQuestion is declined, so the agent asks in its reply instead.
- **Codex:** the handshake is initialize, `model/list` and `thread/start` or `thread/resume`. The turn is `turn/start` with model, effort, speed and permission policy, and the thread's policy is set again at launch. Command and file-change approvals are server requests answered accept or decline. Cancel is `turn/interrupt`. The turn ends at `turn/completed` or at the thread's `thread/status/changed` to `idle` once the turn started, whichever comes first, reported once: Auto's `auto_review` reviewer streams the answer and goes idle but never sends `turn/completed` (codex-cli 0.167), while Codex otherwise sends idle right before it. A thread resumed reports idle before its turn starts, which is not an end. Idle after an interrupt is a cancel, idle after an error is that error.
- **Settings:** show only the latest model per tier. Claude uses stable Fable, Opus, Sonnet and Haiku aliases, default Sonnet. ChatGPT uses the newest listed ID matching Astra, Sol, Terra or Luna, default Terra. Missing tiers remain unavailable. Effort offers Low, Medium, High and Extra high, default Low. Permission labels Supervised, Auto-accept edits, Auto and Full access map to Claude's `default`, `acceptEdits`, `auto` and `bypassPermissions`, and to Codex's read-only, workspace-write, Auto review and full access policies. Default is Auto. Speed is Regular or Fast when the model lists it, default Regular. Saved explicit IDs stay authoritative. The tool reports one it no longer supports, and Wicket shows that message. Default and Regular remain selectable if the listing disappears. Changes apply on the next turn. Switching agent starts a new conversation.
- **Stream answers:** on by default. Off buffers text until a new message ID, tool start, completion or failure. Show the current working step and append each completed message in one update. The final body and Copy match streaming mode. Bound the whole answer at 1 MiB, including published and pending messages. The final replacement uses settled layout.
- **Permission requests** use the shared native confirmation inside the glass card. A question title, action summary, up to three file names or a command, and Show details explain the request. Use 20-point padding, 12-point spacing, a 16-point semibold title and regular buttons. Titles and body text have a two-line limit. Body text follows Text size. Confirmation cards scroll within a 560-point body cap. Full paths, commands and changes are selectable in a bounded scroll area. Abbreviate home to `~` in summaries. Don't allow and Allow once resolve the request. Cmd+Return confirms, Escape declines, plain Return does nothing and Tab visits controls. Agent-stated deletion, locations outside the working folder after resolving symlinks, or commands without reported file locations show the consequence and open details. Repeated key events are consumed while a confirmation is pending. Deletion uses Allow deletion. Allow is always once.
- **Instructions:** one bundled file, `agent-instructions.md`, is all Wicket says to the agent, and it updates with the app: context and canvas first, then each component with its use, look and one realistic line of syntax, then the rules, then a short Wicket documentation section listing where things are (working folder, extension contract, extensions folder, `config.json`, and the executable for headless tests), whose placeholders the host fills in. There is no composite example, so no house layout is taught. The owner's optional `instructions.md` in the Wicket folder is appended under its own heading. `WICKET_EXECUTABLE` can override the advertised executable path. They go in as system or developer instructions, never in a user message, so they never pile up in the conversation: Claude gets `--append-system-prompt` on every turn (its compaction rebuilds the system prompt from the current process, so a first-turn-only flag would be lost), Codex `developerInstructions` on `thread/start`, which a resumed thread keeps (checked live). A follow-up carries only the user's text. Nothing replaces either tool's own system prompt.
- **Limits:** Settings sign-in check 8 s, silence at start 30 s, a turn 600 s, model listing 10 s. A process that ends during a turn, even with exit code zero, is a failure. Cancelling waits for the CLI's answer and force-stops the process tree after 3 seconds.
- **Sessions:** the bar always holds the next question, with Ask a follow-up… during a conversation. The answer card has an 18-point inset, 15-point medium question header, two lines and Show more inside its scroll area. Copy stays upper right. The last ten earlier question/answer pairs stay in memory behind Previous questions · N. Earlier answers use selectable plain text without extra web views or file watchers. A draft remains editable during work; Return submits only a nonempty idle draft. Hotkey and clicking away hide and retain conversation, draft and pending confirmation for 300 seconds after hiding or completion, whichever is later. Work continues hidden. A permission pending at hide is declined after 300 seconds without needing to reopen; reopening or asking a new question cancels that deadline. Reopening after expiry also declines pending permissions even while the agent is busy. Reopen says Continuing conversation and Esc End conversation until the next question, which restores the actual turn status. A conversation opened by the `agent` action starts empty: no question header or Copy, a one-line hint instead of an answer, Ask <agent>… as placeholder and ↩ Ask and Esc Discard in the footer, and no Continuing conversation on reopen. Its first question leaves no empty turn behind. Escape stops voice first, declines a confirmation, cancels a running turn, then ends the conversation. In extension detail it returns to search. At root it clears input before a second press closes. No conversation survives app restart.
- **Working folder:** agent sessions start in the Wicket folder, which holds the extensions, the docs and the agent instructions.
- **Run log:** `~/Library/Logs/Wicket/agent.log` (`~/Library/Logs/Wicket Dev/agent.log`; inside `WICKET_CONFIG_DIR` when that is set, so tests and headless runs never touch the real one) records every agent run for debugging after the fact, in plain text and never through os_log. A run is a `RUN` header (agent, model, effort, mode, folder, command), then one line per JSON line `SEND` and `RECV` (raw, keys sorted, over 32 KiB cut), `ERR` for stderr, `CANCEL`, `EXIT` with the process status and `END` with how the run ended: `finished`, `cancelled`, `failed: <message>`, `timeout after <limit>`, or the reason the process was let go. Each line is `date time #run TAG text`, the run ID telling apart a stopping run and the next one. The file moves to `agent.old.log` (replacing the previous one) when it is over 2 MiB at the start of a run. Lines are written on a serial queue by one seam, `JSONLines` for the lines and `AgentLink` for the ending, so no translator knows about it; a write that fails is ignored. It holds the user's own conversation, so it never leaves the machine.
- **Process I/O:** newline-delimited JSON, with a 4 MiB per-message framing limit. Blocking pipe reads run on Dispatch queues, outside Swift's cooperative thread pool. ProcessTree owns queued stdin writes and closing input. Agent answer text is limited to 1 MiB.

### What we learned from the protocols

Checked on 10 and 11 Nov 2026 against Claude Code 2.1.321 and codex-cli 0.167.0, using the existing logins.

- **Both CLIs have a native protocol** that covers everything the design needs: streaming, follow-ups, allow and deny, changing model and effort, resuming a session after a restart, cancelling and tool progress. That made the Node adapters unnecessary.
- **A warm agent is not free.** Half a gigabyte per agent breaks the lightweight promise, so each question runs its own process, which ends with the turn. A follow-up resumes the same session, and both CLIs did so in a live check.
- **Agents inherit the user's own configuration**, including their MCP servers, which is part of that memory and start time. Wicket states this plainly and later may offer a lean profile.
- **Ready has layers.** A started process is not a signed-in one. A status command before every question cost a process per question, so Settings checks it and a question relies on the tool's own error: Claude answers `authentication_failed` at once, Codex gets 401 and retries.
- **The models come from the tools.** Claude lists them in its `initialize` response and Codex in `model/list`, both without a model call.
- **The two agents differ in small ways** that the translators absorb: Claude takes settings as flags and Codex per turn; a denied request ends the turn differently; Codex reports file changes before it asks.

Client-supplied MCP servers are not used.

## Views

Text size in General is Small, Medium, Large or Larger. Answer and confirmation body sizes are 13, 15, 17 and 19 points. Scale answer headings, code, tables and components in proportion. Result titles scale from 14 points, and row heights grow with them. Input and Settings sizes stay fixed. Footer text is at least 12 points. This config setting applies live through the single config writer.

There is one view, `{"body"?, "items"?, "actions"?}`, and its parts decide the layout. At least one of `body` and `items` must be present; an empty `items` array alone is an empty list. `type` is not read. Forms, preferences and secrets are meant to build on declared arguments (Extensions) rather than a view of their own.

| Parts | Layout |
| --- | --- |
| `items` | The native list: icon, title, subtitle and actions per item. Alone it is the only shape whose items appear at the root. |
| `body` | A Markdown body in the safe answer web view, with a native command header and the view `actions`. Return runs the first view action. |
| `body` and `items` | The body at its full height, a divider, then the native items, all in one scroll region (the web view never scrolls on its own here). Nothing is selected until an arrow key enters the items; then Return runs the selected item's first action, and typing or arrow up from the first item leaves them again. Return with nothing selected runs the first view action. View `actions` stay in the header. |

```json
{"items":[{"id":"result","title":"6.21 mi","keywords":["distance"],"prominent":true,"actions":[{"type":"copy","text":"6.21"}]}]}
{"body":"## Result\n<stat label=\"Total\" value=\"42\"/>\n<fact label=\"Source\" value=\"Local\"/>","actions":[{"type":"copy","text":"42"}]}
{"body":"## Berlin\n<stat label=\"Now\" value=\"12°C\"/>","items":[{"id":"hourly","title":"Hourly forecast","actions":[{"type":"run","arguments":{"view":"hourly","city":"berlin"}}]}]}
```

The card is as tall as its content, up to the screen-derived cap that bounds an answer. Without a body, view `actions` are ignored. Short label/value pairs are `<fact>` tags in the body; the first Wicket's native metadata list is gone. Errors use selectable native text with Copy and Ask agent buttons. The repair brief includes folder, command, JSON request, decoding path/message and stderr tail when available.

### Rich answers

Answers go beyond markdown. Plain text walls are what every other tool already offers.

- **What the agent writes:** ordinary markdown plus a few short tags, for example `<stat label="Revenue" value="€12k" delta="+8%"/>`. Tags are the cheapest thing for an agent to produce and need no schema lookup. They are custom, not HTML: tags carry only data, so the model picks what to show and the theme decides how it looks; HTML with classes invites the model to design.
- **Renderer:** the answer is converted to HTML and shown in one web view (the SwiftUI `WebView` of macOS 26). The bundled theme gives each tag its look; the owner's `theme.css` overrides it, so a new component is a few lines of CSS that you or the agent can add without recompiling.
- **Starting set:** items `answer(value, detail)`, `stat(label, value, delta, tone)`, `fact(label, value)`, `bar(label, value, percent, tone)`, `event(time, title, detail)` and `badge(label, tone)`; containers `callout(tone)`, `card(title)`, `columns` with `column`. Tones are positive, warning and negative. Repeated `stat`, `fact`, `bar` and `event` items are grouped by Wicket into `w-stats`, `w-facts`, `w-bars` and `w-timeline`; explicit group tags are accepted and ignored, so the model never writes wrappers. Containers accept markdown inside. All component names become inert `w-` elements; an unknown tag shows its text and its attribute values. Tag candidates are at most 1,024 bytes and names at most 64 characters. Scan bounded, non-overlapping candidates and substitute once. Code stays literal, using UTF-8 byte offsets for LF, CRLF and bare CR. Only streaming holds unfinished tag-like text back; a completed body keeps prose such as `use i<count in loop`.
- **Items:** `item(title, subtitle, open | copy | ask, icon)` is the one tag the page does not draw. The reply is split before rendering (`ProviderView(reply:)`): each self-closing `<item/>` outside code leaves the Markdown and becomes a `Row` with the same `RowAction` as an extension item, so the agent's reply is the same view: `body` plus `items`. A title and exactly one of `open`, `copy` and `ask` are required; anything else is dropped. `open` takes an http, https or mailto URL, a `wicket://` URL (an address, with an extension and input and never arguments) or a path that is absolute or starts with `~`; `OpenPolicy` decides at parse time, so a refused item is dropped, never shown inert, and again at action time, as for extensions. `ask` is the `agent` action. Items show below the page in one scroll region, in tag order, wherever they stand in the text. Row ids are `item-N`, so selection survives streaming. Permission prompts stay outside this system. The renderer never sees an item tag. Selection: a page starts with nothing selected, so Return in a conversation still sends the follow-up, and the same holds for an extension view with a body; the first arrow key selects the first item, up from the first item or any typing deselects.
- **The stylesheet** is the bundled theme in the `wicket` cascade layer followed by the owner's `theme.css` from the Wicket folder, so the owner's rules always win while the bundled theme updates with the app. `theme.css` is installed as a commented template listing the tokens and components, and watched as an exact file, including atomic replacement. Both are trusted local styling. The 0.1 copies `answers.css` and `agent-instructions.md` are no longer read.
- **Safety:** agent content cannot run script, load remote resources by itself or navigate. Raw HTML and images cannot become active content. Content JavaScript and subresources are disabled, storage is not persistent, and CSP uses `default-src 'none'; script-src 'none'` with inline styles only. The bundled patch/measurement bridge runs in WebKit's isolated client world, separately from page scripts. Hidden WebPage tests check bridge execution and independently check CSP on a raw page. Only http, https, mailto and `wicket://` links work, through Wicket, on a click; a `wicket://` link is an address.
- **Sizing:** the answer area is between 80 and 500 points high, grows without shrinking while streaming and may shrink on completion, and updates are batched every 40 ms. When native items sit below the body, the page is measured uncapped and the card scrolls as a whole. The web view and its empty page are created when the panel opens, so WebKit startup (about 220 ms measured offscreen) is not paid on the first answer, and released 60 seconds after the panel is hidden.
- **The launcher's own list, input and prompts stay native SwiftUI, with an AppKit text field for editing and IME.**

## Extensions

A folder under `extensions/` with `wicket.json` and an executable in any language, or only a `wicket.json` that lists items.

```json
{"name":"Deploy","keyword":"deploy","command":["./deploy.py"],"icon":"shippingbox","match":"^deploy .+$","fallback":false}
{"name":"Bookmarks","icon":"bookmark","items":[{"id":"gh","title":"GitHub Dashboard","keywords":["github"],"actions":[{"type":"open","url":"https://github.com"}]}]}
{"name":"Caffeinate","command":["./main.py"],"arguments":[{"name":"hours","placeholder":"hours"},{"name":"minutes"}],"submit":true}
```

### Behavior

- **Discovery:** watch extension folders live. No restart or build is needed. A rescan that finds the same manifests changes nothing and never restarts running work, so an extension writing files in its own folder cannot cancel itself. Invalid manifests become repair rows for enabled providers. Required are a nonblank `name` and a `command`, `items` or both. `command` is a nonempty argv with a nonempty executable and no NULs. `items` are items exactly as in a view (the same `Row` type and id rule, `Row.validIDs`). Optional fields are `keyword`, SF Symbol `icon`, regex `match`, boolean `fallback` (default false), `arguments` and boolean `submit` (default false); all but `keyword` and `icon` need a `command`. Items are read once at discovery, with their search keys prepared then (`SearchIndex` in `ExtensionCommand`), and a program may refresh them by rewriting its own manifest atomically; the folder watch picks that up like any edit.
- **Declared arguments:** `arguments` is an array of at most three `{name, placeholder?}`, names nonempty and unique. They are ordinary arguments: what the user fills in arrives under that name in `request.arguments` (an unfilled one is absent), and the extension's own run actions may set the same names. The model holds what the input bar draws (`LauncherModel.declaredArguments`, `argumentValues`, `setArgument(_:to:)`): at the root the arguments of the selected extension command row, whose values are a draft dropped when the selection moves or the panel is dismissed, and Return on that row enters the command with the draft as its arguments, in a chosen request; inside a command its own, whose values are the command's arguments, and an edit is like typing. The input bar draws them as slots (Launcher, Argument slots).
- **Submit:** with `submit: true` a command runs when an address is followed (entering it, a run action, a link) and on Return, never on typing, argument edits, voice or refreshes, which neither cancel a running request. Return with nothing selected sends one chosen request with the current input and the declared arguments; what a run action set is sent with that action's own request only, or a Delete chosen once would repeat with every later Return. Selection follows the rule of conversations and pages (`LauncherModel.itemsWait`): after typing nothing is selected, an arrow key enters the items and Return runs the selected one, typing or up from the first leaves them.
- **Execution:** no shell expansion. An extension runs straight from its own folder, which is the working directory. Relative executables and resources resolve there. Bare commands use PATH, with Homebrew/local bin paths added. Installed interpreters work, for example `["/usr/bin/python3","main.py"]`. Set `PYTHONDONTWRITEBYTECODE=1`.
- **Messages:** write one ProviderRequest JSON value plus newline to stdin, then EOF. Stdout is one JSON view without logs or fences, or Markdown, followed by successful exit. Output that starts with `{` (after whitespace) is JSON and must decode as a view, or the run fails with the decoding path; anything else is Markdown, read by the reply parser as a body with the agent's tags and `<item/>` rows. Empty output fails. Use stderr for diagnostics. One process per request. Typed edits inside a command rerun it, except in a `submit` command; speech waits until settled. Arguments persist until replaced or the command is left; they never become executable argv. Only the one request the user's activation caused is `chosen`. Esc returns to root.
- **Bounds:** 10-second deadline, 1 MiB stdout, 256 KiB stderr, retaining the last 4 KiB for errors. Cancel, timeout, completion and quit clean up the owned process tree, including descendants. Blocking pipe reads run on Dispatch queues so concurrent slow programs cannot starve cancellation or deadlines.
- **Enabled means trusted:** an extension runs when its source is on, with no fingerprint, copy, ledger or review. A new folder is on as soon as it appears. Agent-written folders too. The owner's only control is switching it off in Settings, Sources. A switched-off extension does not appear in the launcher and does not run, except by name in headless mode. Edits take effect on the next request.
- **Limits of trust:** an extension runs with the user's ordinary access. It is not an OS sandbox, and nothing checks the code before it runs.
- **Self-extension:** install `extension-contract.md`, an offline unit-converter pattern (`extensions/units`: length, mass, volume, speed and °C, °F, K) and five optional examples outside active sources: web search (`examples/web-search`), currency (`examples/currency`), quicklinks (`examples/quicklinks`, five links as items and no program), note (`examples/note`, `submit` and no arguments: a chosen request with typed text appends it with a timestamp to `notes.md` in its own folder, and every request lists the last five notes, or before the first a one-line body, Type a note and press Return.) and password (`examples/password`, declared arguments `length` and `count` with placeholders 20 and 5 and no `submit`, so it reruns as a slot changes: that many random passwords of that length from Python's `secrets`, letters, digits and a few symbols, each row copying itself; a missing, invalid or out-of-range value, beyond 128 characters or 20 passwords, uses the default). Free text such as a note belongs in the input; arguments are for short parameters (owner's review of 0.2.1). Copy one into extensions to use it. Existing installed folders stay untouched. The currency example matches only conversion-shaped input (`100 usd in eur`, `€50 to $`, the ECB's 30 currencies and `€ $ £ ¥`), downloads the ECB daily reference rates at most once a day into `rates.json` in its own folder, falls back to an older cache when offline, and names the source and rate date with its age in the row subtitle. Its amounts read a lone mark before three digits as grouping, since an extension gets no locale. The contract tells authors to put short answers in row titles, use detail views for more, and keep row IDs stable, with a weather example. `extension-contract.md` is Wicket's reference and is rewritten from the bundle at every launch, so agents always read the current rules; the extensions and examples install only if their folder is absent, preserving local edits. The agent instructions point to the contract, extension directory and headless executable. Two real Claude authoring runs produced working extensions.
- **Parity:** aliases, prominent copy rows, empty-input patterns and native file/app icons express app launch and math through this contract. The compiled app provider keeps its search index warm in memory and rebuilds it on watched filesystem changes. A run-once replacement must maintain its own index/cache. Long-running extension lifecycle remains deferred.

### Triggers and ordering

| Trigger | Declared as | What happens | Example |
| --- | --- | --- | --- |
| Name | `name`, `keyword` | Fuzzy matched while typing. No program until chosen; choosing it sends a chosen request with empty input and any filled-in declared arguments | "Deploy" |
| Pattern | `match`, a regular expression | Matches run and publish one complete view at root when the process finishes | `100 usd in eur`, an equation |
| Fallback | `fallback: true` | Offered after Ask agent when nothing matches strongly; choosing it preserves the root input | "Search the web for …" |
| Items | `items`, a list of items | Name matches at the root like apps, by title and keywords, with no process; only for nonempty input, the best 20 per extension. An item without `icon` takes the manifest's, without `subtitle` the extension's name | Bookmarks, snippets, a list of commands |

- Wicket checks regexes without running a script. Patterns may match empty input. Limit regexes to 512 UTF-8 bytes and input to 4,096 bytes, with a 5 ms regex progress deadline. A newer keystroke cancels old work and drops stale views. There is no incremental row streaming.
- Provider IDs are `math`, `apps`, `files`, `clipboard` and `extension:<folder-name>`. Users can switch sources on or off or replace built-ins with extensions. Sources the list omits take their default: on, except `clipboard`. Ordering is fixed; see Result order.
- An extension with `items` and no `command` still has its command row, and Wicket answers that command itself: the view is its items filtered by the typed input with the same matcher (all of them for empty input), ordered as below. Nothing runs, so a list of thousands is a searchable command. With a `command` too, the program answers as usual and the items are extra rows at the root. An item's `run` action without `extension` means its own extension.
- Within a chosen extension command, exact title/alias, then a prefix from a word start (the same tiers as the root), then the order the extension returned. Learned usage plays no part there, and picks made inside a command are not recorded. Rows need not match the query to remain visible.
- Strong means math, a nonempty successful pattern result, or a name match with tier 1 or 2 (exact, or a prefix from a word start). Empty input keeps apps first and suppresses fallbacks. If nothing is strong, Ask agent moves on top and fallbacks follow it, ordered by name.
- A pattern result with a body becomes a row to enter the command; at the root only items contribute. Detail and fallback choices preserve root input; only a name choice clears it. A selected failure row enters the command with the root input, which runs it again and shows the full native error with its report, as entering it any other way would. Each is an ordinary `run` address; the fallback row's request is chosen, the detail and error rows only show what the pattern produced and are links, never chosen.
- Request and response are single JSON values, so a later long-running protocol can reuse them line by line.

## Headless command-line mode

The same executable handles these modes before NSApplication, with no window, status item or hotkey. It uses the real config, usage, app scan, discovery, ranking and extension runner, without watchers.

```sh
Wicket --query '10 km in mi'
Wicket --extension note --input 'buy milk' --chosen
Wicket --extension password --arguments '{"length":"32","count":"3"}'
```

Choose exactly one of `--query TEXT` or `--extension ID`. `--query` uses enabled sources only. `--extension` runs any discovered extension, even a switched-off one, because naming it is the consent. It accepts a folder name or `extension:<folder-name>`, optional `--input TEXT` (default empty), `--arguments JSON_OBJECT` of strings (default `{}`; an array is an error) and the flag `--chosen` (sends `chosen:true`, as choosing a run action would). Arguments are literal option values, without shell reinterpretation. `--help` prints a JSON usage object.

Query output is `{input,items:[{provider,row}],askAgent:{onTop,reason}}`, including Ask agent in the ordered items and file results once their Spotlight query has finished. Each row shows its real actions, so the output says what Return does. Pattern failures appear as error rows. Direct invocation prints the decoded view, or for an extension without a command the view Wicket answers itself from its items. Failures print `{"error":"..."}` and exit 1; success exits 0.

`WICKET_CONFIG_DIR` selects the working folder. For authoring tests, run `Wicket --extension <folder>` directly. No scratch folder or flag is needed.

## Decisions

| Decision | Outcome |
| --- | --- |
| Fresh repository or reshape the first Wicket | Rewrite with selective ports, landed in this repository as 0.1 with the first Wicket in git history. See [COMPARISON.md](COMPARISON.md) |
| Rich answers | Drawn in a web view styled by one CSS file |
| Style of rich answers | The stylesheet follows native SwiftUI and macOS design as closely as it can: system fonts, sizes, spacing, colours and control shapes. The web view is a flexible canvas, not a different look |
| Panel background | Less see-through than the prototype, so content stays readable over busy backgrounds. Transparency is a preference |
| App launch and math | Compiled Swift behind the extension contract, switched on and off in the same Sources list as extensions |
| Result order | Fixed by match quality, with learned usage only breaking ties. Users cannot reorder sources; they switch them off. One pure function serves the panel and headless mode |
| Extension trust | Removed. An extension runs if its source is on, from its own folder. New ones are on at once; the user switches them off in Sources. `--extension` runs any discovered extension. Agent permission requests are unchanged |
| Extension items | A manifest may list items, read once and ranked with apps through the same door (`Ranking.Names`); no process runs while typing. Root ids are prefixed `item:` so they never meet the command row's. A known list is items; a computed answer for what was typed is `match` |
| Arguments | Named, an object of strings, replacing the positional array (concept review of 12 Nov 2026, finding 2), with no reading of the old array: a broken extension shows its repair row and the agent fixes it. A manifest declares at most three for the user to fill in; they are ordinary arguments. `chosen` is the user's activation, derived from whether an address is a link, never from whether it has arguments. `submit` makes a command take its input like a conversation: Return sends. An action's menu name is its `title`, never derived from its arguments |
| Screen switches | Wait for the new screen's first content, up to 150 ms, and switch content and height together (owner's complaint on 0.2.1: entering Note left the long root height under an empty list, then shrank). Collapsing to the bar at once and growing on arrival was rejected: a command with many items would flash small then large. No animation hides it |
| File search | Native, through Spotlight with MDQuery and no index of our own; files are name matches ranked after every other kind in their tier, at most eight, with open and reveal. Not an extension: `mdfind` cost more latency and the contract had neither the ranking nor reveal |
| Open-action files | Existing apps, folders and nonexecutable documents only; reject scripts, workflows and installers, resolve symlinks and recheck on use |
| Distribution | One repository for the released app and Wicket Dev; same bundle ids, signing team and Sparkle key as 0.0.x, so installed copies update to 0.1 |
| This document | Kept current with what is built, in enough detail to rebuild Wicket from it |

## Lessons so far

Things that cost time or surprised us, worth knowing before any future rebuild.

- A custom tag language is cheap for the agent and expensive to parse yourself. Let an existing engine read it.
- A warm agent process costs about half a gigabyte. Run one process per question and resume the session.
- A started agent process is not a signed-in one. Recognize the tool's own signed-out error instead of checking before every question.
- Panel focus, input methods, and process trees are subtle. Carry tested code forward.
- On-screen testing by agents disturbs whoever is using the Mac. Keep logic testable without a window and batch the screen checks.
- A build nobody has looked at must never be handed over. Offscreen pixels and geometry tests cannot prove glass or focus; those need a person at a real window.
- Most of the size difference from the first Wicket comes from design decisions and omitted scope, not demonstrated redundant code. Those decisions came from designing the product from first principles without reading the old code first. See [the size comparison](docs/size-comparison.md).
- An independent review early on found two serious defects: blocking pipe reads starved the cooperative thread pool, and CRLF crashed the tag adapter. Both were fixed with regression tests; independent review of each larger change is worth its cost.
- The first panel jittered while typing and looked plainer than the first Wicket. Stable panel sizing and visual polish are not free by-products of a rewrite and need their own attention.
- A device-change observer added in one review round broke voice on a Bluetooth microphone. It treated a normal startup notification as failure, and hardware-free tests missed it. Fixes at hardware edges need a hands-on check before they are called done.
- Audible testing on a machine in use is forbidden. Never play speech or sounds, change devices or volume, or save microphone audio. An explicitly allowed silent probe does not replace real dictation and device-switch checks.
