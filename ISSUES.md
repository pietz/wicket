# Known issues

Open problems and unverified behavior, checked against the code on 11 Nov 2026. Fixed items are not listed; git history has them. What is planned is in [ROADMAP.md](ROADMAP.md).

## Before publishing a release

Nothing here needs code. Each needs a person on a real Mac, or credentials.

- **Sparkle upgrade path** worked from 0.0.15 to 0.1.0 and on to 0.1.1 on the owner's Mac. The cask path is unchecked.
- **A settings reset for existing users.** 0.1 does not read 0.0.x's `settings.json`, usage, voice or approval files, nor its extensions (another protocol); a customised hotkey falls back to ⌥Space. Nothing is deleted (a test pins this). Say it in the release notes; migration is in the roadmap.
- **Permissions under the release signature.** The microphone grant and any login item from 0.0.x are keyed by the same bundle id and team, so they should carry over; confirm once. Launch at login with a Developer ID build is unverified.
- **Hardened runtime with WebKit and Sparkle.** The release bundle verifies (`codesign --verify --deep --strict`) and runs headless, but the GUI paths (web view, Sparkle's update window, speech) were not exercised in the signed bundle.

## Product

- **Reference files are installed once.** The contract also has no version, and the request carries none, so neither side can tell which contract an extension was written against. The answer theme and display instructions now load from the app with owner files layered on top; `extension-contract.md` and the bundled `units` extension are still copied into the config folder only if absent, so a Wicket update never refreshes them. Installed extensions that still print `{"type":"list","rows":...}` keep working because `rows` is read as `items`, but the installed contract text is stale and teaches the agent the old shape. Decide how upgrades deliver changes (an installed version marker, or a diff the user can accept) without overwriting local edits.
- **Enabled means trusted.** A new extension folder, including one an agent writes, runs as soon as it appears, with the user's access and no review; an agent that edits an enabled extension changes what runs next. Edits during a run can affect it, since there is no copy. This is deliberate (SPEC, Extensions), but pattern-triggered runs are invisible: Sources does not show when an enabled extension runs on its own. The architecture review of 11 Nov 2026 sharpened this: the agent works in the Wicket folder, so even in Supervised or workspace-write mode, writing an extension turns a contained file write into unsandboxed execution on a later keystroke. The reviewers disagree on the fix: gate new pattern extensions behind explicit activation, or keep enabled-means-trusted and make it visible (announce new extensions, show pattern runs, say plainly that permission modes do not contain the agent in its own folder). A gate is only complete with content fingerprints, which is the ledger that was removed.

### Architecture review, 11 Nov 2026

Two independent reviews (GPT-6 Astra, Claude Fable 5.2) that then read each other's findings. Both would keep the foundation: one view shape for agent, extensions and built-ins, data-only tags in WebKit, one process per question, plain files, headless testing. Claims marked verified were checked in the code.

- **Host rows are still special in name search** (verified). Apps, files and extension items reach `Ranking.compose` through one list of sources, but the Settings and Clipboard History rows are made inside it, and the view branches on `provider == "apps"`. File search stays native (see SPEC Decisions), so a file catalog from an extension would rank alongside it, not replace it.
- **File search is outside the provider contract** (verified). It streams batches through its own `batches` path because `Provider` returns one view. Proposed: an internal cancellable stream of views, with run-once scripts as one update; external JSON-lines streaming only when an extension needs it.
- **Per-agent facts live outside the translators** (verified). `agent == .claude` branches in `AgentCLI`, `AgentOptions` and `AgentDiscovery`; SPEC's "no per-agent integration code" is out of date. Proposed: one agent definition per CLI beside its pure translator. Model choice offers only the curated tiers, so a newly advertised model outside them needs a hand edit. The run log should record the CLI version.
- **Extension paste strips newlines** (verified, `Provider.swift`), although extensions are trusted, so a snippets extension cannot paste a paragraph. The request has no locale, which the currency example works around.
- **Component behaviour is partly compiled in** (verified). Grouping names and `badge` as the one inline tag are in `AnswerMarkdown`, so a user component cannot group or sit inline; each component is described in four files. Proposed: generic grouping of adjacent same-name tags with layout left to CSS.
- **Reply parsed per delta** (verified, minor). Once a reply contains `<item`, `answer.didSet` reparses the whole reply on the main actor for every delta; parse in the 40 ms render batch.
- **Product claims.** "Bring your own agent" is two hard-coded CLIs; ACP over a user-supplied command is a later adapter, not a priority. An installed copy cannot read its own source; give the agent a version-pinned repository URL. "No other launcher does this" is unverified; both reviewers prefer "requests become dependable reusable commands" as the promise.
- **Card and component polish** (a review, not yet checked in the renderer): cards side by side can have unequal heights; the guidance should say facts are for short label/value pairs and tables for comparable records; bars deserve an accessibility pass.
- **Renderer memory and speed** were measured only on a prototype (242 ms first paint, 37 ms later, 95 MB before and 178 MB after first web-view use). A matched measurement of the integrated app, with the same answers and machine, cold and warm, process-tree memory before, during and after the release delay, is still to do.
- **Agents inherit the user's own configuration**, including MCP servers, which costs start time and memory per question. Wicket says so; a lean profile is a later option.
- Conversations do not survive an app restart.

- **File search limits.** Spotlight caps hits at 500 before sorting, so for a common prefix the best name may be outside the sample; relevance was never measured against labelled ground truth. Loose files directly in home are not searched (a scope must be a folder). Files on FAT and exFAT volumes usually carry the executable bit, so `OpenPolicy` refuses to open them and they only reveal. Reveal in Finder has no key yet, only the context menu (ROADMAP, Actions menu).
- **Omitted sources are now on.** File search needed existing `config.json` files, which list only math and apps, to pick up a new built-in, so a source the list omits is on and only `"enabled": false` switches one off. A hand-written `"providers": []` no longer turns every built-in off.

### Items, arguments and submit (review of 12 Nov 2026)

- **Entering a command by its name is now chosen.** An extension written against the old rule that acts on any chosen request (`if chosen: deploy()`) now acts when it is entered. The bundled programs do not; extensions the agent wrote earlier need a look. Array `arguments` are refused with a decoding error, after the program ran.
- **A catalog change reruns an open command and cancels its running request**, also a chosen one. An extension that rewrites its `wicket.json` to refresh items must do so last; another extension rewriting its manifest at that moment still interrupts. Refresh only when the open command's own entry changed.
- **The 20 best items per extension are picked by fuzzy score alone**, in manifest order among equals, before tier and usage apply. In a large list a much used item can stay out for a short input; looking usage up per item costs a JSON encoding each.
- **Return twice in a submit command sends twice**: the input and slot values stay after a submit, so a second Return repeats it. Decide whether a submit clears them.
- **Slots at the trailing end** of the pill, not after the typed text, because a field that grows per keystroke fights AppKit's scrolling and IME text.

## Process I/O

- **No backpressure on a slow consumer.** `FileHandle.chunks(limit:perLine:)` stops reading once a flood exceeds its limit, but it yields into an unbounded `AsyncStream` and never waits for the consumer, so a slow reader of a fast writer that stays under the limit can still let read-ahead pile up. Bounded for floods, not backpressured.
- **`Launch.capture` is uncapped.** The Settings sign-in check (`claude auth status`, `codex login status`) appends all stdout into `Data` until the process ends or the 8 s limit passes. Only the time is bounded, not the bytes.
- **Agent stderr is uncapped.** `JSONLines` keeps the last 4 KiB of stderr, but reads it without a byte limit, so a process that floods stderr is read to the end, at CPU cost though not memory.

## Code debt

From a review of an earlier snapshot, rechecked against the current code. The first three items of that review (extension trust, one query composer, screen captures inside the app) are done, as are the Node runtime, the module merge, the voice teardown relay and the duplicated agent handshake.

- **Launcher state is implicit.** `LauncherModel` has no mode value: the open command, its view, problem and busy flag, the conversation and the confirmation are separate properties reset together in several places. One `mode` (search, command, conversation) and one `confirmation` property would remove a class of missed-reset bugs. Risk: medium, covered by `ProviderTests`, `ConversationTests` and `VoiceTests`; check panel jitter by eye afterwards.
- **Callbacks instead of Observation.** `onResultsChange` is called from about fifteen places in the model and `onChange` from `AgentSession`, `ExtensionHost` and `ConfigurationStore`, wired by hand in `AppDelegate`. macOS 26's `Observations` sequences could replace them. Observation coalesces, so the panel may resize one run-loop turn later; panel stability was hard won.
- **`model.problem` carries several things** (config errors, hotkey conflicts, provider errors, paste errors) and is cleared by checking `hasPrefix("Config:")`. Keep each source separate and let the footer pick.
- **Two hardware serialization schemes in voice.** `Microphone` (lock plus an opening stream) and `EngineCapture` (serial queue) both serialize open and close. One class on one serial queue would do. Only with a hands-on voice test: a review fix here once broke Bluetooth voice.
- **Small leftovers.** `ProcessTree.exitStatus` and `Shutdown.notRunning` are unused. `Result` (in `Composition.swift`) shadows `Swift.Result`; rename it when touching those lines. `SettingsActivation` exists only to call a deprecated method without a warning. `ExtensionFailure` is used as the general message-carrying error, including by the headless mode.
- **A flaky voice test.** `transcriptActivityCannotExtendTheHardLimit` failed once in four full runs on 12 Nov 2026 (a 500 ms limit against 20 ms sleeps under parallel load); like the disabled permission test it needs an injectable clock.
- **Capture test.** Nine states whose text WebKit draws (answers, conversations, extension detail) fail the text-recognition check on the home server, before and after the changes of 12 Nov 2026.
- **Tests.** The hotkey `Handle` fake is declared four times in `SettingsTests` and `KeyHandlingTests`; share one. `HeadlessTests` runs `.build/debug/Wicket` from a hard-coded path and silently depends on a debug build existing (`Scripts/check.sh` builds first); say so in the test or build the product from it.
- **Voice permission test is disabled.** `permissionWaitDoesNotUseStartupOrCaptureDeadlines` raced its 250 ms startup timer against the session's first update under parallel test load (failed about one full run in three). Not a product bug; re-enable it once `VoiceInput` takes an injectable clock or sleep so the test fires deadlines itself.
